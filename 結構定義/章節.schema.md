# 結構定義：章節（正文源 `chapters/chNNNN.md` ＋衍生 `chapters/chNNNN.ai.md`）

> **這是什麼**：定義「幕綱寫成散文後」長怎樣。這是子專案 B（撰寫）的核心 schema——把幕綱的結構化欄位（角色／時空／行動／衝突／結果）展開成有場景、有對白、有感官細節的正文段落，同時保留可回溯到幕綱的錨點，讓因果與伏筆的機械可追溯性不因進入散文層而中斷。
> **2026-07-27 重構輪（功能 03）**：本 schema 宣稱的格式從此**都有守衛**（`設計原則.md` E1）。新增 `ch-lint --book <書>`（`tools/beat_metrics`，與 `beat-lint` 同套件共用幕號 registry）——幕錨點五條、`對應幕` ≡ 正文錨點集合、front-matter 六鍵、`_index.ai.md` 的視圖一致性與備註欄；成長哨兵的目標集補上 `chapters/`；`prose-metrics` 補上章密度參考行。本輪拍板的理由與**被駁回的方案**寫在各條規則旁邊（F2：跟著它保護的規則走），逐項可搜「已駁回」。診斷與拍板全文見 `docs/重構/功能報告/03-正文章節.md`。
>
> **本次重設計的核心變更**：章節改成**正文（源）／metadata（衍生）分離**——正文 `chNNNN.md` 是純散文人管源，機讀 metadata（對應幕／POV／基調・風格參照／狀態）移到衍生 `chNNNN.ai.md` 的 front-matter。**幕界錨點 `<!-- 幕NNN -->` 是唯一例外**：它內嵌回正文源檔（HTML 註解不可見、不礙人讀改），因為錨點必須貼著散文位置才有意義。所有權見 `共同約定.md` 二。
> **方法依據**：`技巧知識庫/場景與情節推進.md`（Scene/Sequel 展開）、`展示而非講述與五感描寫.md`（句子層級執行）、`視角與敘事人稱.md`（POV／知識邊界）、`敘事距離與DeepPOV.md`（Deep POV／心理距離調控）、`對白.md`（對白句型與壞習慣）、`動作場面寫作.md`（動作場面專項，選用）、`畫面感與電影化.md`（運鏡／示現／插敘／轉場）、`修辭與字句鍛鍊.md`（譬喻／擬詩／映襯／字句，依取向定位選用）、`心理描寫.md`（內在描寫五技法＋疼痛描寫）、`字詞句法與抗生硬.md`（抗生硬地板）、`網文與文學取捨.md`（取向定位決定節奏、爽感密度與文字功底門檻）。

## 用途

章節＝依作者拍板的分章方案，把連續幾幕的幕綱內容展開成正文。

**幕綱是「結構」的單一真實來源（因果鏈、伏筆狀態、賭注、結構階段），正文不得牴觸它；但正文不是幕綱的渲染結果。** 正文是**人管·源**（見 `共同約定.md` 二）——它是「這個世界具體長什麼樣」實際居住的地方：在場的人、他們說的話、房裡的物件、動作與環境，都是在這一層第一次存在。**正文合法地增加資訊，這不是發明設定，這就是寫作。**

分界走 `共同約定.md` 七「承諾與演出」：**承諾**（設定層／幕綱／事實流已釘死的）遵守，**演出**（其餘一切）自由發明；事後才回報該升格的部分。把正文當成「不能增加資訊的渲染輸出」，會讓幕綱一抽象、正文就跟著空——這是本 schema 刻意修正的既往措辭。

正文可隨時重寫，不影響幕綱本身的正確性。

## 檔案配置（正文源／metadata 衍生 兩檔）

```
chapters/
  chNNNN.md        # 人管·源：純散文正文＋內嵌幕錨點 <!-- 幕NNN -->（無 front-matter）
  chNNNN.ai.md     # AI管·衍生：對應幕/所屬arc/POV/基調・風格參照/狀態（front-matter，重生自同名 .md）
  _index.ai.md     # AI管·rollup：權威章序表；源＝本資料夾所有 chNNNN.md 的集合
```

- **每章兩檔**：正文源 `chNNNN.md` 由作者／`write` 自由編輯（散文修改權在作者，見規則）；`chNNNN.ai.md` 由 `write` 生成、`derived-sync stamp` 封章，作者**不手改**機讀事實。
- **章號補零 4 位**：`ch0001.md`、`ch0002.md`……**全書連續編號，不因跨 arc 而重置**。補零使檔名字典序＝章序，避免 `ch10` 排在 `ch2` 前。
- **`_index.ai.md` 是權威章序**（見下），不是 `_index.md`——章序表由 `write` 依實際章檔重生。

### chNNNN.ai.md 的「源」是 chNNNN.md（重生語意）

`chNNNN.ai.md` 經 `tools/derived_sync` 以同 stem 對映到 `chNNNN.md`——**改動正文即令對應 `.ai.md` stale**，提示「正文變了，metadata 該重新校對」。重生時：

- **對應幕**＝直接掃描正文裡的 `<!-- 幕NNN -->` 錨點抽出（機械可導，見下「幕錨點規範」）。
- **POV／基調・風格參照／狀態**＝`write` 落筆時的決定，重生時**沿用並複核**（正文改動未動到涵蓋的幕時，這些欄不變；若正文改到跨進別的幕，`write` 據新錨點更新並提醒作者）。
- 校對後 `derived-sync stamp chNNNN.ai.md` 封回新 hash。

### 章號不預配號段（與幕號的不對稱是刻意的）

`幕綱.schema.md` 替每個 arc 預配 100 個幕號，**是因為幕號是連結標的**——`[[幕NNN]]` 前因、`埋/收[[伏筆:x]]` 所在的幕、正文錨點 `<!-- 幕NNN -->` 全都指著它，重編號得追著散落各處的引用改，代價極高、明令禁止。

**章號不是連結標的**：沒有任何產物用 `[[chNNNN]]` 指向章節，章號只活在檔名與 `chapters/_index.ai.md`。所以章號**不預配號段**，`write` 也**不替尚未寫成的上游 arc 猜測預留章號**——猜測本身才是風險（猜少了會與已寫的章相撞，猜多了留下一段永久空洞）。

亂序下沉、先寫後段的 arc 時：從當下最小的可用章號往後編，`_index.ai.md` 以「（未寫）」列標出前面 arc 的幕範圍。日後補寫排在前面的 arc，若作者要讓章號回到閱讀順序，改**檔名（正文源＋衍生對一起）、正文檔頭標題、`_index.ai.md`** 即可，沒有引用要追。挪不挪由作者決定——`_index.ai.md` 的「對應幕」欄才是章與幕的權威對映，章號只是檔案的名字。

## 正文源 `chNNNN.md` 的格式（純散文＋內嵌幕錨點）

```markdown
# ch0001 · 禁忌的叮嚀與焚夜

<!-- 幕001 -->
（幕001「禁忌的叮嚀」的 Scene 正文……）

<!-- 幕001→幕002 -->
（銜接幕001到幕002的 Sequel／過渡正文，若份量足以成獨立段落才另起錨點……）

<!-- 幕002 -->
（幕002「溜進畫廊」的 Scene 正文……）

……
```

- **正文源只含**：章名標題（`# chNNNN · 章名`，供人閱讀）＋純散文＋內嵌幕錨點。**無 front-matter、無 metadata bullet 列**——那些一律在 `chNNNN.ai.md`。
- **章名標題留在正文源**是刻意的：作者讀改的是這份檔，標題貼著內容才好認；它是人性化標籤、不是機讀事實（機讀章序在 `_index.ai.md`）。

### 幕錨點規範（唯一內嵌回正文源的機讀標記）

> **守衛：`ch-lint --book <書>`**（`tools/beat_metrics`）。下面每一條都標了它是第幾項；
> 觸發時機是 `write`／`revise` 落檔後與 `write-test` 開頭（見「規則」節）。
> **2026-07-27 之前這六條一條都沒人守**——`<!-- 幕NNN -->` 是全 repo 唯一「有機讀標記、
> 零解析器」的地方，唯一碰到它的程式（`prose_metrics`）作用是把它**剝掉當雜訊**。
> 一世之尊 108 個錨點全清，是 AI 一路寫下來的紀律，不是系統保證的乾淨（`設計原則.md` E1）。

- **`<!-- 幕NNN -->`**：標記緊接其後段落主要在渲染該幕的 Scene（Goal/Conflict/Disaster）正文。同一幕若跨多段，只需在第一段前標一次，直到下一個錨點出現前都視為同一幕的延伸。
  - 幕號**必須存在於幕綱**（全書某支 `arcNN.md` 有 `## 幕NNN`）——`ch-lint` 第 1 項。
  - 章內錨點**單調遞增**（正文順序＝幕的演出順序）——`ch-lint` 第 2 項。
- **`<!-- 幕NNN→幕MMM -->`**：標記兩幕之間的 Sequel／過渡正文（銜接前一幕結果到下一幕動機的反應/兩難/決定）。若過渡文字很短（一兩句話），可省略獨立錨點、併入前一幕錨點段落尾端。
  - 兩端都要存在於幕綱，且 `NNN < MMM`——`ch-lint` 第 4 項。過渡錨點**不進單調序列**（它夾在兩幕之間），也不算「這一章寫了那一幕」。
- **為何內嵌正文（唯一例外）**：錨點必須**貼著散文位置**才有意義（它標的是「這一段在渲染哪一幕」）；抽到 `.ai.md` 就失去定位。HTML 註解對讀者不可見、不礙閱讀與編輯，是承載它的自然容器。`chNNNN.ai.md` 的 `對應幕` 欄即由掃描這些錨點導出。
  > **✗ 已駁回「一幕一檔」**（把錨點升格成檔名，2026-07-27）：過渡散文屬於兩幕**之間**，會被迫生出 `幕017→幕018.md`；更致命的是要讀一整章就得有合成檔，而合成檔是衍生的、不能編輯——**有 UI 的寫作工具替你隱藏了這層成本，這個系統沒有 UI**。作者修訂時是打開一整章讀過去，章就是連續編輯單位（`設計原則.md` C2）。完整理由見 `docs/重構/02-待用構想.md` 已駁回清單。
- **作者可用人性化標記**：作者手寫過渡時可用 `--- 幕002 ---` 這類好認的分隔，`write` 落檔時正規化回 `<!-- 幕002 -->`。
  - `ch-lint` 第 5 項**偵測並報「請正規化」，不代改**——代改是編輯動作，閘門只回答「這份檔還是不是它宣稱的那個格式」。同一項也報「註解裡有幕號卻不是標準錨點」（一般編輯註解不冤枉）。
- **不新增第二套 ID 系統**：一律沿用幕綱既有的 `幕NNN` 編號——正文層的追溯基準仍是幕綱編號，呼應幕綱「單一真實來源」的精神。
  > **位數不固定，不要寫 `幕(\d{3})`。** 本條 2026-07-27 前寫「三位數」，那是錯的：幕號預配號段是每 arc 100 個（`幕綱.schema.md`），**arc10 之後必然溢出三位**——實測一世之尊 arc11 起是 `幕1001`。repo 內 8 處工具正則全用 `\d+` 所以沒炸，但**照舊 schema 寫的新工具會 silently 前綴匹配**（`幕1001` 讀成 `幕100`），不報錯、給出一整批假的不一致。本輪第一次量測就踩過這個坑。所有解析器一律 `幕(\d+)`。
- **一幕不可跨章節切開**：章節邊界只能落在某個 `幕NNN` 錨點之前或某個過渡錨點之前，不可把同一幕的 Scene 正文切成兩半分屬兩章。**全書「幕號 → 章」是單射**——`ch-lint` 第 3 項。

## 衍生 `chNNNN.ai.md` 的格式（AI 生成，嚴格）

```markdown
---
generated-from: <chNNNN.md 的 hash>   # 由 tools/derived_sync stamp 蓋，勿手填
generated-at: 2026-07-19
對應幕: [幕001, 幕004]                  # 多幕寫 [起, 訖]；單幕寫 [幕001]。由掃描正文錨點導出
所屬arc: arc01
POV: { 角色: 小女巫, 人稱: 第三人稱有限, 距離: Deep POV }
基調參照: 00-摘要.md「基調」            # 不重抄基調全文，只指參照來源
風格: 風格.ai.md                        # 本章套哪份風格檔
狀態: 草稿                              # 草稿／已定稿
---
## 本章事實                             # 本章釘下的狀態／錨；格式見 事實流.schema.md
- 幕002（arc01）· 少年 · 知識前沿：＋尚不知〔信物用途〕
- 幕002（arc01）· 少年 · 錨〔信物的形制〕：巴掌大、缺一角的青銅牌
```

（範例用中性泛例，非任何書內容——schema 範例一律不引某本書的實際章節，以免污染以該書做盲測的驗證。）

### `## 本章事實`（本章正文釘下了什麼）

本區塊住 `狀態`（6 維 delta）與 `錨`（正文釘死的數字·專名·道具語彙）；**`約束` 不住這裡**，它屬 `story/物件/<實體>.md` 的「## 不得寫成什麼」（信封格式見 `事實流.schema.md`，約束表格式見 `物件.schema.md`）。

**它為什麼住在衍生檔**：狀態與錨是**該章正文的函數**——重讀那章就能重算。住進隨正文走 hash 偵測的 `.ai.md`，作者改了正文，`derived-sync check` 就報 stale，重生即修正。這是它與 append log 的關鍵差別：append log 沒有任何機制發現「釘下這條事實的正文已經被改寫了」。

- 位置欄寫**幕號**（`幕NNN（arcAA）`），不寫章號——一章可跨數幕，且章號可亂序。
- 幕號須落在本檔 `對應幕` 區間內、arc 須與 `所屬arc` 相符。**由 `fact-lint` 守**（2026-07-27 補；在那之前這條承諾掉在 `fact-lint` 只讀行、`derived-sync validate` 只讀 front-matter 的分工縫裡，**沒有任何檢查器**）。有事實行卻缺這兩欄也會報——那時候沒有任何東西能核對這些事實掛對了章沒有。
- 未產生任何事實的章可省略本區塊。

**內容欄只寫「這一幕改變了什麼」**（純化紀律，`fact-lint` 在守）：

- `知識前沿`／`持有`／`能力` 是**集合維度**，寫操作串：`＋已知〔X〕`／`＋尚不知〔X〕`／`〔X〕→已知`／`−〔X〕`。**仍然成立的舊事一律不重抄**——它還在舊那筆裡，`fact-project --history <實體>/<維度>` 查得到。`知識前沿` 的命題名須是幕綱登記過的伏筆名。
- `位置`／`所屬`／`關係` 是純量，寫自由文字、維持覆蓋。
- **不得夾帶別條軸的東西**：伏筆埋/收屬幕綱、裁決理由屬 `裁決流.md`、下游排除線屬 `story/物件/<實體>.md` 的「## 不得寫成什麼」。門檻：內容欄 >200 字、括號內註解佔比 >40%、出現「不得／守死／射程／留白」這類語彙，`fact-lint` 都會報。

> **為什麼要有這三條**：實測某本書（93 章）事件**筆數**每 arc 都是 15–36 沒有成長，**內容欄**卻從 76 字脹到 194 字、括號佔比 36%→52%——兩個機制分別是「覆蓋語意逼出的重抄」與「唯一會被 write 讀到的欄位變成什麼都能塞」。集合維度解掉前者，本三條擋掉後者。

### 欄位說明

**六欄皆必填**，由 `ch-lint` 第 7 項守（缺鍵／`狀態` 越出枚舉／`POV` 缺子欄都報）。

| 欄位 | 可不可重生 | 說明 |
|------|-----------|------|
| 對應幕 | ✅ 正文的函數 | 多幕寫 `[起, 訖]`、**單幕寫 `[幕001]`**（見下）；由掃描正文 `<!-- 幕NNN -->` 錨點導出；一章對應一段**連續**幕範圍，不交錯覆蓋其他章已涵蓋的幕 |
| 所屬arc | ✅ 正文的函數 | 對照 `story/幕綱/arcNN.md`；須與錨點實際落在的 arc 相符（`ch-lint` 第 6 項） |
| POV | ❌ **不可重生** | 本章固定的敘事視角角色＋人稱／距離；v1 每章僅一位 POV 角色（不同章可切換，同章內不可）。格式 `{ 角色: X, 人稱: Y, 距離: Z }`，三個子欄都要有 |
| 基調參照 | ✅ | 只引 `00-摘要.md`「基調」，供撰寫與 write-test 核對一致性；不重抄 |
| 風格 | ❌ **不可重生** | 指向 `story/設定/風格/` 下某風格檔（見 `風格.schema.md`）。**2026-07-27 由選填改必填**：舊規則說「單一風格檔時可省略，預設 `風格.ai.md`」，而**沒有任何工具實作那個 fallback**（grep 全 `tools/` 確認）——一條沒有讀者的預設值，只會讓 `write-test` 測試5 拿不到本章該對照哪份風格檔 |
| 狀態 | ❌ **不可重生** | `草稿`／`已定稿` 兩值（`write` 產出一律先標「草稿」；作者確認後可改標） |

#### `對應幕` 的寫法（單幕 `[幕N]`、多幕 `[起, 訖]`）

`ch-lint` 第 7 項驗這一條：**單幕不得寫成 `[幕N, 幕N]`、多幕不得寫成單值**。

> **為什麼是這個形狀**（2026-07-27 作者拍板）。實測一世之尊三種寫法並存：`[幕N, 幕N]` 52 支／`[幕N]` 26 支／`[起, 訖]` 15 支，而下游解析器（`fact_projection/chapters.py`）三種都吃——**寬鬆是刻意的**（那支檔的註解寫著「這一欄是機讀的，但它終究是人會看、偶爾會手改的一行」），只是沒有任何東西在收斂它。
> **✗ 已駁回「一律 `[起, 訖]`」**：那會讓 78/93 章帶一個冗餘的同值寫法，換到的只是「解析器少一條分支」——而解析器本來就要留那條分支給手改的人。
> **解析仍然寬鬆、只是寫法會被報**：讀得懂就讀，形狀不對另外報一筆。閘門的職責是指出格式漂了，不是讓下游讀不到資料。
> **新書適用**；`一世之尊` 是刻意保留的病例書、不遷移，所以 `ch-lint` 在它身上會一直報這一條（**聚合成一行**，不是 52 行）。

#### `POV`／`風格`／`狀態` 是**不可重生**的三欄（重生時必須帶舊值）

這三欄是 `write` 落筆時的**創作決定**，不是正文的函數。把 `.ai.md` 全刪掉、只拿 `chNNNN.md` 重跑一次：「第一人稱」抽得回來、「這一章故意用誰的視角」抽不回來（`共同約定.md` 零第二問的判準）。它們住在會被重生的檔裡，所以：

- **重生紀律與 `## 本章事實` 完全相同**：`write`／`revise` 重生某章的 `.ai.md` 時，**必須把舊的這三欄帶進 context** 當基準，不空白重判。改一個錯字就洗掉本章的 POV 宣告，比不重生還糟。
- **守衛只守得住一半，另一半誠實承認**：`ch-lint` 驗得了「三欄存在、`狀態` 在枚舉內、`POV` 三子欄齊、與 `_index.ai.md` 的視圖一致」（第 7／8 項），**驗不了「重生前後未變」**——那是跨時間斷言，而系統不保存「上一版」（git 歷史不是系統的一部分）。第 8 項是它的**間接守衛**：重生洗掉 POV 而 `_index` 沒同步重生時會當場被抓到；兩邊同時洗掉就抓不到。依 E1，schema 只宣稱守得住的那部分。
- **這條縫在單 POV 的書上永遠看不見**：一世之尊 93/93 章都是同一個 POV 角色，所以它結構性地不會暴露。第一本多 POV 的書才會踩。
- **✗ 已駁回「搬進正文源 `chNNNN.md`」**（作為檔頭一行或 HTML 註解）：那在 `設計原則.md` A1 上更正確（作者的決定該住源檔），但會打破「正文源只含散文＋錨點、無 metadata」這條乾淨且被三支 skill 依賴的規則——代價比病灶大。
- **✗ 已駁回「維持口頭紀律、什麼都不標」**：本書看不出來 ≠ 沒問題。

## 章密度規範（分章單位＝一個節奏單位）

- **章＝一個節奏單位**，有兩種、都合法：(i) 一個**閉合**的爽點/情緒循環（小起承轉結），或 (ii) **一段連續張力線中的一節**——本章只結一個小節拍，那條宏觀目標**跨章不閉合、持續悶燒**。分章單位是「節奏單位」，不是「篇幅感」。**不是每章都得閉合**——整段（數章）都各自閉合小勝利、章末各自打包，正文就會碎、無記憶點（見下「反模式②」與 `技巧知識庫/場景與情節推進.md` §六）。
- **依 `00-摘要.md`「取向定位」定基準**：**中文網文向預設一章一幕的粒度**（一幕＝一個 Scene）、**約 3000 字**（起點體例）＋章末鉤子；文學向才容許章節自然收束、跨幕邊界較鬆。**「一章一幕」只定粒度、不等於「每章都要閉合一個完整爽點循環」**——該幕的 Scene 可只推進一條跨章張力線而不了結它。
  > **3000 字是「參考體例」，本系統不設達標線**（2026-07-27 作者拍板）。`共同約定.md` 九要求一條書級宣告連帶寫出「單位／達標線／誰核對」——這一條有前兩者、缺第三者，於是實測一世之尊 **13/93 章達 3000、40/93 < 2000、21/93 < 1500**，而唯一在守章長的 `prose-metrics` 判準是**相對本書前段**，前段基準 2,616 字/章本身就低於宣告 → **絕對缺口在結構上測不到**。
  > **補上的核對者是 `prose-metrics` 的「章密度（參考體例，非判定）」節**：讀 `00-摘要.ai.md` 的 `取向定位` 原文照抄，印「N/M 章 ≥3000 字」。**不設門檻、不進可疑點、不影響 exit code**——它印的是一個數字，不是一個判定。
  > **✗ 已駁回「給它一條達標線」**：章長依張力起伏重分配（高潮 set-piece 厚、過場薄）是本節下一條就在講的事，任何門檻都會把正確的做法報成問題。**✗ 也駁回「刪掉這條宣告」**：它是本 schema 唯一一條「有單位、可數、只缺核對者」的宣告，補完比刪掉更符合 `共同約定.md` 九。**✗ 並駁回「拿關鍵詞判這本書偏不偏網文再決定要不要印」**：那要用詞表分類中文形容詞，正是「幫基調加機讀欄」被駁回的形狀（見 `docs/重構/02-待用構想.md`）。
- **兩個反模式（皆避免）**：①把兩個各自完整的爽點循環壓進一章 → 蒙太奇→承重事件被塞進子句→下一章引用即「跳躍、要回頭查」（字數遠超 3000 是信號）；②每章各自閉合小勝利、**章末總結式收尾**、宏觀張力從不跨章 → 碎片化、無記憶點。
- **章末三種切法（`write` 撰寫章邊界時選一種；細則見 `技巧知識庫/戲劇張力與懸念.md` §二）**：**硬切斷章**（下一章緊接同一張力→停在未解畫面/動作、不回顧不預告）、**前開式軟鉤**（用具體新擾動向前拋）、**收束斷章**（段/arc 邊界才閉合＋喘息、鉤子仍是新擾動非回顧）。**反模式「總結式收尾」明令避免**：章末用「回顧本章處境＋預告未來」的抽象總結段收尾（例：「他站在一個死人的屋子裡…欠著死人的債」／「三日之後，真正的那個人要親自來了」）＝講述，是「硬要總結感」的來源；續接章根本不該收攏、硬切即可。
- **字數依張力起伏重分配、非等長勻平**（3000 字為基準非死線，依段落自然邊界浮動）：一段的**高潮幕鋪成 set-piece**（厚）、**過場幕壓薄**（快），並安排喘息/日常節拍與峰後餘韻讓記憶點長出來（見 `場景與情節推進.md` §六）。某幕遠不足基準且與鄰幕合成一節奏單位→可併章（作者拍板）；某幕遠超基準含多循環→訊號是幕綱該拆幕（回 `beat-sheet`），受「一幕不可跨章切開」限制、`write` 不硬拆。
- 方法依據見 `技巧知識庫/網文與文學取捨.md`（節奏速度·連載鉤子強度）、`場景與情節推進.md` §五（單章快慢）§六（跨章張力線·快慢交替·餘韻）、`戲劇張力與懸念.md` §二（章末三種切法）、`Data/跨語言技巧/結構與節奏.md`（連載單位）。

## `chapters/_index.ai.md` 格式（AI 生成，權威章序）

```markdown
---
generated-from: <本資料夾 chNNNN.md 集合 digest>   # rollup，見 共同約定.md 三
generated-at: 2026-07-19
---
## 章節索引
| 章 | 對應幕 | 所屬 arc | POV | 風格 | 狀態 | 備註 |
|----|--------|----------|-----|------|------|------|
| ch0001 | 幕001–幕004 | arc01 | 小女巫 | 主世界 | 草稿 | 女巫夜訪，信物易手 |
| ch0002 | 幕005–幕007 | arc01 | 小女巫 | 主世界 | 草稿 | 畫廊失竊，第一次照面 |
| （未寫） | 幕008–… | arc02 | — | — | — | arc02 幕綱尚未拆出/尚未撰寫 |
```

- 每次 `write` 新增/更新章節時，重生本表並 `derived-sync stamp _index.ai.md`。
- 表尾可加一列標示同一 arc／全書尚未寫成章節的幕範圍，避免作者誤以為已全部完稿。
- **這是章序的權威來源**（不是檔名）：亂序下沉時「對應幕」欄才是章↔幕的權威對映。
- **前六欄是各章 `chNNNN.ai.md` front-matter 的視圖，不是第二個家**——兩邊不一致就是有人只重生了一邊。`ch-lint` 第 8 項逐列比對（`幕001–幕004` 與 `[幕001, 幕004]` 是同一件事，比的是語意不是字串；POV 比 `角色` 子欄），並驗「有章衍生檔卻不在表裡」與「表裡列了不存在的章」兩個方向。

### 「備註」欄：只住兩種東西

**① 表尾「（未寫）」列的範圍說明　② 一行極短的章摘要（這一章演了什麼），上限 100 字。**

由 `ch-lint` 第 9／10 項 ＋ 成長哨兵（`derived-sync check` 的 `DERIVED_BYTES` 與 `ROLLUP_LINE_CHARS`）共同守。

**三類內容明令不得住這裡**（各有自己的家）：

| 不得住這裡 | 它的家 | 為什麼 |
|---|---|---|
| `埋\|收[[伏筆:x]]` 標記 | `story/幕綱/arcNN.md` 的「伏筆」欄，查詢走 `foreshadow-project` | 幕綱是伏筆的單一真實來源。這一份**沒有任何工具讀**，於是實測已經漂移：索引 18 標記/15 名 vs 幕綱 20/16，**3 個名字對不上**（分隔符漂了一個、各只在一邊各一個）。`ch-lint` 第 9 項擋 |
| 結構階段（起／承／轉／合） | 幕綱的「結構階段」欄與 `story/參照/結構.ai.md` | 已經有兩份了，這是第三份 |
| **幕排序設計註**（為什麼這幾幕這樣排、哪個護欄沒觸發、本輪拍板了什麼） | 幕綱檔尾 `## 設計註` → `story/參照/裁決流.md` | **那是幕的排序理由，不是章的東西**，而且它**不可重生**——住在 rollup 衍生檔裡，下次重生就沒了，而 `.ai.md` 沒有 diff 會被審。100 字上限讓它在結構上寫不進來 |

> **100 字這個門檻是量出來的**（同成長哨兵各門檻的作法）：一世之尊健康群 arc01–arc04 是 33／53／48／54 字/章、**最大 92**；漂移群 arc05 起 88 → 347（arc09），最長 561 字——那 561 字就是一整段幕的排序理由（`ch0075` 列）。100 落在兩群之間的空隙。
>
> **本輪只清內容、不裁形態**（2026-07-27 作者拍板抉擇 2 C）。`chapters/_index.ai.md` 是成長型產物（實測每列 196 B → 781 B，4.0×；500 章外推 ≈381 KB）而**沒有投影入口**，依 `設計原則.md` D3 它可能根本該是 `ch-project` 的輸出而不是一支檔——但那與 §10 就緒儀表、§12 rollup 是**同一個判斷**，先在這裡拍板等於替後面三個功能定調。**已登記為欠債**（`共同約定.md` 八的查詢入口表有這一列），形態隨 10／12 一起裁。

> **「章末狀態快照」這個區塊已刪除**（2026-07-27）。它是僵屍規格：本 schema 定義它、`derived-sync validate` 的枚舉允許它、`write` 說「改由投影衍生」，而**沒有任何工具產生它**——實書裡只剩兩行引用已改名工具（`state-project`）的殘骸。
>
> 要人眼可讀的章末切片，跑 `fact-project --as-of <該章末幕>`，**不落檔**。理由見 `共同約定.md` 八：那是「理解全局」用的，依 D3 該是投影輸出而不是一支檔；落檔就會變成第二份真相，而且沒有人負責重算它。

## 規則

- **正文修改權在作者**：`write` 產出的 `chNNNN.md` 是可直接編輯的草稿，不是受保護的定稿。正文源改動後，對應 `chNNNN.ai.md` 由 `derived-sync check` 報 stale，`write`／`revise` 據新正文重新校對 metadata 並封章。
- **機讀事實不手改**：`chNNNN.ai.md` front-matter 由 `write` 生成、工具封章；作者要改 POV／風格指定，改的是「請 write 重寫這章」的決定，不手動改衍生檔（改了下次重生即覆蓋）。
- **`## 本章事實` 的重生紀律——以舊 delta 為輸入，不空白重抽**：「哪些事實值得登記成錨」是判斷不是計算，同一章重抽兩次可能得到不同集合。`write`／`revise` 重生某章時，必須把**舊 delta 帶進 context** 當基準（「上次抽了這些，正文只改了 X 段，只調對應的那幾筆」）。空白重抽會讓作者改一個錯字就洗掉整章的事實登記——那比不重生還糟。
- **同一條紀律涵蓋 front-matter 的 `POV`／`風格`／`狀態`**（2026-07-27 補）：那三欄與 `## 本章事實` 一樣不是正文的函數，重生時一律**帶舊值進 context**，不空白重判。它們為什麼留在 `.ai.md`、以及守衛守得到哪一半，見上面「欄位說明」。
- **改到錨就要查下游**：重生後若某個 `錨〔名〕` 的值變了，跑 `fact-refs --anchor 〔名〕`——它拿新舊值去 grep 全書正文，找出**已經按舊值寫下去**的章。`derived-sync` 看不到這一半（那些章的 `.md` 沒動、hash 沒變），而正文的矛盾是讀者會看到的那一種。
- **落檔後跑三個格式閘門**（各自擁有自己那份格式的唯一真相，不建跨工具相依）：
  - `ch-lint --book <書>`（`tools/beat_metrics`）——**本 schema 的主要守衛**：幕錨點五條、`對應幕` ≡ 正文錨點集合、front-matter 六鍵、`_index.ai.md` 的視圖一致性與備註欄。它與 `beat-lint` 同套件、共用幕號 registry（`structure.parse_book`），但**是獨立指令**：`write`／`revise` 落檔後要驗的是正文層，不該同時吃到幕綱那邊與它無關的問題（同 `object-lint` 是 `fact-lint` 聚焦入口的先例）。
  - `derived-sync validate --book <書>`——驗 `.ai.md` 的結構：`generated-*` 必填鍵、`##` 節在封閉枚舉內。
  - `fact-lint --book <書>`——驗事實信封行的格式與落點（含「事實行的幕號 ∈ 本章 `對應幕`」）。
  - **三支都先印「我檢查了幾筆」**（`設計原則.md` E2）。`ch-lint` 印「N 章正文源／N 個幕錨點／N 支章衍生／N 列章序」——**剛寫完一章而錨點數是 0，那不是乾淨，是解析器沒讀到你的檔**。
- **待裁決回饋走衍生檔**：撰寫時若發現問題根源在**幕綱**，走「建議作者直接編輯幕綱或重跑 beat-test」（幕綱是作者利器·直改，無回饋區）；若溯源到**世界觀／00-摘要／角色／風格**，在 `story/參照/待裁決.md` 追加一列（`標的` 欄寫該源檔路徑，格式見 `待裁決.schema.md`），交 `worldbuild`／`character`／`develop` 提請作者改源後重生。對「章節本身」的回饋（罕見）也寫同一支檔，`標的` 欄填 `chapters/chNNNN.md`。
- **不做自動一致性追蹤**：幕綱若在章節寫成後又被修改，本 schema 不要求自動比對／自動標記過時（`derived-sync` 只偵測「正文源動了」這一類；幕綱→章節的語意過期走 `sync` 語意比對）。

## 檢查點（供 write-test 參照）

> **機械那一半已經有工具了**（2026-07-27）：下面凡標「`ch-lint` 已驗」的，`write-test` **不再由 LLM 逐章做集合差**——先跑 `ch-lint`，LLM 只做它剩下的那半（判斷題）。`write-test/SKILL.md` 測試1 從 2026-07-27 之前就寫著「這是最高優先級的**機械事實，不需 LLM 判斷**」，而那時**沒有工具**，執行者一直是 LLM。

- **幕涵蓋完整性**（`ch-lint` 第 6 項已驗機械那半）：本章「對應幕」範圍內每一幕，是否都能在正文中找到至少一個 `<!-- 幕NNN -->` 錨點？`chNNNN.ai.md` 的 `對應幕` 是否與正文實際錨點一致（不一致＝該重生封章）？**LLM 只判**：命中的錨點段落是否真的在渲染該幕的 Scene，還是掛名湊數。
