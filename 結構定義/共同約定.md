# 結構定義：共同約定（所有 skill 共用）

> **這是什麼**：所有寫作 skill（develop／organize／outline-test／beat-sheet／beat-test／write／write-test／revise／sync／worldbuild／character／expand）共用的基本約定。各 SKILL.md 以一行引用本檔，不再各自複述——避免十來份逐字重複的條文各自漂移。
> **修改本檔＝修改所有 skill 的行為**，變更前先確認影響面。

---

## 一、資源定位（不得寫死絕對路徑）

- **技巧知識庫／結構定義**：讀「本寫作系統 package 根目錄」下的 `技巧知識庫/` 與 `結構定義/`（與 `.claude/` 同層）。不確定根目錄時，從當前工作目錄向上尋找「同時含這兩個資料夾的目錄」。
- **書內容**：`raw/`、`story/`、`chapters/` 一律相對於「作者當前所在的那本書資料夾」。作者未指明是哪本書時，先確認。

## 二、四種所有權（本系統的骨架）

每個檔案都歸入一種所有權，決定「誰能寫它、有沒有 schema」。**動任何檔前先確認它的所有權**。

| 所有權 | 誰寫 | schema | 例 |
|--------|------|--------|-----|
| **人管·源** | 作者自由寫，**無格式要求**（重可讀可改） | 無 | `raw/`；設定層 `<實體>.md`（角色／世界觀／風格）；`00-摘要.md`；章節正文 `chapters/chNNNN.md` |
| **AI管·衍生** | AI 依「源」重生，**作者不手改** | 嚴格（`.ai.md`） | 設定層 `<實體>.ai.md`、`_index.ai.md`、`_總覽.ai.md`；`00-摘要.ai.md`；章節 `chNNNN.ai.md`；`chapters/_index.ai.md`；`就緒儀表`／`結構`／狀態事件流**投影**（綜合檔，宣告式·不帶 `.ai.md`·不走 hash） |
| **AI管·append log** | AI 章末追加，只增不重生 | 嚴格 | `狀態事件流.md`（狀態的唯一真實來源） |
| **作者利器·直改** | 作者直接改，含可機讀連結語法 | 中（連結語法） | `大綱`、`幕綱` |

### 源 → 衍生（本次重設計的核心）

- **源是唯一真實來源**；`.ai.md` 是「重生自源的建構產物」，如同 `.c`→`.o`。衍生檔**只會「新鮮／過期」，不會與源漂移**——因此拆兩檔不違反單一真實來源。
- **作者只碰源檔。** 衍生檔即使被誤改，下次重生即覆蓋；整個衍生層可隨時由源整批 rebuild。
- 衍生檔**照樣 commit 進 git**（本 repo 刻意版控書內容；衍生檔小、且 skill 讀它當 context）。

### 衍生檔 `.ai.md` 格式（混合：MD 殼＋YAML front-matter）

```markdown
---
generated-from: 3f9a1c…      # 對應源檔（正規化後）內容的 hash，見第三節
generated-at: 2026-07-19
角色: 凱                       # 以下為「機器事實」：對映／旗標／禁用詞表／維度狀態…
所屬arc: [arc01, arc03]        #   供 tools/ 快而準地讀（YAML，可程式解析）
伏筆: { 埋: [怕水], 收: [] }
影響力: 高
---
## 需求四象限                  # 以下為「prose 分析」：供 LLM skill 讀
- 期盼：…
- 想要（誤導）：…
## 限制與代價 / 升格哨兵
…
## 待裁決回饋                  # 下游 test 發現的可疑點 append 於此（見第四節）
```

- **機器事實放 front-matter**（YAML），**prose 分析放 MD 本體**。哪些欄位是機器事實由各產物 schema 規定。
- `_index.ai.md`／`_總覽.ai.md` 是 rollup 衍生檔：其「源」＝同層所有源 `*.md` 的集合（見第三節 digest 規則）。

## 三、變動偵測與同步

- **機械偵測（`tools/derived_sync`）**：對每個 `<實體>.ai.md`，重算其源檔正規化 hash，與 front-matter 的 `generated-from` 比對；不符即 **stale**。這給「像 git 那樣偵測人動了設定」但零外部 DB——hash 隨檔走。
  - 正規化＝統一換行、去每行尾空白、去檔尾多餘空行（見 `tools/derived_sync`），使無語意差異不誤判。
  - rollup（`_*.ai.md`）的源 digest＝同層各源 `<檔名>:<內容hash>` 排序後再 hash——**新增／刪除／改動任一同層源檔都會令 rollup stale**。
  - skill 重生某 `.ai.md` 後，呼叫 `derived-sync stamp` 把新 hash 蓋回 front-matter（別手算）。
- **stale 的處置**：偵測器只報「哪些衍生檔過期」；**重生內容是 skill（LLM）的工作**（worldbuild／character／write…），不是偵測器能做的。整批重生＝把偵測器列出的 stale 清單逐一交對應 skill。
- **深層語意過期**（結局→伏筆回收、題旨→立場鋪陳幕、世界觀規則→幕可行性）**仍走 `sync` 的語意比對**；機械偵測只管「人動了某源檔」這一類，兩者互補。

## 四、下游回饋（動尾改頭的落地）

- 下游發現問題根源在上游的「設定／摘要」時：**不改源、不改衍生的分析區**，而是在對應 `.ai.md` 的「## 待裁決回饋」區依 `結構定義/回饋記錄.schema.md` **追加一列**。
- 由 `worldbuild`／`character`／`develop` 回頭消化：提請作者修改**源檔**，再重生 `.ai.md`（回饋列隨重生清掉或轉「已採納」註記）。
- **幕綱沒有回饋區塊**——它是「作者可直接修改的利器」；發現幕綱問題只在對話中指出，建議作者直接改或重跑 `beat-test`，不代寫。
- 更新 `就緒儀表` 時，順手發現某 `.ai.md` 有「待裁決」列，於對應列備註欄加註「⚠️N 筆待裁決回饋」（被動偵測，不另開掃描流程）。

## 五、AI 角色 ＝ 共創 ＋ 審稿（非門檻）

- **所有創作決定權在作者。** AI 提草稿、抓重點、攤開選項與後果，但承重的創作抉擇（主角、結局、題旨、排幕、分章、任何一段文字）必須由作者拍板，絕不代決。
- **審稿員不是門檻。** 所有測試／診斷輸出「可疑點報告」交作者判斷，不做自動 pass/fail、不設數值門檻；嚴重度標示僅供排序參考。
- AI 產出的一切（骨架或散文）都是**可編輯、非受保護、非定案**的草稿。

## 六、揭示層級標記（🧊 水下）

有些設定與角色動機是**後段才向讀者揭示**的（母愛護盾的機制、反派的真動機）。這類條目寫進設定層 `.ai.md` 時，用下列標記註明它何時揭示。

### 語法

```markdown
（🧊 水下｜揭示於 收[[伏筆:母愛護盾]]）      ← 指向幕綱裡的回收點
（🧊 水下｜跨集留白，本書不揭）              ← 本書內不揭示
```

**每個 🧊 標記必須二選一**：指向一個伏筆名，或明標跨集留白。伏筆名須與幕綱裡的 `收[[伏筆:x]]` 完全一致（沿用 `幕綱.schema.md` 的連結規範）。

### 為什麼是指標，不是描述

**揭示時機的唯一真實來源是幕綱的 `收[[伏筆:x]]`。** 這裡只放一個指向它的連結，不用散文複述「此條於結局引爆」——那等於在幕綱之外另立第二本揭示帳，正是 `幕綱.schema.md`「伏筆不另立登記簿」刻意避開的壞味道。要知道某條 🧊 何時揭示，去幕綱查它的 `收` 在哪一幕。

### 解析規則

- **判先後不能比幕號大小。** 幕號是穩定 ID、不代表全書順序（見 `幕綱.schema.md`「幕號配號規則」）。要判斷某個揭示點排在某章之前或之後：先查該幕屬於哪個 arc，再對照 `story/幕綱/_index.md`「全書順序」比較兩個 arc 的先後；同一 arc 內才以幕號序為準。
- **揭示點還不存在是合法狀態。** 🧊 指向的伏筆名若在所有幕綱裡都還找不到 `收`（例如該 arc 尚未拆幕），標「揭示點待落幕」列為**資訊、非可疑點**——比照「本 arc 伏筆狀態」表對刻意留白的處理。

### 分工

- **寫標記**：`worldbuild`（世界觀）、`character`（角色）、`develop`／`organize`（冷啟動時發現該留水下的條目）——皆作者確認後，寫進衍生 `.ai.md`。
- **驗標記**：`beat-test` 機械核對每個 🧊 是否解析得到 `收` 點或明標跨集留白。
- 標記是**給下游看的資訊**，不是門檻——它讓下游知道「這條在某章是不是還在水下」，不阻擋任何撰寫決定。

## 七、承諾與演出（下游能自由發明什麼）

上游永遠不可能前置窮盡所有細節——幕綱寫不完一個房間裡有什麼、誰在場、說了哪句話。本節定義下游（尤其 `write`／`revise`）**哪些必須遵守、哪些可以自由發明**。

### 兩類，一條線

| | 定義 | 下游怎麼對待 |
|---|------|------------|
| **承諾** | 上游已經釘死、下游不可牴觸的事實 | 遵守；要動它得回上游改 |
| **演出** | 其餘一切——在場的人、房裡的物件、天氣、一句寒暄、一個動作、對白的措辭 | **自由發明** |

**承諾的範圍是可列舉的三處**，不多不少：

1. `story/設定/**`（世界觀規則、角色事實、風格約束）
2. `story/幕綱/`（因果、伏筆埋收、賭注、結構階段、arc 承諾區）
3. `story/參照/狀態事件流.md`（實體六維度的當下值；查詢走 `tools/state_projection` 投影）

### 邊界規則

- **動筆前只回答一個「查詢」問題**：**上游有沒有講過這件事？** 有 → 遵守；沒有 → 自由。
- **不要回答「預測」問題**（「這個細節算不算承重／後面會不會被依賴」）。預測不可判定，查詢可判定——**把不可判定的預測換成可判定的查詢，是本節的全部用意**。要求下游預先分類每個細節，實測結果是它乾脆什麼都不寫。
- **沉默＝授權。** 上游沒寫的細節就是下游的。幕綱**不必寫「留 write 現場長」**這類標記——那是預設，不是例外；要限制某個細節，把它寫成承諾。
- **判不準時，先把場面寫出來，再把那條可能承重的斷言報出來。** 兩件事不衝突，不要為了避免標記而放棄演出。

### 升格走既有機制，且永遠在事後

某條演出事後若判定該升格為承諾：

- **狀態型**（某實體某維度的變化）→ `write` 章末 append 進 `狀態事件流.md`（見 `狀態事件流.schema.md`）。
- **新規則／新設定事實** → 在對應 `.ai.md` 的「## 待裁決回饋」追加一列（見第四節），交作者裁決是否改源。

**這是事後回報，永不作為動筆前的閘門。** 一致性由三件既有的事承擔：下游讀前一章正文對腔、狀態投影、事後的促升偵測（`write-test`）。**本節改的是順序（先演出、後回報），不是取消回報，也不新增第二本帳。**

## 八、context 取用契約（skill 該把什麼讀進來）

書愈長，產物愈大——這是**正確的**，一本 500 章的書本來就比 30 章的書記得多。問題不在檔案大，在於 skill 預設**整檔讀**：於是單次執行的 context 載入量隨書長度線性成長，最後擠掉真正該用來寫作的注意力。

### 硬規則

> **skill 不得整檔讀取「成長型產物」，一律經投影／選取工具取用。**
> 需要新的取用切面時，**加投影，不要在 SKILL.md 裡寫「請只讀相關部分」這種規勸**——規勸不會被執行，工具會。

### 成長型產物與各自的查詢入口

| 產物 | 為何成長 | 查詢入口 |
|------|---------|---------|
| `story/設定/角色/*.ai.md`、`story/設定/世界觀/*.ai.md` | 角色／主題愈來愈多 | `settings-select --arc arcNN [--beats 幕N-幕M]` |
| `story/參照/狀態事件流.md` | 每章 append 事件 | `state-project --as-of 幕NNN（arcAA） --entities …` |
| `story/幕綱/*.md`（跨 arc 的伏筆帳） | 每個 arc 一檔 | `foreshadow-project [--arc arcNN] [--open-only] [--suspect-only]` |
| `story/幕綱/*.md`（幕的可演性＋母題自我複製） | 每個 arc 一檔 | `beat-metrics [--arc arcNN] [--detail]` |
| `chapters/*.md`（全書正文的結構統計＋解說段掃描） | 每章一檔 | `prose-metrics [--per-chapter] [--exposition-list --range chNNNN-chNNNN]` |

工具一律以 `uv run --project <套件根>/tools/<工具> <指令> --book <書資料夾>` 呼叫，**唯讀、零 LLM、可覆算**。

另有 `derived-sync check --book <書>`：除了衍生檔新鮮度，會附帶印出**成長哨兵**（幕綱每幕位元組、源檔單檔上限、綜合檔單行長度）。哨兵是 advisory——**不計入需處理數、不影響 exit code**，但它是「檔案形態開始走樣」唯一的自動訊號，別忽略它。

### 不受此限的

- **人管·源**（`raw/`、設定層 `<實體>.md`、`00-摘要.md`、`chapters/chNNNN.md`）：系統已用「一實體一檔、檔名即選擇器」控制單檔大小，整檔讀是安全的。**代價是單一源檔不該無限長**——某支源檔明顯肥於同層其他檔時，提示作者拆檔，不要改成「只讀一部分」。
- 該 arc 自己的幕綱、風格檔、摘要：本來就是單檔且有界。

### 為什麼是工具而不是規勸

每個測試 skill 都已宣告「**機械可抽取部分**（確定性）vs **LLM 判語意部分**」。長期以來「機械」那一半是**靠 LLM 讀整份檔案**執行的——既貴又會漏。凡確定性的工作（掃標記、配對、計數、選檔、算 as-of、統計）一律進程式，LLM 只做判斷。

## 九、宣告型約束（書級宣告要能被核對）

書級宣告——**基調**、**取向定位**、**節奏檔位**、各種**配額**——共有一個失效模式：宣告寫下來了，然後沒有任何一層對它負責，成品與宣告脫節而無人察覺（診斷01 P9／P11 就是同一條）。

### 三件事，缺一不成立

一條書級宣告落檔時，必須連帶寫出：

| | 問什麼 | 反例（等於沒宣告） |
|---|---|---|
| **(i) 單位** | 這條在**哪個尺度**上成立：每章／每 arc／全書？ | 沒寫——於是單章跑測試時判不了，逐 arc 跑時也沒人跑 |
| **(ii) 達標線** | 怎樣算做到了？寫成**可數或可指認**的形式 | 「貼身喜劇」「節奏偏快」「資訊密度偏豐富」——讀感形容詞，不可證偽 |
| **(iii) 誰核對** | 哪個 skill、在哪一層、對照什麼判？ | 沒指定——每個 skill 都以為別人管 |

> **寫不出這三件的不是宣告，是願望。** `develop`／`organize` 落檔時發現某條宣告缺這三件，**停下回問作者，不得直接封章**——比照 `風格.schema.md`「`可用句式` 不得所有檔位都碎在同一個最粗的一級」的處置。

**已經是本節實例的既有規則**（不在此重述，改到那邊看）：`風格.schema.md` 的 `可用句式`「只宣告顆粒度、值要可數」與「不得全碎在同一級就停下回問」、`摘要.schema.md` 的「常態段宣告靠長線大謎供能時，`貫穿大懸念` 要可指認」。

### 「可核對」不等於「機械可測」

達標線要可核對，但**不強求有機械量**。有些宣告實測就是量不出來——這時 (iii) 指定的核對層是 **LLM 逐 arc 判**，而不是放棄核對。

**基調就是這一類**（2026-07-25 實測）：拿一份喜劇簽名詞表掃一世之尊逐 arc，arc10 掉到 0.00 次/千字、arc11 又彈回 1.02，arc03/06/07/09 全在中段——**任何門檻都會過度回報**。故基調不設機讀欄、不進 front-matter，核對走 `write-test` 測試5 的**逐 arc、相對本書前段**語意判斷（判準紀律同 `prose-metrics` 漂移：拿這本書自己的前段當尺）。

> 這條路徑是 2026-07-22 作者裁決（否決「加基調機讀欄」，四理由存檔）指定的：「**未來要機械化的正確順序＝先驗證、再泛化**……動的也應是 schema 的『檢查點』清單加一行文字，而非加機讀欄。」本節就是那個泛化。**不要再提「幫基調加一個 front-matter 欄」**——已測過、不成立。

### 與「地板／天花板／配額」的關係

`技巧知識庫/_index.md`「技法的三種效力」分的是**技法**的效力；本節管的是**書級宣告**怎麼寫才能被核對。配額型技法的密度上限是跨書恆定的（歸知識庫）；配額型**宣告**（這本書的某個東西每 arc 至多幾次）才歸本節。判斷歸誰，問 `風格.schema.md` 那句：**換一本書，這條會不會不一樣？**
