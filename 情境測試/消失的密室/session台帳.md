## S9 新長出的、七軸表沒有的三格（交階段 3）

1. **一支閘門的 docstring 指示呼叫者拿它的輸出去對照一份語料不同的宣告，而那份指示生出了一列假的待裁。** `rhythm.py:46-47` 逐字寫「對照本書參照語料或 `可用句式` 宣告」，而 `句長中位` 掃全部段落（`:305-309`）、宣告剔掉帶「」的行（`風格.md:50`）。在對白段佔 23–41% 的書上系統性低報 4–6 字。**代價可覆算**：`待裁決:19` 掛了兩天、題目是「常態段該寫回 20–30 還是重切恐怖檔」，而**常態段從來沒有站在 16，它站在 21**；同一列推導出的「恐怖檔位落差預算被預支」也跟著整條倒過來。**與 S7 交出的「呼叫者吃掉 exit code」同族**：閘門印對了，讀的人拿到一個錯的東西——只是這次錯的不是數字，是**該拿它去比什麼**。而且**這一格比那一格更難發現**：exit code 那格至少有一個正確值可以對照，這一格的兩個數字都是對的，錯的是它們被放在同一個句子裡。
2. **`write-test` 的 11 項全部瞄準正文，而本輪最貴的三個發現全部在正文的上游——它們是副產品，而副產品沒有守衛。** 三個「高」沒有一個的結論是「正文有病」：一個是判準被拿去對錯的語料、一個是判準被讀在錯的粒度、一個是承諾區長出了上游沒有的量。**三次都是受測體為了驗正文才去讀那幾支上游檔**（`風格.md:50`／`敘事距離與DeepPOV.md:13-22`／承諾區 `:7`），也就是說**這種發現的產生機率等於「審稿員這次剛好讀到哪幾支上游檔」**。沒有任何一支 skill 的職責寫著「審上游判準」，也沒有任何閘門看得見「承諾區宣告了一個上游沒有的約束」（`beat-lint` 守格式，而這是內容）。**與 S7 第 3 格（沒有任何閘門量得了一個提案的檢索覆蓋夠不夠）是同一個病的另一面**：那一格是漏讀造成假的健康，這一格是**碰巧讀到造成真的發現**——兩者的共同點是**覆蓋率不是被設計的，是被抽籤的**。
