# 待裁決

> 依 `結構定義/待裁決.schema.md`：下游流程（`beat-test`／`write`／`write-test`／`expand`／`revise`…）在細節層發現「問題根源其實在上游設定／摘要」時，先落地記錄於此，交作者裁決是否回寫**源檔**。**只記錄，不代寫。**
>
> **這支檔的合約**（`共同約定.md` 零）：AI 寫、**你可以直接改、改動會留著**（沒有東西會重生它）、格式由 **`decision-lint`** 守。它與大綱、幕綱、`story/物件/<名>.md`、`裁決流.md` 同一列：**作者利器·直改**。
>
> **這裡住「還沒裁決的」；「已經裁決的」在 `裁決流.md`。** 兩者是**兩筆內容**：這一筆的決定權在 AI（它是觀察），那一筆的決定權在人（它是裁決）。一列混兩種決定權就該拆——實測混住的下場是那個只允許一個值的 `狀態` 欄被寫成 440 字論證。
>
> **沒有 `狀態` 欄，這是刻意的。** 這張表只住待裁決的，狀態是恆真的。**離開＝刪列**，而刪列的同時要在 `裁決流.md` append 一列記下「為什麼這樣裁」。
>
> **查詢**：`uv run --project <套件根>/tools/decision_projection decision-project --book <你的書> [--target 設定/角色/<名>/]`——它**一次吐兩節**（裁決＋待裁決，兩軸共用 `標的` 選擇器），所以消化前查一次就同時看到「還沒裁決的」與「已經裁決過的」。
>
> **落檔前跑 `decision-lint --book <你的書>`**：恰四欄、日期格式、標的存在性、`發現` 欄長度。
