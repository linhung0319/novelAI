# novelAI — AI 輔助小說寫作系統套件

這個 repo **本身就是「寫作系統套件」**，不是某一本書。它承載「每次寫作都需要、且跨所有書不變」的方法與工具；小說內容（每本都不同）則放在各自的書資料夾裡，兩者嚴格分離。

> **第一性原則在 `結構定義/設計原則.md`**（六問＋原則 A–G）：這套系統「檔案該怎麼分、誰能寫什麼、什麼時候該拆」的推導規則。每一條都對應一個實測過的失效模式，證據寫在各條的「為什麼」。
> **2026-07-27 ～ 07-29 跑完一輪全系統重構**（15 個功能軸，逐輪診斷與拍板見 `docs/重構/`）：把每個產物軸的格式承諾都接上守衛，並廢除了六支「關於全部東西」的綜合檔（五支 rollup 索引＋就緒儀表＋結構對應表）改成投影。
>
> 早期設計依據：`docs/superpowers/specs/2026-07-10-novel-structure-pipeline-design.md`（子專案 A：`raw/` → 結構化 `story/`，終點＝幕綱通過測試）、`docs/superpowers/specs/2026-07-11-subproject-b-write-skill-design.md`（子專案 B：依幕綱動筆）。**兩者的射程都已被上面那輪重構覆寫，讀它們之前先讀 `設計原則.md`。**

## 三個組成部分

| 部分 | 資料夾 | 角色 |
|------|--------|------|
| **結構定義** | `結構定義/` | 「符合結構的產出」到底長怎樣。**12 支 schema**（摘要／世界觀／角色／風格／大綱／幕綱／章節／物件／事實流／裁決流／待裁決／就緒）＋兩支跨軸權威：`設計原則.md`（第一性原則，管「怎麼推導」）與 `共同約定.md`（所有 skill 共用的操作約定，管「推導出來的結果長怎樣」）。設定層（世界觀／角色／風格）與摘要、章節採**源→衍生兩檔**（人寫 `<實體>.md`＝唯一真實來源，AI 重生 `<實體>.ai.md`＝機讀分析；變動偵測 `tools/derived_sync`） |
| **技巧知識庫** | `技巧知識庫/` | 整合後的寫作「方法」，扁平並列（技法與 skill 是多對多，資料夾會強迫單一歸屬）。**唯一入口是 `技巧知識庫/_index.md`**：查哪一支用它的「何時查它」欄。<br>**這裡刻意不列檔名**——列舉一份會隨技法輪次成長的清單，下場是漏列而沒有人發現（`CLAUDE.md` 上實測漏 8/27 支）。哪一支被哪幾支 skill 引用跑 `meta-lint --emit kb` |
| **Skills** | `.claude/skills/` | 「操作」，**12 支**。垂直推進：`develop`（粗階段冷啟動）→ `organize`（整理大綱，全書或局部 arc）→ `outline-test` → `beat-sheet`（幕綱共創）→ `beat-test` → `write`（依幕綱撰寫正文）→ `write-test` → `revise`（依報告定點修訂）。橫向補厚：`expand`（劇情層，把單薄的 arc 就地長厚）、`worldbuild`（設定層，補厚世界觀並消矛盾）、`character`（獨立設計單一角色）。跨層診斷：`sync`（上游改動找過期下游、回頭收斂前盤點已承諾事實） |

分工：**技巧知識庫承載「方法」，skill 承載「操作」**——skill 執行時載入知識庫與結構定義來工作。

### 第四個部分：守衛（`tools/` 生產、`devtools/` 開發期）

「沒有檢查器的保證只是口頭承諾」是這套系統用痛學過很多次的一件事，所以**每一條 schema 宣稱的格式都要指名一個檢查器與一個觸發時機**（`設計原則.md` E1）。

- **`tools/` 7 個 Python 套件／21 個指令 ＝ 生產包**（全部吃 `--book`），另 `devtools/` 1 個套件／1 個指令是開發期的（`meta-lint`，見 `devtools/README.md`）。一律唯讀、零 LLM、可覆算：**12 支格式閘門**（`beat-lint`／`ch-lint`／`outline-lint`／`char-lint`／`world-lint`／`style-lint`／`summary-lint`／`readiness-lint`／`fact-lint`／`object-lint`／`decision-lint`＋`derived-sync validate`）＋投影查詢（`fact-project`／`decision-project`／`foreshadow-project`／`structure-project`／`readiness`／`settings-select`…）。
- **每一支都先印「我在這本書上檢查了幾筆」，0 也印**——只回答「發現幾個問題」的檢查器，在它自己被關掉時會印「乾淨」。
- **守衛自己由 `meta-lint` 與 `.github/workflows/tools.yml` 守**：`meta-lint` 是唯一一支不吃 `--book` 的指令（它的「書」是 repo），驗指令 ↔ 觸發者雙向、schema 指名的守衛存在、平行清單一致、輸出與 exit 契約、**生產包封閉性**等 13 項。
- **生產包 ＝ 系統層 7 項，唯一的排除是 `tools/*/tests/`**（黃金檔釘病例書、語料回歸釘 `examples/`，都是開發期資產）。`tools.yml` 步驟 ⑤ 把生產包導出到一棵**沒有任何開發期檔案**的樹並跑 21/21——**那是「系統層真的與開發期分開」的機械證明，不是宣稱**。

> 清單不落檔（那會是第 N 份會漂移的複本）——跑 `uv run --project devtools/meta_lint meta-lint --emit guards`。

### 為什麼 skill 放在「專案層」`.claude/skills/`

只有在 `novelAI/` 這個目錄工作時，這三個寫作 skill 才會被 Claude Code 載入，因此**天生與你平常寫程式用的其他 skill／plugin 隔離**，不會互相污染。日後若要跨目錄使用，可再升級成獨立 plugin。

## 開新書怎麼做

1. 複製 `書本模板/` 到 repo 根目錄，改名為你的書名（例：`奇幻冒險/`）。
   > 書資料夾與系統套件一起在本 repo 版控（見下方第 7 點）。
2. 把你手上的瑣碎筆記、靈感、半成品（任意格式）丟進 `你的書/raw/`。
3. 若 raw 還很亂、主線/題旨/結局未定，先對 Claude 說「幫我把 raw/ 想清楚」（觸發 `develop`）收斂大方向；若大方向已大致就緒，直接說：**「幫我把 raw/ 整理成符合結構的大綱和幕綱」**（觸發 `organize`，產出全書 `story/01-大綱.md`）。若只有**某一段**已想清楚、全書結局還沒定，可以說「先幫我把『這一段』整理成大綱」——`organize` 會改產出局部的 `story/大綱/arcNN.md`，不必替尚未收斂的全書結局搶先拍板；待全書收斂後再回來走一次全書模式。
4. 大綱/摘要大致定稿後，可用 `outline-test` 審大綱；再反覆用 `beat-sheet` 共創幕綱、用 `beat-test` 審稿，直到幕綱通過測試。
   > **某一段劇情太單薄**（只有一個橋段、缺衝突）→ `expand` 就地長厚；**設定累積了矛盾、或某個維度要深做** → `worldbuild`；**要獨立設計一個新反派／配角** → `character`。這三支是**橫向**能力：不往下一層走，而是把同一層某個產物補厚＋自洽。
5. 幕綱就緒後，說「幫我把這幾幕/這一章寫成正文」（觸發 `write`）——AI 會先提議分章方案供你拍板，再依幕綱展開成 `chapters/` 下的散文草稿。寫完用 `write-test` 審稿，要把可疑點修掉用 `revise`。
6. **迭代**：回頭改了上游（結局拍板、題旨修改、世界觀規則變更、幕綱在成章後又改）之後，說「哪些下游過期了」（觸發 `sync`）列出待重驗清單；要回頭收斂粗層（結局、配角、中後段）之前，也可先用 `sync` 反向盤點已下沉段落「已承諾的事實」。
7. **書的版本歷史**：書資料夾與系統套件**一起在本 repo 版控**（刻意設計——迭代型創作經常回頭改，小說內容需要版本歷史）。開新書後記得把書資料夾 commit 進來即可，不需另外設定。

每本書資料夾結構：

```
你的書/
├── raw/        # 你丟進來的任意格式素材（唯一一個「預設不讀」的輸入，見下）
├── story/      # 整理後符合結構的產出
│   ├── 00-摘要.{md,ai.md}     # 主線／題旨／基調／視角／取向定位
│   ├── 01-大綱.md、大綱/arcNN.md
│   ├── 設定/{世界觀,角色,風格}/ # 一實體一檔：源 <實體>.md（你寫）＋衍生 <實體>.ai.md（AI 重生）
│   ├── 幕綱/arcNN.md、_順序.md  # _順序.md ＝ arc 的故事先後（源，沒有任何檔算得出來）
│   ├── 物件/<名>.md            # 具名且會變狀態的東西：約束、揭示層級、為什麼存在
│   └── 參照/{裁決流,待裁決,就緒}.md
└── chapters/   # 依幕綱寫的章節草稿（由 write 產生；正文 chNNNN.md＋衍生 chNNNN.ai.md）
```

> **沒有索引檔是刻意的**：章序、角色清單、arc 清單、世界觀主題清單全部是**投影**（`ch-lint --emit`／`char-lint --emit`／`outline-lint --emit`／`world-lint --emit`），不落檔。理由：索引是「關於全部東西」的檔，所以任何找不到家的內容都會落在它身上，而它的 hash 守的是源檔集合、不是它自己的內容——**於是沒有任何東西會反對**。

> **`raw/` 是唯一一個「預設不讀」的輸入**：它沒有 schema、沒有 lint，**而那是正解不是欠債**（零摩擦是這個資料夾唯一的功能——半夜想到一句話要能直接貼進去）。整批讀是 `develop` 冷啟動分揀的特權；其餘任何 skill 走**兩段式**：先列檔名＋大小清單，有明確觸發條件或你點頭，才讀被挑中的那幾支。**選擇器是人，不是工具。**
> 反過來也成立：**任何一輪討論裡你都可以請 AI 把「暫時用不到但不錯」的東西寫進 `raw/`**，不限 `develop`。

## 核心約束（設計原則）

- **嚴格分離**：系統/技巧（不變、跨書）與小說內容（每本不同）分開。skill 不依賴任何一本書的絕對路徑。
- **副檔名只扛一個位元**：`.md` ＝你的手改就是新的真相；`.ai.md` ＝下次重生即覆蓋。**第二個位元「有沒有人逐欄取值」由「有沒有 lint」承擔，不由副檔名承擔**——而**取值者是程式或 LLM 都算**（LLM 讀壞格式會安靜地讀錯，比當場炸更糟）。
- **幕綱是結構化 Markdown**：每幕一 section＋固定八欄；用 `[[幕NNN]]` 指前因、`埋[[伏筆:x]]`／`收[[伏筆:x]]` 標伏筆。**伏筆 registry ＝幕綱標記 ∪ 物件檔**，`beat-lint`／`char-lint`／`world-lint` 驗每個引用都命中它。
- **局部下沉是一等公民，不是變通**：大方向不平均沒關係——已清楚的一小段（arc）可以先在大綱層（`story/大綱/arcNN.md`）與/或幕綱層（`story/幕綱/arcNN.md`）下沉做細，其餘留粗；下沉品一律標「暫定，待粗層鎖定」。
- **測試 skill 是「審稿員」不是門檻**：`outline-test`／`beat-test`／`write-test` 輸出可疑點報告交作者判斷，不做自動 pass/fail。**格式閘門才做 pass/fail**，兩者分開跑、分開計。
- **AI＝共創＋審稿**，所有創作決定權在作者。
- **確定性的工作一律進程式，LLM 只做判斷**：掃標記、配對、計數、選檔、算 as-of、統計——**加投影，不要在 SKILL.md 裡寫「請只讀相關部分」這種規勸**（規勸不會被執行，工具會）。
