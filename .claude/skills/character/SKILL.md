# character — 按需獨立設計單一角色

系統其他 skill 只在別的動作裡「順帶」產角色：`develop` 在粗階段冷啟動時**打包**配角、`expand` 在偵測到某段劇情缺衝突時**副產**一個對手。本 skill 補上缺的一級操作：**任何時候，作者就是想獨立設計一個角色**（新反派、新配角、或替既有角色補上需求弧線），不必為此跑整套 develop 或硬造一個劇情缺口。

定位是「中間檔位」的輕量操作——單一產物、單點寫入，不套用大 skill 的全套儀式。

**AI 角色 = 共創 + 審稿**：你依方法提角色草稿以降低白紙恐懼，但**所有創作決定權在作者**——採不採某個角色、四象限怎麼填、要不要進正史，一律作者拍板。你只提案，不代決。

## 共同約定（必讀）

資源定位、**兩類檔案公理**、AI 角色（共創＋審稿、非門檻）、**源→衍生兩檔＋下游回饋**規則見 `結構定義/共同約定.md`（零、二、三、四）。**源→衍生落地**：作者拍板的角色寫進**源**（單檔 `story/設定/角色/<名>.md` 或目錄 `story/設定/角色/<名>/<切面>.md`，皆自由手寫），再依 schema 重生 `<名>.ai.md`，`cd tools/derived_sync && uv run derived-sync stamp <名>.ai.md` 封章（別手算 hash）。**沒有 rollup 要重生**（`_index.ai.md` 2026-07-28 功能 12 廢除，全書角色清單跑 `char-lint --emit`）。

**本 skill 最容易犯的四個錯（皆由第零節公理直接推出，`char-lint` 與成長哨兵會報）**：
1. **不要把共創問答紀錄寫進源檔。** 那一輪逐題拍板的 Q&A（Q1…Q9、未用備案、本輪拍板記錄）是 AI 產物，屬 `story/參照/裁決流.md`；源檔只留**結論**。實測某角色源檔逐題問答佔 35.9%、加上帶日期的拍板紀錄節共 **61.2%**，把一支必須整檔讀的檔撐到 32 KB 而觸頂——**而它觸頂的原因不是角色太厚，是寄居內容**（成長哨兵的 hint 現在會先叫你檢查這件事，見步驟 5「先搬後拆」）。
2. **不要在 `<名>.ai.md` 開 schema 沒有的節。** 「硬事實」「下游硬約束」「反派備註」寫的是正文釘死的事實與負向排除線——那屬 事實軸——`錨` 屬該章 `chNNNN.ai.md` 的 `## 本章事實`、`約束` 屬 `story/物件/<實體>.md` 的「## 不得寫成什麼」。衍生檔的節是封閉枚舉。
3. **不要在 `<名>.ai.md` 檔末寫 blockquote 裁決日誌。** 理由寫多長都行，寫在 `裁決流.md`。
4. **不要留佔位、也不要為了讓工具看得見而建空殼檔。** `需求四象限`／`預期弧線` 是必填且**不得只寫「（源檔未載，待跑 character 補）」**——`beat-test` 測試4 拿那兩節當角色弧線的基準，拿到佔位字串時它不會知道，而 `check`／`validate`／`settings-select` 三支都會回報正常。源檔還沒東西可分析就**先不生成那支 `.ai.md`**：2026-07-27 起 `char-lint` 第 2 項從**源側**掃「源有衍生無」，缺檔會被報出來，不必再用空殼檔去餵掃描器。

## 依據

- `結構定義/角色.schema.md`——本 skill 的**源→衍生格式**：源**一律單檔起步**（`<名>.md`，自由手寫），因**大**（哨兵報 `源檔肥大`）或因**有秘密**（要開 `水下.md`）才升目錄形態 `<名>/{核心,來歷,能力,關係,水下}.md`——五切面是封閉枚舉、**不必全建**，且 `<名>.md` 與 `<名>/` **不得並存**；衍生 `<名>.ai.md` 為需求四象限（期盼／想要／落差／需要）＋預期弧線＋馬斯洛層次＋對衝關係（反派可給「正當需求」），**節是封閉枚舉**（2026-07-27 起**不再有**「## 待裁決回饋」節）、**必填兩節不得是佔位**，front-matter **只有六鍵**（`generated-*`／`定位`／`所屬arc`／`暫定`／`伏筆`——`角色`／`弧線類型`／`影響力` 2026-07-27 依 A4 刪除，零解析器零消費者）；**無 rollup**（`_index.ai.md` 2026-07-28 功能 12 廢除，全書角色清單跑 `char-lint --emit`，它從資料夾與各檔 front-matter 當場重算）。
- `結構定義/事實流.schema.md`——正文已釘死的事實（`錨`）與下游硬約束（`約束`）的落點，**不是角色衍生檔**。
- `結構定義/裁決流.schema.md`——「為什麼這樣定」的落點；消化前用 `decision-project --target <該角色源路徑> --active-only` 查這個角色過去已經裁決過什麼。
- `技巧知識庫/需求四象限.md`——設計需求弧線與兩難的核心方法：期盼＝動力／想要＝誤導／落差＝阻礙／需要＝圓滿，選正／平／負弧線型，「需要」須拖到最後才滿足，「反派也有正當需求」。
- `技巧知識庫/角色塑造.md`——把角色設計得立體可信：三面向、三層行為反差、由外而內三階段、塑造六法（供描述角色時避免只給扁平標籤）。
- `技巧知識庫/世界觀與背景.md` ＋ `story/設定/世界觀/*.ai.md`（主題清單跑 `world-lint --book <書> --emit`）——判斷角色的出身／能力／動機是否違反世界觀核心規則、是否自洽。
- `技巧知識庫/網文與文學取捨.md`——依衍生 `00-摘要.ai.md` 的 `取向定位` 欄拿捏：偏網文則角色可帶更強的爽點功能（金手指持有者、打臉對象…），偏文學則倚重需求弧線與內在矛盾的縱深。

## 流程

### Phase 1 — 提案（唯讀，不改任何檔）

1. **確認書與需求**：作者未指明哪本書、或要設計什麼樣的角色（定位／功能／與誰對立）時先確認（見 `共同約定.md` 一）。
2. **載入方法與格式**：讀上列「依據」的 `技巧知識庫/*.md`（先讀各檔檔頭「目錄」標**核心**的小節；附錄按需再讀）與 `結構定義/角色.schema.md`。
3. **讀 context**：
   - **摘要軸兩支都讀**——衍生 `story/00-摘要.ai.md`（`主線`／`題旨`／`基調`／`取向定位` 等**六個語意欄**＋取向定位分析，**權威在這裡**）＋源 `story/00-摘要.md`（承重決定的散文與理由，整檔讀）；角色需服務主線、其弧線需能呼應題旨。
   - `story/設定/世界觀/*.ai.md`——核心規則（角色的能力／出身／動機不得違反）。
   - `story/設定/角色/`（若已有角色）——既有各源／`<名>.ai.md`（全書清單跑 `char-lint --emit`），避免重複、並讓新角色的需求與既定角色（尤其主角）**形成衝突**。
   - **既有裁決**：對要深化的角色跑 `uv run --project <套件根>/tools/decision_projection decision-project --book <書資料夾> --target 設定/角色/<名>/ --active-only --as-of <目前寫到的 arc>`——看這個角色過去已經拍板過什麼（`--as-of` 讓程式依射程欄自動濾掉過期的），避免重新爭論已定案的事、或提出與既有裁決牴觸的方案。
   - **正文已釘死的**：跑 `fact-project --for-beat <該角色登場的幕> --kinds 錨,約束`（或 `--as-of` ＋ `--entities <名>`）——這些不能靠改設定推翻（要改得改正文）。
   - **先掃既有角色（含 `develop` 打包時只寫一行正當需求的配角源檔）**：若作者要設計的角色**已有源 `<名>.md`**（不論內容多寡）→ 本次是「**替既有角色補上需求弧線**」（見 description）＝**就地深化該既有的 `<名>.md` 源檔再重生**，**不另建一個重複的 `<別名>.md`**；確認 `角色/` 下查無此角色檔，才是全新角色。
   - **前置檢查**：若連 `00-摘要.md` 主線／題旨或 `story/設定/世界觀/`（無任何源 `<主題>.md`）都不存在 → 判定粗階段未就緒，**停下**建議先跑 `develop`，不要在真空中設計角色。
4. **提 1–N 個角色草稿**：每個草稿給
   - 一句話定位（在故事裡幹什麼、與誰對立）；
   - 需求四象限（期盼／想要／落差／需要；反派同樣給「正當需求」，與主角需求同樣正當會讓矛盾更強）；
   - **若這個角色的真動機是後段才向讀者揭示的**（真凶、臥底、偽裝成敵人的守護者）：四象限**照樣填角色的真實**（否則 `beat-test` 的弧線檢查失去意義），**不在 `.ai.md` 裡分【表面】/【水下】兩層**（那個寫法 2026-07-27 刪除——它是作者拍板何時揭、不可重生，住在會被重生的檔裡下次重生就沒了）。「讀者現在還不能知道」記在 `story/物件/<名>.md` 的 `揭示層級` 欄（`水下｜揭示於 收[[伏筆:x]]` 或 `水下｜跨集留白`，見 `物件.schema.md`）。揭示點取自幕綱既有的 `收[[伏筆:x]]`；查不到就標「揭示點待落幕」，別自己造一個伏筆名。
   - 預期弧線（盲目→挫折→醒悟→滿足，或平／負弧線）＋馬斯洛層次；
   - 與世界觀自洽的檢查結果、與既有角色的衝突關係；
   - 選填：一條足以立體化的「三層行為反差」或塑造六法示例。
   - 承重處（要不要進正史、選哪個版本）明確標「待你拍板」。**到此為止，不寫任何檔。**

### Phase 2 — 拍板後寫入（作者選定後才執行）

5. **寫源 `設定/角色/<名>.md` → 重生衍生 → stamp**（依 `角色.schema.md`）：
   - **改的是源**：依作者選定，把角色寫進**源**（自由手寫，好讀好改）。**一律單檔 `<名>.md` 起步**——「定位＝主角／反派」只是**建議**先分好切面，不是預設形態（實測舊 schema 那條「主角／反派預設目錄形態」**0/24 次生效**）。再依 schema 重生 `<名>.ai.md`（四象限＋預期弧線＋馬斯洛＋對衝關係＋選填兩難；front-matter 六鍵，`暫定: true` 沿用舊「⚠️ 暫定」語意）；`cd tools/derived_sync && uv run derived-sync stamp <名>.ai.md` 封章。**沒有 rollup 要重生**（見下）。
   - **必填兩節不得是佔位**：`需求四象限`／`預期弧線` 要真的填。源檔太薄、這一輪還分析不出來 → **就先不生成那支 `.ai.md`**（`char-lint` 第 2 項會從源側報「源有衍生無」，那是正確的訊號）；**不要生一支四節都是「（源檔未載…）」的空殼檔**。
   - **升級形態的兩個獨立觸發者**（別把它們綁在一起）：
     - **因為大** → 成長哨兵報 `源檔肥大`（25,000 B）時。**但先搬後拆**：先照哨兵 hint 檢查有沒有寄居內容（共創問答／拍板紀錄 → `裁決流.md`；正文釘死的事實 → 章 delta；硬約束 → 物件檔），搬完再量一次——實測那支觸頂的角色源檔 61.2% 是寄居內容，搬走就低於門檻、根本不必拆。
     - **因為有秘密** → 要開 `水下.md` 時，**與角色大小無關**（一個 800 B 的配角也可以有秘密）。
     - 升級是**搬移不是重寫**：`git mv <名>.md <名>/核心.md` 保住歷史，再把段落分派到需要的切面。**五切面不必全建**，最小的目錄形態就是 `核心.md`＋`水下.md`。**`<名>.md` 與 `<名>/` 不得並存**（並存會讓 `settings-select` 產生兩個同名 Entity，目錄形態的切面從此選不到；`char-lint` 第 7 項會報）。
   - **順手清掉既有的枚舉外節**（本輪動到的那個角色）：`<名>.ai.md` 若還帶 `## 硬事實`／`## 下游硬約束`／`## 反派備註`／`## 源檔既載要點`／`## 🧊 水下`／`## 待裁決回饋` 或檔末裁決 blockquote，**在這一輪重生時一併分派掉**（錨→章 delta、約束與揭示層級→`story/物件/<名>.md`、回饋→`story/參照/待裁決.md`、理由→`裁決流.md`），不要原樣抄進新版。**重生會吃掉它們而不留痕跡**——那些節裡有明說「不可翻案」「守死」的東西。
   - **不必重生任何 rollup**（2026-07-28 功能 12 抉擇 1 A：`_index.ai.md` 廢除）——全書角色清單跑 `char-lint --book <書> --emit`，它從資料夾與各檔 front-matter 當場重算。**檔名就是 ID**：新角色的檔名不得帶括號別名（`真慧（方阿七）` ✗、`真慧` ✓），別名屬該角色源檔的散文或 `story/物件/<名>.md`。**源檔 H1 底下要有一句「這個角色是什麼」**——投影的 `一句話` 欄讀它，`char-lint` 第 9 項守。
   - **就地深化（不建重複檔）**：對象角色已有源 `<名>.md`（哪怕只有一行正當需求）時，**改寫同一個 `<名>.md`**、重生其 `.ai.md`——一角一檔，天然不會產生平行殘影（不必再手動劃除 stub）。**不得**為同一角色另建 `<別名>.md`。其他作者已寫定的角色源檔不動。
   - **後段 reveal 型角色**：`<名>.ai.md` 的象限寫角色真實、**不分層**；改開（或補）一支 `story/物件/<名>.md`，front-matter 寫 `揭示層級: 水下｜揭示於 收[[伏筆:x]]`，並在「## 為什麼存在」寫下作者拍板的分界理由。**不另加自創的洩題警告區塊**——`揭示層級` 就是給下游的訊號，`物件.schema.md` 已定義它的意思。落檔後跑 `object-lint --book <書>` 驗（它會核對那個收點在幕綱找不找得到）。
   - 若角色設計**引入新的世界觀設定**（新種族／新能力來源／新組織）→ 依 `共同約定.md` 四，在 `story/參照/待裁決.md` 追加一列（`標的` 欄寫 `設定/世界觀/<主題>.md`；不改世界觀源、不改其分析區），交付時提示「已記錄 N 筆待裁決」，交 `worldbuild` 消化。
6. **落裁決流＋清回饋列**（結案的東西要離開待辦區，見 `待裁決.schema.md`「結案怎麼離開」）：本輪作者拍板的每一項，在 `story/參照/裁決流.md` append 一列（`日期｜來源＝character（本輪主題）｜標的＝該源檔路徑｜裁決＝一句話（≤200 字）｜理由＝為什麼（不限長）｜射程｜狀態＝生效中`）。**這本書沒有那支檔就照 `書本模板/story/參照/裁決流.md` 的骨架先建一支**——目的地不在時 `derived-sync check` 會報，而理由會改落 `.ai.md` 的 blockquote（實測那是 46,245 字元的來源）。若本輪消化了 `story/參照/待裁決.md` 裡標的為本角色的列——結論已落源檔或事實軸、理由已落裁決流之後，**把那幾列刪掉**。落檔後跑 `decision-lint --book <書>`。
   - **本次動到的源檔若已有舊的問答節，一併搬**（不只搬本輪的）：`<名>.md` 裡的 `## Q1 · …`…`## Q9 · …`、`## 未用備案`、帶日期的 `## 本輪拍板紀錄`／`## tell 預算表（arcNN·作者拍板）` 這類節，**在這一輪一併 append 進 `裁決流.md`、從源檔刪掉，源檔只留結論**。**這是本輪唯一會清理既有累積的觸發點**——不設這個觸發者的話，那些內容只會一輪一輪繼續長（實測某支源檔已達 61.2%，而 `oversized_sources` 只會說「這支檔太大」，不會說「它之所以太大是因為 61.2% 不屬於它」）。**不動本輪沒碰到的角色**。
   - **一項裁決一列**，不要把整輪決定併成一列長文（那會讓 `--target` 過濾失效）。
   - 若本輪產生了「下游不得寫成 X」的硬約束，**在 `story/物件/<該角色名>.md` 的「## 不得寫成什麼」新增一列**（4 欄 `約束名｜不得寫成｜生效自｜解除於`——「實體」不是欄位，它就是這支物件檔的檔名；見 `物件.schema.md`）。**那支物件檔還不存在就順手開一支**（front-matter 至少要有 `型別: 角色`，並在「## 為什麼存在」寫下作者拍板的理由）。**不是**寫進 `<名>.ai.md`、也**不是**寫進章 delta（那會被重生吃掉）。`生效自` 多半寫 `全書`（角色層的排除線通常是全程的，且這樣才能回溯管住已寫的段落）；**那個 arc 還沒拆幕也照寫**，投影會當成「尚未抵達」印一行資訊、不報錯。日後要延長或解除射程＝**改那一列的欄位**，不是再加一列（**改之前先跑 `fact-refs --constraint <約束名>`**：約束不會自癒，射程內已經寫成的正文得自己去看）。落檔後跑 `object-lint --book <書>` 驗格式。

7. **跑閘門**：`cd tools/derived_sync && uv run char-lint --book <書>`（＋`uv run derived-sync validate --book <書>`）。它會驗這一輪落檔的東西：必填節不是佔位、front-matter 六鍵的語意、形態沒有並存、伏筆名命中 registry、源檔 H1 底下有非空行。（第 ⑤⑥ 項是**舊 `_index.ai.md` 的殘留偵測**——那支檔 2026-07-28 已廢除，缺檔不是問題。）**覆蓋率行一律印、0 也印**——特別看「N 支源沒有衍生檔」與「M 個 slot 是佔位」這兩格。既有書的舊問題會一起被報（病例書不遷移），**本輪動到的那個角色不該出現在裡面**。

8. **更新就緒源檔＋指路**：更新 `story/參照/就緒.md`「設定層·角色」列的成熟度（**只准 `空白`／`草擬`／`就緒`／`已鎖定`／`—` 五個 token 之一**；理由 append 進 `story/參照/裁決流.md`），落檔後跑 `uv run --project <套件根>/tools/derived_sync readiness-lint --book <書>`；以「已追加、仍暫定」姿態呈現，提醒後續拆幕（`beat-sheet`）或寫正文（`write`）時此角色即可被引用。

## 邊界

- **與 `develop` 分工**：develop 是粗階段冷啟動、一次打包世界觀＋主線＋一組配角；character 是粗階段之後任何時候、針對**單一**角色的定點設計。粗層未就緒就退回 develop。
- **與 `expand` 分工**：expand 因某段劇情缺衝突而**副產**角色（角色是劇情缺口的解法）；character 是**主動獨立**設計角色（角色本身就是目的）。若作者其實是要補某段劇情，導去 expand。
- **不拆幕**（交 `beat-sheet`）、**不寫正文**（交 `write`）、**不做世界觀補厚／消矛盾**（交 `worldbuild`）。
- **不自動 pass/fail**：草稿是提案，承重抉擇（採哪個角色、進不進正史、四象限定稿）一律作者拍板；產出皆為可編輯、非受保護的草稿。
