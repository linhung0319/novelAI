# 設定層「事實／裁決」分軸 — 設計書

- 日期：2026-07-26
- 狀態：**已核准，待落地**（作者 2026-07-26 拍板三項抉擇：分兩檔／依定位分目錄／五切面）
- 範圍：設定層源檔與衍生檔的無界成長；正文既成事實與裁決紀錄的落點；`狀態事件流` 的推廣。
- 交付邊界：系統套件（`結構定義/`、`.claude/skills/`、`tools/`）。`一世之尊` 只跑量測與相容性報告，**不動任何書內檔**。

## 一、觸發問題與量化診斷

作者觀察：`一世之尊/story/設定/角色/` 有些檔案非常大，懷疑是「該由 `狀態事件流` 管的東西被存進了 `角色/`」。

**該懷疑經查為否**——邊界守住了。`write` 步驟 8（`.claude/skills/write/SKILL.md:113`）只 append 進 `狀態事件流.md`，它唯一寫進 `角色/*.ai.md` 的動作是追加「待裁決回饋」列；抽驗孟奇的私帳、年齡、報名「真定」也確實都在 `狀態事件流.md`（幕501／幕507／幕509）。

實際成因是另外四條：

| # | 成因 | 證據 |
|---|------|------|
| D1 | **正文既成事實沒有落點** | `孟奇.ai.md`「硬事實」1966 字、`血刀頭陀.ai.md`「反派備註」5118 字、`真慧.ai.md`「下游硬約束」——三個 `角色.schema.md` 都沒定義的自創節 |
| D2 | **裁決紀錄沒有家、也沒有回收** | 各 `.ai.md`「待裁決回饋」**表格是空的**，量全在表後的自由 blockquote：孟奇 2092 字／真慧 2095 字／血刀頭陀 3274 字 |
| D3 | **共創問答逐題紀錄寫進源檔** | `血刀頭陀.md` 43% 是 `character` 那輪的 Q1–Q9 對話 log（編號跳號，Q6/Q7 不在檔裡） |
| D4 | **哨兵看不到衍生檔** | `tools/derived_sync/src/derived_sync/sentinel.py:72` 明確 `continue` 掉 `.ai.md` 與 `_*`；`long_lines` 只掃 `story/參照/` |

量化基線（2026-07-26，`一世之尊/story/設定/角色/`，49 檔）：

- 源 136 KB／**衍生 219 KB**——衍生層已大於它所衍生的源；24 對衍生/源有 **21 對是衍生較大**。世界觀層同病：源 78 KB／衍生 129 KB。
- 單調成長、從未縮過：`真慧.ai.md` 1.4 KB（7/20）→ 13.2 KB（7/25）；`孟奇.ai.md` 3.2 → 17.6 KB；`_index.ai.md` 0.9 → 35 KB。
- `孟奇.ai.md` 真正落在 schema 內的節（四象限／弧線／馬斯洛／對衝）只佔 **16%**。
- `_index.ai.md` 52% 是 schema 完全沒有的「乙批·`character` 觸發條件表」（8085 字）；schema 說 rollup 是「一行需求」，實際每列 800+ 字。

## 二、根因

`診斷01` 的 **R9「治理文字擠掉創作預算」**（2026-07-26 標記已修）處理的是幕綱：三分成承諾區／八欄／檔尾設計註，設計註三條回收判準，成長哨兵計量。**設定層得的是同一個病，一項都沒套用。**

但套用 R9 的修法並不是正解。依作者 2026-07-26 拍板的分類公理：

> **書內檔分兩類。**
> **人類可讀可寫**（源）——人寫的容易有格式問題，AI 大多情況**必須整檔讀入**，所以**只有這一類需要限制檔案大小**；控制手段是 `結構定義/` 的資料夾與檔案結構，讓作者被結構引導分檔，AI 也能由目錄與檔名判斷此刻該讀哪幾支。
> **只由AI與程式產生**（衍生／log）——格式固定，**檔案再大都沒關係**，因為程式能在 AI 需要時只抽出需要的那一部分放進 context。

用這條公理看，根因是一個**從未成立的前提**：

`.ai.md` 被歸類為「AI管·衍生·嚴格 schema」（`結構定義/共同約定.md:20`），於是被默許成長。但**全系統沒有任何工具能切 `.ai.md` 的段**——`tools/settings_select/src/settings_select/select.py:26` 的 `read_path` 回傳的是整個檔，`settings-select` 的粒度是「哪幾支檔」而非「檔裡哪一段」。於是衍生檔同時具備「會隨劇情無限長大」與「必須整檔讀入」，是兩類裡最壞的組合：**它拿了第二類的免死金牌，卻活在第一類的讀取方式裡。**

對照組印證了這個判讀：全系統唯一沒人喊痛的成長型檔是 `狀態事件流.md`——固定 4 欄信封 ＋ `state-project --as-of` 可切片，所以它一路長到 200+ 行也不構成負擔。

> **推論（本設計最重要的一句）**：`狀態事件流` **設計是對的，只是被侷限在「6 維狀態」這一種事實上**。其他同樣由 AI 產生、同樣隨劇情累加的事實——正文釘死的錨、負向硬約束、裁決理由——沒有對應的軸，只好倒灌進源檔與分析區。缺的不是「回收機制」，是**軸**。

### 「裁決理由」屬哪一類？

屬**只由AI與程式產生**。判準：它從來不是作者手寫的——每一段都是某輪 skill 執行完自己寫下的（`真慧.ai.md:70`「2026-07-25（`character` 補厚·真慧＋玄悲同輪）」）；作者在對話裡拍板，落檔的是 AI。且其欄位天然固定：日期／來源 skill／標的／裁決／理由／射程／狀態。

由此得出對既有機制的修正：

> **「回收／壓縮」是補丁。** 設計理由之所以只能靠人工刪，是因為它被寫進了自由 prose 的檔（源檔、`.ai.md` 本體、幕綱檔尾）——那裡沒有第二條路。照公理它根本不該住在那裡。移進格式固定、程式可切片的軸之後，它**永遠不必刪**，過期的自然不會進 context。

## 三、設計

### 3.0 公理入法（`共同約定.md` 新增「零、兩類檔案」）

兩類的定義如上。並補一條**資格條款**，堵住本次的根因：

> 衍生檔要享有「可以很大」的豁免，**必須有對應的投影／切片工具**。沒有工具能切它，它就跟源檔同等受限——大小照源檔的門檻管。

### 3.1 動作一：`狀態事件流` 升格為 `事實流`

`story/參照/事實流.md`。**沿用現行 4 欄信封與 fold 模型**，第三欄由「6 維枚舉」擴成三類 token：

```
- 幕508（arc06）· 孟奇 · 知識前沿：…                        ← 狀態（6 維枚舉，不變）
- 幕508（arc06）· 孟奇 · 錨〔年齡〕：十五（入寺兩年餘）←ch0046
- 幕904（arc10）· 真慧 · 約束〔不得成為第二證人〕：…
```

| 類型 | 記什麼 | 誰寫 | 現在流落何處 |
|---|---|---|---|
| `狀態`（6 維不變） | 逐幕 delta | `write` 章末 | ✅ 已在正確位置 |
| `錨` | 正文釘死的數字／專名／道具語彙 | `write-test` 促升 →`revise` | `孟奇.ai.md`「硬事實」、`血刀頭陀.ai.md`「相對刻度」 |
| `約束` | 負向排除線（不得寫成 X） | `write-test`／`character` | `真慧.ai.md`「下游硬約束」、`血刀頭陀.ai.md`「反派備註」 |

**slot 語意**：key ＝ `(實體, 第三欄 token)`，沿用「序最新覆蓋」。

- `錨〔年齡〕` 改版＝再發一行同名事件（孟奇的年齡錨已經歷過一次修訂，這正是需要的語意）。
- `約束` 解除＝發一行同名、內容以 `（解除）` 起頭的事件；`--active-only` 時剔除。
- **射程用「顯式解除」表達，不新增第 5 欄**——保住「固定 4 欄信封」這個賣點。

**相容性**：現行 `parse_events` 用 `rpartition("·")` 取第三欄 token（`tools/state_projection/src/state_projection/fold.py:39`），這個解析法不必改；只在維度驗證處（同檔 `:43`）加 `^(錨|約束)〔(.+)〕$` 分支。**舊檔 100% 相容，6 維行為逐字不變。**

### 3.2 動作二：`裁決流`（新軸）

`story/參照/裁決流.md`，append-only 表格：

```markdown
| 日期 | 來源skill | 標的檔 | 裁決 | 理由 | 射程 | 狀態 |
```

- **永不人工回收**：由 `decision-project` 按標的檔＋射程過濾，過期的自然不進 context。
- `.ai.md` 的「待裁決回饋」表**只留 `待裁決` 列**；結案（已採納／已駁回）即移進裁決流。
- **`.ai.md` 不得出現自由 blockquote 日誌**——這是 D2 的直接封堵。

分兩檔而非合一（作者拍板）：兩者讀者不同。事實流給 `write` 逐章投影查，裁決流只給 `character`／`worldbuild`／`sync` 消化時查；合檔會讓 `write` 每次投影都掃過一堆治理文字。

### 3.3 動作三：源檔目錄形態

```
story/設定/角色/<名>/          ← 定位＝主角／反派：預設此形態
  核心.md   他是誰／氣質／聲音        ← 幾乎每次都讀
  來歷.md   出身／深背景               ← character、揭底時才讀
  能力.md   武學／境界／隨身物         ← write 動作幕讀
  關係.md   對衝／羈絆
  水下.md   秘密／終局落點             ← 揭底前 write 不讀
story/設定/角色/<名>.md        ← 定位＝配角：維持單檔，跨門檻再升級
```

- **檔名即選擇器**，與現行「一角一檔」是同一個機制再往下一層。
- **`水下.md` 不只是分大小，是真的存取控制**——讓 `write` 在揭底前的章節拿不到揭底資訊，比 🧊 標記（同檔內的提醒）強一級。
- 依定位分而非一律目錄：路人角色（`符真真.md` 518 B）不必開五個空檔。
- **世界觀不套切面**：它的分檔機制已是「一主題一檔」，過大時的正解是**拆主題**（`江湖勢力.md` 25 KB → 拆更細的主題檔），沿用既有的檔名即選擇器。

### 3.4 哨兵改造

從量「檔多大」改成量「**必須整檔讀的東西有多大**」：

- 源檔／源目錄總和 → 硬門檻（沿用 25000 B）。
- **新增 `unsliceable_derived`**：`.ai.md` 超過門檻**且**含 schema 封閉枚舉外的節 → 報「衍生檔不可切片」。這條直接對應 3.0 的資格條款。
- `long_lines` 掃描範圍從 `參照/` 擴到含 `.ai.md`——抓 `_index.ai.md` 那種每列 800 字的 rollup。

## 四、對既有機制的影響

| 既有機制 | 影響 |
|---|---|
| `幕綱.schema.md`「設計註要回收」（R9 修法） | 設計理由移入裁決流；三條回收判準（已升為通則／已兌現／已過射程）降級為 `射程` 欄位，由程式過濾取代人工壓縮。R9 從「要有人負責刪」變成「不需要有人負責」 |
| `sync` 的「已承諾事實反向盤點」 | 從 LLM 每次重讀重算，改為 `fact-project --kinds 錨,約束` 直接查。這也解釋了 D1——「已承諾事實」一直被當成**算出來的**，但它其實是**被寫下來的** |
| `就緒儀表.md` 的 10038 字 cell | 同一個病（沿革住進狀態表格）；沿革移入裁決流，狀態格只報現況 |
| `回饋記錄.schema.md`「回饋列隨重生清空」 | 這個承諾一直沒兌現，因為結案的列無處可去。有了裁決流才真的可清 |
| `狀態事件流.schema.md` 邊界表「已承諾事實 → `sync`」 | 改為指向本檔的 `錨`／`約束` |

## 五、不做什麼

- **不改 6 維枚舉的語意**，也不放寬它——`錨`／`約束` 是**平行的類型**，不是第 7、第 8 個維度。
- **不動 `一世之尊` 任何書內檔**（作者指定：只做量測驗證）。工具須支援舊檔名 `狀態事件流.md` 的 fallback，讓病例書不必改檔仍可跑報告。
- **不新增自動鏈式觸發**：新軸的維護與查詢由既有 skill 在既有時機順手做（沿用子專案 C 的邊界）。
- **不做 `.ai.md` 的段級切片工具**（`--sections`）：本次靠「封閉節枚舉＋把日誌搬走」把 `.ai.md` 壓回小檔即可；段級切片留給日後真有需求時。
- **不替作者拍創作抉擇**：新軸只是落點，`錨`／`約束` 寫什麼仍走既有的「作者拍板」流程。
