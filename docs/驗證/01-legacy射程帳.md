### 那個例外：`decision-project --book 一世之尊` → exit 2

**它不是本輪造成的，而且 exit 2 是它該回的值。** 那本書從來沒有 `story/參照/裁決流.md`（`功能報告/04` 記過「裁決軸兩支檔 0 本書有」），所以 exit 2 ＝「**這本書還沒有這一層**」是 `共同約定.md`「輸出與 exit 契約」明訂的第三個值，而且它照印覆蓋率行（`檢查範圍：掃了 0 列裁決`）。

計畫 §六 寫「exit ∈ {0,1}」是在還不知道這一格的時候寫的。**條件的本意是「不能崩」，而 exit 2 不是崩**——所以本階段把驗收條件改寫成三件事（並做成守衛）：**不吐 traceback ＋ exit 在契約枚舉 {0,1,2} 內 ＋ 照印覆蓋率行**。§六 已同步更新。

## 二、1b 量：每一支 legacy 分支的活用戶

### 方法（可覆算）

1. 建一個裝 `coverage` 的 venv，`PYTHONPATH` 指向 8 個套件的 `src`（8 個套件皆 `dependencies = []`，純 stdlib，所以可以裝在同一個直譯器裡）。
2. 對 **4 個對象**（`書本模板`／`驗證範例`／`harry_potter`／`一世之尊`）各跑**全部 21 支吃 `--book` 的指令**，逐支 `coverage run --parallel-mode`，每本書一個 data file。
3. 另跑 8 個套件的 pytest coverage。
4. 比對：**只被 `一世之尊` 命中、三本乾淨書一行都沒走到的行** ＝ 死碼候選。

**原始輸出**：4 本書 × 21 支的 exit／stdout／stderr 存成 `runs.json`，coverage 存成 `<書>.json`＋`pytest.json`（scratchpad，不進 repo——它們是量測中間物，重跑就有）。

### 兩個量測上的坑，記下來免得下一輪重踩

- **`coverage --source` 吃逗號不吃 `os.pathsep`。** 第一次跑把 8 個路徑用 `;` 串起來，coverage 把整串當成一個模組名，印 `Module ... was never imported`、`No data was collected`——而**每一支指令的 exit code 都正常**。差一點就拿一份全空的 coverage 當證據。
- **行級 coverage 分不出 tuple 迴圈走到第幾個元素。** `SPINE_FILES = ("_順序.md", "_index.md")` 這種回退，走新落點與走舊落點命中的是**同一行**。所以 spine 那四筆的證據不是 coverage，是**工具自己的輸出**（`spine 讀自 X（舊落點·回退）`）＋**檔案存在性**——兩者都比 coverage 精確。

## 三、1c 清死碼

**共 53 支檔、+1,256／−862 行。** 每一筆刪除都是同一個形狀：**移除讀取路徑 ＋ 立墓碑 ＋ 配測試**。

> ### 這一輪的統一動作：**不讀 ≠ 不報**
>
> 計畫的硬驗收條件寫「移除一條 legacy 讀取路徑必須降級成**被回報的問題**，絕不能降級成 traceback」。實作時發現這句話有**第三個壞法**，而它比 traceback 更難查：**降級成靜默**。
>
> 拿掉回退而不補墓碑，會讓這兩句話變成同一個輸出：
>
> - 「這本書沒有 spine」 vs 「這本書的 spine 住在一個工具已經不讀的落點」
> - 「這本書還沒有事實層」 vs 「這本書 93 章的事實住在一支沒有工具讀的檔裡」
>
> 後者是作者以為那些承諾還在生效。所以**每一條移除的讀取路徑都換成一筆墓碑**，而墓碑那一格 **0 也印**（`設計原則.md` E2／A5）。
>
> 形狀不是本輪發明的——`fact_projection/sources.py` 對 `約束.co.md` 2026-07-27 就這樣做了，註解寫著「**留著它比刪掉它危險**」。本輪只是把它套到另外四筆。

### 2. 舊單檔事實流 → 刪（**代價最大的一筆**）

`一世之尊` 的 `狀態事件流.md`（110,946 B、259 筆事實行）從此不進 `fact-lint`。**那 206 個問題變成 1 個。**

**這一格最容易騙自己，所以逐條寫清楚**：

- **消失的不是問題，是量測。** 病灶（行長 52／括號 110／夾帶 44）一個字沒改，檔還在磁碟上。
- **哨兵沒有跟著關掉。** `derived-sync check` 的成長哨兵仍量它的行（`sentinel.APPEND_LOG_STEMS` 仍含 `狀態事件流`），行長那一半仍有人看。
- **換來的是一句更大聲的話**：「這支檔裡的事實**目前沒有任何工具在讀**，`fact-project`／`fact-refs` 看不到它們，而 `write` 會理直氣壯地違反」。比 206 筆「這一行太長」更接近真相——**那本書的事實層整層失聯**。
- **這是 2026-07-27 那次「0 與 229」的反面**：那次是閘門說「乾淨」而哨兵說「229」，**其中一句是假的**；這次是閘門說「我看不到它」而哨兵說「它在這裡而且很肥」，**兩句都是真的**。

**連帶移除**：`legacy`／`new` 世代欄（`fold.GEN_LEGACY`／`Event.generation`／`Event.legacy` ＋ 4 處 `if e.legacy` 守衛 ＋ `fact_lines_new`／`fact_lines_legacy` 兩欄）。舊路徑不讀之後 `legacy` **再也沒有生產者**，而**一個沒有生產者的枚舉值與一條永遠為真的 `if` 是同一件事**。事件來源仍說得出來，那是 `origin` 欄。覆蓋率行從 `259 筆事實行（新格式 0·舊格式 259）` 變成 `0 筆事實行`——**一個恆為 0 的計數欄看起來像一個還在量的指標**。

### 3. 兩個「假的 exit 2」

刪 spine 回退之後，`foreshadow-project` 對 `一世之尊` 回 exit 2 並印「**這本書還沒有這一層**」——**那是假話**，那本書有 11 支 arc 幕綱檔。同一個形狀在 `fact_projection.collect_events` 也會發生（舊事實流還在的書）。

兩處都改成：**有那一層但讀不動 → exit 1**；真的沒有那一層 → exit 2。

> **假話比錯誤訊息難查**：讀的人會以為那本書還沒開始拆幕，於是不會去看它為什麼跑不動。

**同時補上 E2**：`beat_metrics`（6 處）與 `foreshadow_project` 的 `ScanError` 路徑在此之前 **stdout 全空**，只往 stderr 吐一行。**一支印不出「我掃了幾筆」的工具，與一支被關掉的工具在 log 上長得一樣。** 現在都印覆蓋率行。`fact-refs` 的 `找不到檔案：[Errno 2] No such file or directory: '...'` 也換掉了——**「降級成被回報的問題」的意思是回報得出問題是什麼，不只是不 crash**。

### 4. 新守衛：`meta-lint` 第 6 項的**第 4 條契約**

驗收條件不能只在有人手動跑一次的時候成立。`check_output_contract` 新增病例書那一輪：**21 支指令 × `一世之尊`，驗不吐 traceback ＋ exit 在 {0,1,2} 內 ＋ 照印覆蓋率行**（刻意**不驗 exit 等於幾**——那由 17 份黃金檔逐支釘）。

配兩支「射程非空」測試（階段 0 的同一個釘法）：`test_the_case_book_scope_is_not_silently_empty`（病例書不在 → 這一格與 17 份黃金檔的射程同時變空）與 `test_the_case_book_is_the_only_one_with_prose`（哪天別的書也長出正文，這個樣本可以也應該改成自動挑選）。

> **它第一次執行就抓到東西**（與階段 0 擴 `情境測試/` 射程時一模一樣）：`prose-metrics` 對 `一世之尊` 印的 `## 一世之尊 正文結構（93 章；零 LLM、可覆算）` **不被 `_SCOPE_MARKERS` 認得**，於是報「沒印覆蓋率行」。那是一條合格的覆蓋率行（它說得出掃了幾章），只是形狀是第七種。
> **為什麼拖到今天才發現**：第 6 項本來只跑 `書本模板`（無 chapters/ → exit 2）與一本純 raw 書（同樣 exit 2）——**`prose-metrics` 的成功輸出從來沒有被這一項看過**。病例書是唯一一本有 93 章正文的書。**掃描對象是對的，而樣本沒有涵蓋那條分支。**

## 四、1d 三筆掛帳，全部結清

### 1. `共同約定.md:42` 那句半真的相容承諾

**結清方式是把另一半也拿掉，不是把缺的一半補上。** 實測活用戶 0，補相容是替一條沒有人走的路加工。七處全部只認 `裁決流.md`，舊名換來墓碑。`共同約定.md`／`裁決流.schema.md`／`幕綱.schema.md` 三處文字同步。

### 2. `beat-lint`／`outline-lint` 對兩支 `.md` rollup 從「照舊比對」改成**存在性檢查**

`功能報告/15` 交回 12 的那一筆。功能 12 廢除五支 rollup，而 `ABOLISHED_ROLLUPS` 的射程只到 `.ai.md`（`check_book` 的 `rglob("*.ai.md")` 在定義上看不到 `.md`）——那兩支 `.md` 當時交給這兩支 lint 的殘留偵測，**而實作出來的是照舊比對**。

`beat-lint` 移除四項（視圖 ≡ 資料夾／幕號範圍 ≡ min·max／列序遞增／選用公式只准指路）與七個計數欄，換成一個布林 ＋ 一筆墓碑；`outline-lint` 的第 3 項同形改寫。**那份重算沒有消失**——它在 `beat-lint --emit`／`outline-lint --emit`（功能 12 抉擇 4 C 給它的家），由 `test_the_recomputation_moved_to_emit_not_away` 釘住。

### 3. `prose_metrics` 6 支長期紅測試 → 全綠，`known-red.toml` 清空

- **`skipif` 守錯對象**：檢查 `芯片巫師/` **資料夾**在不在（在，只剩 `raw/`），而測試要的是 `芯片巫師/chapters/`（不在）。**守錯對象的 guard 比沒有 guard 更糟**——沒有 guard 至少壞得像壞的。
- **舊清單反對過的修法，反對得有道理**：它說「改成檢查 `chapters/` 之後這 6 支會變 skip，而那正是**測試是綠的、射程是空的**」。**答案不是不改 guard，是改對 guard ＋ 補一支說「射程空了」的測試**（兩支已補）。
- **真正的死因是語料沒了，不是 guard**：對照組 `芯片巫師` 的章節在 commit `a19bf0d`（作者「只保留他們的 raw」）被刪除。

> **這裡要修正計畫的一句話。** 計畫寫「那 6 本對照語料**全部都在 `examples/` 裡**——測試找不到是因為它在錯的地方找」。**前半對後半錯**：`_SIX` 那六本 known-good 一直都在 `examples/`，而測試也一直讀得到它們（那幾支測試本來就是綠的）。**缺的是第七本——對照組 `芯片巫師`，而它是被刪掉的，不是放錯地方的。** 六本語料在不在 `examples/` 與這 6 支紅測試無關。

**它撐的那個論點隨語料一起離場**：「另一本書、另一份風格檔、另一個文類，節奏簽名一模一樣，**所以病因不在風格檔**」。依賴它的兩支測試移除，並立墓碑 `test_the_second_generated_book_is_gone`——`芯片巫師/chapters/` 哪天回來，那支會紅，而紅字說的是「**對照組回來了，去把那兩支測試接回去**」，不是「有東西壞了」。

`known-red.toml` 清空但**檔留著**：雙向擋的第一個方向（「紅而不在清單裡 → fail」）需要它，而一份空清單與一支不存在的檔在 `tomllib` 底下不是同一件事。`tools.yml` 的 `["known_red"]` 改成 `.get(..., [])`（**清單清空是正常狀態，而 `KeyError` 會讓「沒有已知紅」變成一次 CI 崩潰**），並印「已知紅清單：0 支（0 也印）」。

`meta_lint` 那支 `assert reds` 也改了——**它自己就是同一個病**：那一行把「全綠」與「清單讀不到」壓成同一句紅字。拆成兩支（有的話要有理由／檔還讀不讀得到）。
