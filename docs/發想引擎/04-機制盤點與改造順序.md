# Claude Code 機制盤點與改造順序

> **這一支回答 `03` 的下一題。** `03` 診斷出病因是「SKILL.md 是 prompt，不是執行引擎」；這裡盤點**工具箱裡到底有什麼**，哪些真的執行得了，以及照病灶排出來的改造順序。
> **同樣不改任何東西**，只新增這一支檔。
> **數字分兩種，逐處標明**：`〔實〕`＝ 2026-08-03 對本 repo 的實測；`〔推〕`＝ 依實測值推算的設計估計，落地才知道準不準。
> **機制細節依 Claude Code 版本可能調整**——真的要動手前，先跑一次官方文件核對欄位名，本檔的論證不依賴任何單一欄位的拼法。

# 一、七個機制

| 機制 | 住哪 | **誰觸發** | 進 context 的時機 | **能不能強制** |
|---|---|---|---|---|
| **CLAUDE.md** | 專案根／`~/.claude/`／子目錄 | — | **每回合無條件** | 請求 |
| **skill** | `.claude/skills/<名>/` | **模型**（讀 description 自己決定） | 觸發時，SKILL.md 整支 | 請求 |
| **subagent** | `.claude/agents/*.md` | 模型（或被 SKILL.md 點名） | **獨立 context 視窗** | **✅ 靠 `tools:` 白名單** |
| **slash command** | `.claude/commands/*.md` | **使用者**（打 `/名字`） | 打的當下 | 請求（但可**內嵌 bash 先跑**） |
| **hook** | `settings.json` 的 `hooks` | **事件** | 由 script 決定塞什麼回去 | **✅ 唯一能擋下工具呼叫的** |
| **permissions** | `settings.json` 的 `allow`／`deny`／`ask` | 事件 | — | **✅ 硬擋** |
| **MCP server** | `.mcp.json` | 模型 | 工具 schema | — |

外加兩層：

- **plugin** — 把上面全部（skills ＋ agents ＋ commands ＋ hooks ＋ MCP）裝成**一包可散佈的東西**。
- **Agent SDK ／ `claude -p` headless** — 在 CLI 外面自己寫迴圈，每次都是全新 context。

## 1.1　這張表只有最後一欄真的重要

`CLAUDE.md` 的中心思想已經寫死了：

> 「**確定性的工作一律進程式，LLM 只做判斷**——加投影，**不要在 SKILL.md 裡寫『請只讀相關部分』這種規勸（規勸不會被執行，工具會）**。」

而 **`E1`「沒有檢查器的保證只是口頭承諾」是同一句話的格式版**。

問題在於：**這條原則被套用到「書內檔的格式」，沒有被套用到「skill 自己的行為」。** 12 支閘門守住了「檔長什麼樣」，但「skill 執行時該做什麼、不該讀什麼」全部還停在 prompt 層。

`write/SKILL.md` 的 86 個規勸語彙〔實〕挑五條看，每一條的性質都一樣：

| 規勸原文 | 它在防什麼 | 現在靠什麼執行 |
|---|---|---|
| L67「讀它列出的檔就好，**不要** `設定/角色/*` 全撈」 | context 爆量 | 一句話 |
| L69「`write` **一律不要**加 `--include-underwater`」 | **揭底資訊的存取控制** | 一句話 |
| L76「用 `--for-beat`，**不要**自己填 `--entities`」 | LLM 自填在場者會漏 | 一句話 |
| L107「`行文節奏與呼吸.md` **生成時不必載入**」 | 正面技法在動筆時會被套到每一段 | 一句話 |
| L133「**先寫完** `## 本章事實` **再**封章」 | 否則蓋的 hash 對不上 | 一句話 |

第二條特別值得停一下：**那是存取控制**（`水下.md` 是揭底前的資訊隔離），現在由一句禮貌的請求守著。這在任何別的系統裡都會被當成 bug。

`CLAUDE.md` 對 `raw/` 也是同一個形狀：「**選擇器是人不是工具，不得改成『讀整個資料夾』**」——一句話。

**這不是要指責誰。** 這是說：`03` 診斷出的病因（prompt 執行不了東西）**有一半的解藥不在 skill 這一格**，而在下面三格。

# 二、skill：三層，但沒有第四層

漸進式揭露在 skill 裡是**真的**，共三層：

| 層 | 內容 | 何時進 context | 現行系統 |
|---|---|---|---|
| **1** | frontmatter 的 `name` ＋ `description` | **永遠在** | 12 支 ＝ 10,002 B〔實，`03` base〕 |
| **2** | SKILL.md 本文 | 觸發時**整支** | `write` ＝ 47,973 B〔實〕 |
| **3** | skill 資料夾裡的其他檔（`references/`、`scripts/`、`assets/`） | **被 Read／被 Bash 執行時才進來**，**在那之前成本是零** | **12 支全部沒有**〔實〕 |

所以 `03` §1.2 的「零漸進揭露」要更精確一句：**這不是機制缺陷，是第三層一個檔都沒建。**

## 2.1　但你說對了一半：skill 沒有執行引擎

SKILL.md **不會**「跑到第 5 步」。它是一段一次讀完的文件，12 個步驟是**同時生效的 12 段約束**——`03` §1.1 沒說錯。

拆 `references/` 能解掉的是**「不會走到的分支」**，解不掉**「這個節點不需要、那個節點需要」**。兩者差很多，下面 §六、§九會分開處理。

# 三、subagent

## 3.1　它不住在 skill 裡

```
.claude/
├── skills/
│   └── write/
│       ├── SKILL.md          ← prompt（該瘦成路由表）
│       ├── references/       ← 第三層檔案
│       └── scripts/          ← 可執行
└── agents/                   ← ★ 另一棵樹，不在 skill 底下
    ├── 章落檔.md
    └── 章草稿.md
```

定義檔形狀跟 SKILL.md 很像，欄位不同：

```markdown
---
name: 章落檔
description: 寫完某章正文後，產出 chNNNN.ai.md、封章、跑三個閘門直到全清
tools: Read, Write, Edit, Bash        # 省略＝繼承全部
model: sonnet                          # 省略＝繼承主 agent
---

（本文 ＝ 這個子 agent 的 system prompt）
```

**關係是「引用」不是「包含」，而且多對多。** `write` 步驟 8 呼叫 `章落檔`，`revise` 也呼叫同一支。

**這正好解掉 `03` §2.3 那一格**：

> 「六支會寫檔的 skill 各自寫了一遍同一套 9 個落檔動作，每支平均 3,900 B。**這該是一個動作，不是六份規格。**」

`references/` 只能共用**文字**（六支各自 `@` 同一支檔，但六支仍各自決定要不要遵守）；**subagent 連 context 隔離一起共用**——落檔的 schema 位元組永遠不進創作視窗，六支 skill 誰呼叫都一樣。

⚠️ **副作用**：agent 的 `description` 跟 skill 的一樣是**常駐成本**（主 agent 靠它決定要不要委派）。別開 20 支，那等於把 `03` 表 A 的 base 再墊高一層。

## 3.2　沒有「一次 LLM call」這種 subagent

這是最容易設計錯的一格，說白：

> **subagent 永遠是一個 agentic loop。** 沒有任何欄位可以寫 `turns: 1`。你把它叫起來，它就會自己 tool-use → 讀檔 → 再想 → 直到它認為做完了。

你能控制的只有三個閥，全部是間接的：

| 閥 | 怎麼用 | 效果 |
|---|---|---|
| `tools:` | **不給工具 ＝ 它無事可做，只能一次成形回答** | 最接近「單發」 |
| prompt 形狀 | 「只輸出 X，不要探索、不要驗證」 | 弱約束，會漂 |
| **終止判準** | 給它一個可機械驗收的出口 | **真正決定它該不該多輪** |

## 3.3　判準：**有沒有確定性的驗收者**

> **有 → 多輪**（迴圈到驗收者說 clean）；**沒有 → 單發**（把判斷交回作者或主 agent）。

不是「這件事複不複雜」。**沒有驗收者的多輪，就是讓 LLM 自己說自己寫好了**——那是最貴也最沒有保證的一格，而且它剛好長得最像「進階用法」。

`write` 六個節點對一次：

| 節點 | 該是什麼 | 驗收者 | 為什麼 |
|---|---|---|---|
| A 前置 | **0 次 LLM** | — | 純 script，連 agent 都不該開 |
| B 分章 | **單發**，`tools: Read` 或不給 | **作者** | 給它 Bash 它會跑去驗證自己的分章，浪費且沒意義 |
| C 章草稿 | **單發**，`tools: Read, Write` | 下一個節點 | 沒有機械驗收者。讓它自我批改會踩「抗生硬 ↔ 節奏三上限」互相侵蝕（§9.2） |
| D 體檢 | **0 次 LLM** | — | `prose-metrics` |
| **E 落檔** | **真正的多輪** | **`ch-lint` ＋ `derived-sync validate` ＋ `fact-lint` 三支全清** | 它可以「寫→跑→看報錯→修→再跑」到乾淨，**而且不可能自欺**——`write/SKILL.md` L139 那條在守（事實行或幕錨點印 0 ＝ 你寫的東西沒被讀到，不是乾淨，`E2`） |
| F 交付 | 單發 | 作者 | |

**六個節點裡只有一個該是多輪的，而它是最無聊的那個。** 這通常違反直覺——大家會想把「寫散文」做成多輪自我精修。**但寫散文沒有驗收者，落檔有。**

## 3.4　什麼時候**不要**開 subagent

`references/` 檔和 subagent 都能做到「精準 context」。差別只有一個：

| | `references/xxx.md` | subagent |
|---|---|---|
| context 精準 | ✅ 讀了才進來 | ✅ |
| **中間垃圾會不會污染主視窗** | ❌ 會（lint 報錯輸出、schema 全文、失敗的嘗試全留著） | ✅ 只回傳結論 |
| 作者能不能中途插話 | ✅ 能 | ❌ 不能 |
| 產出要不要付兩次錢 | 不用 | **要**（回傳值進主 context） |

**判準：這個節點會不會產生大量「用完就該丟」的中間物？**

- **落檔 → agent。** schema 位元組 ＋ 三支 lint 的 N 輪報錯，全部是用完就該丟的東西，而它現在整批留在寫散文的那個視窗裡。
- **分章 → `references/` 就好。** 它的產出**本來就是要給作者看的**，丟進 agent 只是繞一圈，還把作者調整分章的互動性弄掉。
- **章草稿 → 走 agent 的話務必讓它 `Write` 檔案、只回傳三行報告**（章號／涵蓋幕／`輸出格式` 那條演出盤點行），別把 3,000 字散文從回傳通道再送一次。

## 3.5　三個必須先知道的代價

1. **subagent 不能問作者。** 它只能做完回報。這聽起來是限制，其實是**強制你實作 `03` §四① 的單一 gate**——所有承重抉擇被逼到分章那一次問完。**但反過來說：多節點如果不配單一 gate，往返只會更多**（`03` §1.4：`write` 一支跨 5 輪、40+ 題）。**這兩件事是正交的兩軸，得一起改。**
2. **腔調連續性要手動遞。** 子 agent 是全新的，寫 ch0005 的那個不記得 ch0004 的口氣。`write/SKILL.md` L170「動筆前讀前一章正文對腔」現在是個期望，在這個架構裡必須變成**強制輸入**。
3. **章與章有依賴，不能平行。** 真正能平行的是 `write-test` 的 11 項檢查、`beat-test` 的 9 項、和分章的 A/B/C 候選——**審稿與提案可以平行，撰寫不行。**

# 四、hook —— 最大的缺口

hook 是一支**在事件發生時被跑的 shell script**，從 stdin 拿到 JSON（含 `tool_name`、`tool_input.file_path` 等），用 exit code 與輸出決定接下來怎樣。`PreToolUse` 回 exit 2 **會擋下這次工具呼叫**並把 stderr 餵回給模型；`PostToolUse` 回 exit 2 會把 stderr 餵回去讓它修。

事件有：`PreToolUse`／`PostToolUse`／`UserPromptSubmit`／`Stop`／`SubagentStop`／`SessionStart`／`SessionEnd`／`Notification`／`PreCompact`。matcher 比對的是**工具名**，路徑過濾在你自己的 script 裡做（讀 stdin 的 `tool_input.file_path`）。

## 4.1　為什麼它比 SKILL.md 的步驟強

**因為它不在模型的注意力預算裡。**

`03` §1.1 的整個論證是「12 個步驟是同時壓在注意力上的 12 段約束」。hook **完全不佔那個預算**——它住在檔案系統的事件裡，模型正在寫字的時候它照跑。

而且它**跨 skill 自動涵蓋**：`write` 寫的、`revise` 改的、你手動改的、未來任何新 skill 寫的，只要動到那個路徑就會被檢查。**這是 `references/` 和 subagent 都做不到的一格**——那兩個都要「被記得呼叫」。

## 4.2　例①：正向地板（`03` 附②）——這才是它該住的地方

`03` 附②：

> 「補上正向地板。現行 12 支閘門**全部是『你寫錯了』，沒有一支問『你有沒有寫』**……翻成**產出後的機械量測**（逐章數對白、在場且有台詞或動作的角色、外部事件、動作詞頻，逐 arc 對照本書前段）。**這是唯一會攔下 93 章崩塌曲線的東西，而它只需要數幾個數字。**」

```
PostToolUse  matcher: "Write|Edit"
  → script 讀 stdin 的 file_path
  → 不是 chapters/ch*.md → exit 0（靜默）
  → 是 → 跑 prose-metrics，對照本書前段（不設跨書絕對值）
      對白數／動作詞頻／在場有台詞角色數 掉到基準 1/3 → exit 2
      stderr 印：「ch0093 對白 0（前 10 章中位 30）、動作詞頻 0（中位 4）」
```

**為什麼寫成 hook 而不是 SKILL.md 步驟 9**：`write/SKILL.md` 步驟 9 就是自我檢查，而 93 章實測是**連續 11 章低於 schema 明訂基準的三分之一，零告警**〔實，`03` §1.4〕。模型正在寫字時，自我檢查是它自己的注意力預算裡優先序最低的一項；hook 不商量。

⚠️ **門檻一律相對本書前段**——`氛圍與筆調.md` 已實測過「任何跨書絕對門檻都會過度回報」，那個負面結果明文寫著叫後人別再試一輪。

## 4.3　例②：落檔閘門，不必再寫進六支 SKILL.md

```
PostToolUse  matcher: "Write"
  → *.ai.md          → derived-sync validate ＋ 對應軸 lint
  → story/物件/*.md   → fact-lint
  → story/參照/*.md   → decision-lint / readiness-lint
  → 有錯 exit 2，stderr 就是報錯全文，模型當場修
```

`03` §2.3 的「六份可以各自漂移的規格」，**hook 比 subagent 更徹底**：subagent 還要被人記得呼叫，hook 不會被忘記。

## 4.4　例③：`Stop` hook ＝ 交付前的守門

```
Stop → derived-sync check ＋ readiness
     → 本次寫的章沒 stamp、或有 stale → 擋下收工，要模型補完
```

`write/SKILL.md` L177「完成後……確認已 stamp」現在是一句期望；`Stop` hook 讓它變成**不做完不能結束**。

## 4.5　其餘幾個入口

# 五、slash command —— 它能**在 LLM 看到任何東西之前先跑程式**

command 檔裡可以用 `` !`cmd` `` 內嵌 bash、用 `@path` 內嵌檔案，兩者的輸出**直接變成 prompt 的一部分**。

## 5.1　`write` 步驟 1／1.5／2 可以整段消失

現在那三步是 **5,732 B**〔實〕，大半在解釋四個 `uv run` 的 flag 該怎麼下。改成：

```markdown
---
description: 依幕綱寫某 arc 的正文
argument-hint: <書> <arcNN>
---
## 本次涉及的設定檔（只讀這些，其餘不撈）
!`uv run --project tools/settings_select settings-select --book $1 --arc $2`

## 進場事實投影
!`uv run --project tools/fact_projection fact-project --book $1 --for-beat ...`

## 權威章序
!`uv run --project tools/beat_metrics ch-lint --book $1 --emit`

## 就緒現況
!`uv run --project tools/derived_sync readiness --book $1`

依上述結果走 write 的分章提議（步驟 3，見 .claude/skills/write/references/分章.md）。
```

**模型醒來時看到的是結果，不是說明書。** 那 5,732 B 裡的 flag 教學、「不要自己填 `--entities`」、「不要 `設定/角色/*` 全撈」全部失去存在意義——**因為那些選擇已經在 LLM 有機會做錯之前就做完了。**

這正是 `03` §四② 稱讚 `sync` 的那句話的實作形式：

> 「它跑最多工具、載入最少文件……**不預先載入產物，而是依依賴鏈讀受影響範圍**。這正是發想引擎的載入契約該有的形狀：**招的定義本身就是選擇器。**」

## 5.2　它補上了系統缺的那個入口：**使用者觸發**

| | skill | slash command |
|---|---|---|
| 誰決定要不要用 | **模型**（看 description） | **你** |
| 用在哪 | 「作者在做 X，該用哪支」 | 「我就是要跑這個」 |

`CLAUDE.md`「降檔閥（反僵化）」那一整段之所以得寫成勸告，正是因為 skill 只有「模型觸發」這一種入口。**command 給了一個確定入口**：`/輕量 <需求>` 就是輕量模式，不必說服模型不要升級成完整 skill。

## 5.3　32 招的天然形狀

`01-引擎目錄.md` 的每一招是「給定 A，產出 B」，七欄裡有一欄叫「**載入**（目標位元組）」、一欄叫「**依據**（逐節指名）」。

**那就是一支 command 的規格書**：`依據` ＝ 檔裡的 `@` 行，`載入` ＝ 你要守的預算，`輸入` ＝ `$ARGUMENTS`。

而 `01` 那條紀律——「**依據逐節指名，不得寫『參考某檔』。寫鬆了就會退回『請只讀相關部分』那種不會被執行的規勸**」——在 command 裡是**自動成立的**，因為 `@技巧知識庫/需求四象限.md` 寫進去就是真的載入，寫「參考需求四象限」則什麼都不會發生。**格式本身逼你寫對。**

`settings.json` 的 `deny` 規則是硬擋，不商量。兩個現成的對象：

# 七、plugin ＆ headless

## 7.1　plugin ＝ 你已經在做的「生產包」

`CLAUDE.md` 已經有這些概念：**生產包**（7 項）、**射程宣告**、`meta-lint` 第 13 項守**封閉性**、`tools.yml` 步驟 ⑤ 的**導出冒煙**、以及 `devtools/` 拆出來的理由（「一支指令進生產包而它的觸發者沒有，是 `E1` 的反面」）。

**plugin 就是那個概念在 Claude Code 裡現成的載體**：它打包的正好是 skills ＋ agents ＋ commands ＋ hooks ＋ MCP，而它的邊界（進包／不進包）跟你手畫的那條是同一種東西。

**這不是建議現在就改包裝**，是說：如果哪天要把這套系統給第二個人用，**不必自己發明散佈格式**，而且 `meta-lint` 第 13 項的三個檢查在 plugin 形態下有現成的落點。

## 7.2　headless ＝ 遷移唯一可行的形狀

`03` §3.4 那句最深的話：

> **52% 是不該被重生的內容 → 沒有人敢重生 → stale 偵測失去意義。**

要解它，得先做一次**遷移**：一世之尊 126 支 `.ai.md`〔實〕、162,265 B 枚舉外節〔實〕，逐支判斷哪些內容是 `D3` 第 ③ 格（重跑不會回來 ＝ 真正的源）該回寫源檔、哪些是 ② 該留下重生。

**這在互動 session 裡做會爆**（每支都要載入 schema ＋ 源檔 ＋ 衍生檔，126 支累積下來遠超任何 context）。`claude -p` 在 bash 迴圈裡一支一支跑，**每支都是全新的乾淨 context**，輸出寫成一份逐檔的分類表交你審。

**這是全篇唯一一個「非做不可、而且只有這一個機制做得到」的用途。**

## 9.2　三件切不動的東西

**① 不要把「寫一段」再往下切成技法鏈。**

「先寫 → 再套 Deep POV → 再套抗生硬 → 再套節奏」這種串接會失敗，而 `write/SKILL.md` 自己就有證據，L107：

> 「**抗生硬會把你推向更短，這一關負責拉回來**」

這兩條是**互相拉扯的地板**。拆成兩個節點會讓它們打架，而且**最後一趟改寫會侵蝕前面每一趟的成果**。同一支檔 L107 還記了一次實測踩坑：「為守配額把想家段的留白砍了，卻在前段用掉了配額」——**那是同一個 context 內就會發生的事，切成多節點只會更嚴重。**

> **節點邊界要切在「產出物」上**（分章表／一章草稿／一份報告），**不是切在「技法」上。**

**② subagent 不能問作者**（§3.5）。

**③ 腔調連續性要手遞**（§3.5）。

## 9.3　節點 C 的技法路由是**機械可判**的

這是最容易被誤設計成 LLM 判斷的一格。實際上判準全部寫在幕綱的欄位裡：

| 要不要載入這支技法檔 | **機械來源** | 效力（`_index.md`） |
|---|---|---|
| `字詞句法與抗生硬.md`／`行文節奏與呼吸.md` | 無條件 | **地板 always-on** |
| `動作場面寫作.md` | 該幕「行動」欄是不是戰鬥類型 | 條件 |
| `伏筆與意外.md` | 該幕有沒有 `埋/收[[伏筆:x]]` | 條件 |
| `主題題旨.md` | 該幕是不是主題三角鋪陳點 | 條件 |
| `需求四象限.md` | 該幕是不是角色抉擇點 | 條件 |
| `世界觀與背景.md` §九 | 該幕有沒有新設定登場 | 條件（**只讀此小節**） |
| `修辭與字句鍛鍊.md` | `00-摘要.ai.md` 的 `取向定位` 欄 | **天花板 opt-in** |
| `心理描寫.md` §二之二／`畫面感與電影化.md` 換行短句 | 不載入，只帶上限句 | **配額** |

**`技巧知識庫/_index.md` 已經把路由表寫好了**——三種效力（地板 always-on／天花板依取向定位 opt-in／配額有密度上限）就是這張表的分類欄。

所以「本章技法清單」**可以是一支 script 的輸出，不是一次 LLM 判斷**。而這正是 `CLAUDE.md` 那句「確定性的工作一律進程式」的直接應用。

## 9.4　節點 D 的判官應該是**程式**，不是 LLM

「跑出結果讓 agent 判斷好壞」這個直覺對，但對 `write` 而言，最該判的那幾件事全是可數的：

```
每章對白數 ／ 動作詞頻 ／ 在場且有台詞的角色數 ／ 場景數 ／ 本章最大外部事件有無
句 : 段 ／ ≤8 字獨立段密度 ／ 重拍裝置數 ／ 逗號 : 句號 ／ 分句均長
```

`03` 那條崩塌曲線〔實〕：

| 指標 | 原著 30 章 | 生成 ch0001–0010 | 生成 ch0084–0093 |
|---|---|---|---|
| 每章篇幅 | ~3300 字 | ~2700 字 | **~1050 字** |
| 每章對白數 | 30–50 | ~30 | **7.5**（ch0093 ＝ 0） |
| 動作詞頻 | 1–9/章 | 0–6 | **0** |

**用一個計數器就攔得住。用 LLM 判官不一定**——LLM 判官會說「這章雖然短但氛圍完整」，而那句話是對的，它只是沒有回答「這本書正在崩」。

`tools/prose_metrics` 已經在了（`行文節奏` 區塊四項簽名「**機械可測有絕對門檻**」）。缺的是把它接到 hook 上。

## 10.1　為什麼 6 排最後（真實的代價，不是保守）

**`write` 的定位是共創，subagent 是黑箱。** 作者現在可以在寫到一半時插話說「這段改一下」；子 agent 跑起來就插不進去，只能等它交件再走 `revise`。

**這不是技術問題，是你要不要放棄那個互動性的選擇**——而 `03` §1.4 抱怨的「跨 5 輪、40+ 題」跟這個互動性是**同一件事的兩面**。真正該砍的是那 40 題的**內容**（「這一句該不該存在」層級），不是砍掉作者插話的能力。**做完 1–5 之後再看那個數字，可能問題已經不在了。**

## 10.2　一句話

`03` 的病灶有兩個：**「規勸執行不了」** 和 **「六份會漂移的落檔規格」**。

- subagent 解掉一半（第二個）。
- **hook 兩個都解，而且不用動任何一支 SKILL.md 的流程。**

所以優先序是 **hook ＞ slash command ＞ `references/` 拆檔 ＞ subagent**，而排在它們全部前面的是**把 `共同約定.md` 搬出去**——那一項零風險、零設計、只是搬家。
