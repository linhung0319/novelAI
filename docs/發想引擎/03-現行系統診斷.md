> 全部是 2026-08-03 的實測值。分類方法：以 SKILL.md 的 section ＋ 編號步驟為粒度，雙模步驟再按 sub-bullet 拆；分母是整支 SKILL.md。
> **doc 側固定成本 base ＝ 111,344 B**（`CLAUDE.md` 21,235 ＋ 12 支 description 10,002 ＋ `共同約定.md` 80,047）——這是每一支 skill 執行前就已經付掉的錢。

# 一、skill 為什麼慢：prompt ≠ 工作流

作者原本把 skill 理解成「工作流 ＋ tool call」：觸發後依序執行、每步完成就釋放、tool 回傳結果、產出。**這個心智模型是對的——落差本身就是病因。**

Claude Code 的 SKILL.md **不是執行引擎，是一段被注入 context 的 prompt**。四個後果，每個都可量：

## 1.1　12 個步驟是同時壓在注意力上的 12 段約束

工作流引擎裡，第 N 步的成本付完就釋放。prompt 裡不是——`write` 的 12 步是**一次全部載入**，然後要求模型在寫散文的同時滿足全部。所以「多加一個檢查步驟」在工作流裡幾乎免費，在這裡是把創作的注意力再切走一塊。

`診斷01` 的 R9 給了這個現象一個很準的名字：**「治理文字擠掉創作預算」**。它 2026-07-26 標記「已修」；2026-08-03，`消失的密室` 長出 238,316 B 的 `裁決流.md`。

## 1.2　零漸進揭露

**12 支 skill 全部是單一 `SKILL.md`，沒有任何一支使用 `references/` 子檔。**

```
.claude/skills/*/SKILL.md   ← 12 支，全部
.claude/skills/*/           ← 底下沒有任何子目錄
```

Anthropic 的 skill 設計本來就支援漸進揭露（reference 檔在被讀取前不佔 context），而 `技巧知識庫/_index.md` L107 自己還引用了這條準則來論證「核心愈薄愈好」。**但那條準則沒有被套用到 skill 自己身上。** 於是 `write` 一觸發，47,973 B 連同不會走到的分支（動作場面特判、多 POV 分配、覆寫既有章、跨 arc 引用…）全部進場。

## 1.3　housekeeping 是「寫檔」的成本，不是「創作」的成本

這是本節最重要的一個數字：

| 群 | 支數 | housekeeping 平均佔比 |
|---|---:|---:|
| **唯讀的 test skill**（outline-test／beat-test／write-test） | 3 | **8.3%** |
| **會寫檔的 skill**（develop／organize／character／expand／worldbuild） | 5 | **38.0%** |

**差 4.6 倍。** housekeeping 幾乎全部集中在「會寫檔的那半邊」——它不是創作的成本，是**落檔的成本**。

推論很直接：**發想引擎只提案不寫檔，等於免費砍掉四成。** 這不是保守設計，是實測結論。

## 1.4　往返次數 × 全額 context

`情境測試/消失的密室/S6` 實測：

- `write` **一支跨 5 輪**、`revise` 跨 2 輪、`beat-sheet`（S5）跨 4 輪
- 八輪對話**問了 40+ 題**
- 產出 **3,700 字**正文
- 同一 session `裁決流.md` **150 → 157 列（＋7）**，以平均 1,085 字/列計 ≈ **7,600 字**

**治理文字的產出是正文的兩倍。**

而那 40+ 題的**內容**比數量更說明問題——全部是「這一句該不該存在」層級的：章末停在哪／哪一句是註腳／貓頭鷹要不要名字／客人姓什麼。**不是**「這一場誰先開口」「這一幕要不要有第三個人在場」。

這是約束集過大時的典型行為：**當可行解空間被壓窄，模型會改成問而不是寫。** 句子層有 5 條鐵律（**4 條是「不得…」**）＋3 個配額上限＋2 個地板，正向技法只有一個（離題型內心戲），而它自帶密度上限（一章 2–3 處、不連續兩段）。

系統自己的話（`診斷01` §四）：

> **「在一個只有負向約束的系統裡，最安全的產出就是最空的產出。」**

93 章的實測後果：

| 指標 | 原著 30 章 | 生成 ch0001–0010 | 生成 ch0084–0093 |
|---|---|---|---|
| 每章篇幅 | ~3300 字 | ~2700 字 | **~1050 字** |
| 每章對白數 | 30–50 | ~30 | **7.5**（ch0093 ＝ 0） |
| 動作詞頻 | 1–9/章 | 0–6 | **0**（ch0072 後 22 章近乎全 0） |

**連續 11 章低於 schema 明訂基準的三分之一，零告警。**

# 二、依賴與閘門：發想被關在編譯結果的下游

## 2.1　12 支裡有 11 支會停下來把你趕回上游

| skill | 前置條件 | 不滿足時 |
|---|---|---|
| `character` | `00-摘要.md` 主線／題旨 **且** 世界觀有源檔 | **停下** →「不要在真空中設計角色」 |
| `expand` | 同上 | **停下** →「不要在空中生劇情」 |
| `worldbuild` | 世界觀有源檔 | **停下** → 退回 `develop` |
| `organize` | 粗階段已完成 | 退回 `develop` |
| `beat-sheet` | 該 arc 有大綱 | **停下** → 先跑 `organize` |
| `write` | 該範圍有幕綱 | **停下** → 先跑 `beat-sheet` |
| `write-test` | 該範圍有正文 | **停下** → 先跑 `write` |
| `revise` | 找得到該章 | **停下** |
| `outline-test` | 有大綱可測 | 退回 `organize`/`develop` |
| `beat-test` | 有幕綱可測 | — |
| `sync` | （無硬閘門） | — |
| `develop` | **唯一沒有前置的入口** | — |

**作者的原始情境會撞上這面牆**：「已經有一段確定想加入的劇情，但角色還不確定」→ 觸發 `character` → 前置檢查發現摘要或世界觀沒建好 → 停下，叫你先跑 `develop`（23,701 B、10 步、doc 側 431,493 B、強制 9 支工具、停下問作者 8–10 次且分散）。

**這不是 bug。** 每一條閘門都有正當理由（不要在真空中發明設定）。但合起來的效果是：**系統唯一的入口是一個要求你一次拍板主角/結局/題旨/取向定位的冷啟動流程，而所有的推導能力都在它的下游。**

## 2.2　現行系統確實有發想能力，只是被三件事限制住

要說公道話：**`expand`／`character`／`worldbuild` 都有真正的生成引擎。**

`expand/SKILL.md`「提案生成規則」第一條，字面就是作者的例子：

> 「**缺衝突** → 套 `衝突 = 動力 + 阻礙`；若阻礙需要一個人格化來源，就推演『**新增一個帶著正當需求 X 的角色／對手**』……這正是『缺衝突 → 建議衝突 → 推演出需要新增某性格角色』的落地。」

三個限制：

1. **只有 3/12 支有。** 其餘九支是編譯、檢查、或同步。
2. **是「診斷驅動」而非「素材驅動」。** `expand` 問「這裡缺什麼」（要先有一個成形的 arc 才問得出來）；作者的問法是「我有 X，X 能給我什麼」（只要有一個特質就能跑）。
3. **`expand` 的引擎只有 5 個檢查**（結構階段／因果／場景完整／角色弧線／世界觀自洽），而知識庫 ＋ `Data/` 支援的推導方向約是它的**六倍**（見 `01-引擎目錄.md`）。

## 2.3　重複載入：12/12 必讀，而重複的形式比複製貼上更貴

| 共用檔 | B | 幾支載入 | 重複載入總量 | 冗餘 |
|---|---:|---:|---:|---:|
| **`結構定義/共同約定.md`** | 80,047 | **12/12 全部宣告「必讀」** | **960,564** | 880,517 |
| `CLAUDE.md` | 21,235 | 12/12 | 254,820 | 233,585 |
| 12 支 description | 10,002 | 12/12 | 120,024 | 110,022 |
| **base 小計** | 111,344 | | **1,336,128** | 1,224,784 |

schema：單份合計 319,534 B，重複載入 **1,304,836 B，冗餘率 75.5%**。
技法檔：單份合計 265,106 B，重複載入 **1,309,078 B，冗餘率 79.7%**。（25 支技法檔裡只有 `畫面感與電影化.md` 是單一 skill 專屬。）

**但真正貴的不是這個。**

> **12 支之間長度 ≥60 B 的完全相同行只有 10 條、冗餘 1,344 B ——佔 278,312 B 的 0.5%。**

重複幾乎**不是**複製貼上，是**同一條規則的 N 種寫法**：

| 同一件事 | 在幾支各寫一遍 | 平均相似度 |
|---|---:|---:|
| 「摘要軸兩支都讀＋權威在六欄」 | **9 支、10 處** | 29.5%（最高 55.7%） |
| 「就緒.md 更新（五個 token 之一）」 | 7 支 | 32.2% |
| 「設定層走選取／不整批讀」 | 5 支 | 36.9% |
| 「落裁決流」 | 4 支 | **99.6–99.7%（唯一的複製貼上）** |
| 「待裁決.md 追加一列」 | **11 支、共 40 次引用** | 語意同一、寫法各異 |
| 「rollup 2026-07-28 功能 12 廢除」 | 8 支、**23 次** | — |

**同一個契約在 9 支各寫一遍，等於 9 份可以各自漂移的規格。** 這比複製貼上難維護——複製貼上至少改一處就能 grep 到其餘八處。

**六支會寫檔的 skill 各自寫了一遍同一套 9 個落檔動作**（改源 → 重生 → stamp → 跑該軸 lint → 寫裁決流 → 清待裁決 → 更新就緒 → readiness-lint → decision-lint），每支平均 3,900 B。**這該是一個動作，不是六份規格。**

# 三、`.ai.md` 兩檔制：不是全冗餘，冗餘的是「散文半身」

原始設計意圖：`.ai.md` 有固定格式，程式可以**精準切片**取 context 給 LLM。同時規則要求它只能是源的重新表述、**不得含新資訊**。

作者感覺到的矛盾是真的，而且不只一個。

## 3.1　真的付了錢的三處

### ① 章節軸的 front-matter —— 最強的一格

| | 一世之尊 | 消失的密室 |
|---|---|---|
| 源 : 衍生 | 620,200 : 23,010 = **0.037** | 20,670 : 4,144 = **0.200** |
| 每支大小 | 238–256 B（極穩定） | 769–1,302 B |

六個欄（`對應幕`／`所屬arc`／`POV`／`基調參照`／`風格`／`狀態`）全部被 `beat_metrics/chapters.py` 與 `fact_projection/chapters.py` **逐欄**取值，投影成章序表。**「拆兩檔」與「程式逐欄取值」兩件事同時成立、成本幾乎為零。若只保留一個軸，就是它。**

### ② `消失的密室/story/設定/風格/風格.ai.md` —— 全 repo 唯一 100% 兌現設計原意的一對

源 **8,703 B** 自由散文 → 衍生 **1,166 B**，比值 **0.134**，而且：

```
front-matter 1,165 B（99.9%）　正文 0 B
```

五個欄（`基調參照`／`禁用詞表`／`稱謂系統`／`可用句式`／`語域`）全部被 `style_lint.py:573-587` 逐欄取值。

**同一支 schema 下的一世之尊產出 12,247 B（比值 1.732），其中 35.3% 是違規的 `## 待裁決回饋`。** 差別純粹是有沒有遵守。**這一對證明設計是可以兌現的：當衍生檔正文為 0 B 時，兩檔制就是純賺。**

### ③ 角色／世界觀的 LLM 分析 —— 「衍生」身分真正的正當性來源

| 檔 | 源 → 衍生 | 不可機械導出的分析佔比 |
|---|---|---:|
| `消失的密室/角色/榮恩` | 1,249 → 5,920（**×4.74**） | **≈86%** |
| `消失的密室/世界觀/權力與程序` | 1,801 → 3,559（×1.98） | ≈74% |
| `消失的密室/世界觀/爬說嘴` | 4,064 → 4,697 | ≈53% |

`榮恩.ai.md` 裡的這一段，是這一格價值的最好例子：

> 「**這一格永不兌現，而理由是機械的、不是氣質的**：他要的是被單獨數出來，而這本書零例外的單一視角**在機制上就保證了沒有人會替他數**。」

**把 1,249 B 的源檔刪掉重跑一次，這句話不會回來。**

## 3.2　規則本身要改的一個字

按系統自己的 D3 三分法（`CLAUDE.md` 第二問）：

| 逐格問「這一格的機械來源是哪一支檔的哪一欄」 | 落點 |
|---|---|
| ① 答得出來 | 投影，不落檔 |
| ② 答不出來，但只拿源檔重跑一次會回來 | 衍生 `.ai.md` |
| ③ **答不出來，且重跑不會回來** | **真正的源** |

上面那句「他那一格不被兌現的原因，就是這本書的視角規則本身」是 **③**。它住在一支合約寫著「下次重生即覆蓋」的檔裡。

但同時，`角色.schema.md` **明訂四節必填**（需求四象限／預期弧線／馬斯洛層次／對衝關係），而這四節在定義上就是新的判斷。**系統實務上是接受這種內容的。**

**所以那條規則的正確讀法是「不得含新『設定』」，而非「不得含新『分析』」。** 現在的寫法讓最有價值的內容處在一個文字上違規、實務上必需、而且會被重生吃掉的位置。

## 3.3　是冗餘的四處

### ① 設定層的散文節：是 (a) 純冗餘，而且沒有任何程式切得動它

`爬說嘴.ai.md` 的 `## 影響力`（佔該檔 22.5%）三條在源檔 `## 它在故事裡負責什麼` 已經逐條寫過，連句子都一樣：「這條能力線是題旨的載體，不只是一個謎題零件」。`一世之尊/風格.ai.md` 的五個散文節在源檔全部有同名節。

**而且沒有任何工具切得動它們。** repo 自己已經寫死這個結論：

- `結構定義/共同約定.md`「資格條款」：「衍生檔要享有『可以很大』的豁免，必須有對應的投影／切片工具。**沒有工具能切它，它就跟源檔同等受限**」，並明指「**`settings-select` 的粒度是『哪幾支檔』不是『檔裡哪一段』**」。
- `tools/derived_sync/src/derived_sync/sentinel.py:375,384` 的告警 `kind` 直接叫做 **「衍生檔不可切片」**，在一世之尊觸發 **33 次**。
- `settings-select --book 消失的密室 --arc arc01` 實測輸出印的是**檔案清單與位元組數**（`合計 53258 bytes（23 檔／14 個實體）`），不是節。

**唯一被 SKILL.md 指名讀「某一欄」的只有兩處**：`00-摘要.ai.md` 的 `取向定位`（3 支 skill）與 `chNNNN.ai.md` 的 `POV`／`風格`（`revise`）。**「精準切片取 context」這個設計原意，在設定層尚未實作。** 一支 33 KB 的 `江湖勢力.ai.md` 進 context 時就是整份 33 KB。

### ② 零消費者的宣告欄：一世之尊仍帶 97 個實例

`docs/重構/02-待用構想.md` 記過的三組欄，現在都在程式裡有具名的 `RETIRED_KEYS`（`world_lint.py:45`／`char_lint.py:52`／`summary_lint.py:83`）。實跑：

- `world-lint --book 一世之尊`：4 支仍帶已廢除的欄／共 **20 個**
- `char-lint --book 一世之尊`：**24/24 支**仍帶／共 **74 個**（角色×24、弧線類型×24、🧊水下×14、影響力×12）
- `summary-lint --book 一世之尊`：**3 個**（`基調主從`／`終局`／`節奏檔位`）

## 3.4　最深的一句

> **52% 是不該被重生的內容 → 沒有人敢重生 → stale 偵測失去意義。**

stale 偵測的真正價值是**存在性的**（讓「作者改了源卻忘了重生」在原則上不可能靜默），不是統計性的。但這個價值目前被第 ③ 點抵銷掉了：**你不敢按下重生鍵，那個機制就只是在記錄一個沒有人會用的事實。**

還有一個附帶證據：**93/93 章的 `## 本章事實` 是 0 支**（`fact_projection/sources.py:68` 自己記著「事實層覆蓋率是 0」）。一世之尊的 93 支章衍生檔全部只有 front-matter，`fact-project` 的三種投影在那本書上沒有輸入。而消失的密室 4/4 支都有——同樣是遷移落差，不是設計缺陷。

# 四、現行系統裡可以直接照抄的三個好設計

診斷不是為了否定。這三個是實測最乾淨的設計，發想引擎的形狀直接沿用它們：

## ① Phase 1 / Phase 2 單一 gate —— 來自 `character`／`expand`／`worldbuild`

**唯讀診斷 → 一次攤開所有候選 A/B/C → 拍板後才寫檔。**

實測：`expand`／`character` 各只有 **1 個停下問作者的點**，且設計成一次問完（`beat-test` 也是 1 個，在末端）。對照 `develop` 的 **8–10 個分散問點**（4 個「停下不得封章」的閘門全在同一步的不同 sub-bullet，觸發時機在落檔當下，無法預先一次問完）與 `organize` 的 5 個。

**往返次數是使用者感受到的「跑很久」的主因，而它是設計出來的，不是模型造成的。**

## ② `sync` 的形狀 —— doc 側 185,690 B，全系統最低

`sync` 是 12 支裡最接近「工具編排器」的一支：

| | sync | write |
|---|---:|---:|
| SKILL.md | 13,063 B | 47,973 B |
| doc 側固定成本 | **185,690 B** | 566,304 B |
| schema 載入 | **2 支 51,322 B** | 6 支 176,813 B |
| 技法檔載入 | **1 支 9,961 B** | 21 支 230,174 B |
| 強制跑工具 | 8 支 | 6 支 |
| 載入(a) 佔比 | **4.6%（最低）** | 25.8% |

**它跑最多工具、載入最少文件。** 原因是它「不預先載入產物，而是依依賴鏈讀受影響範圍」——先讓程式算出該讀哪些，再讀那些。這正是發想引擎的載入契約該有的形狀：**招的定義本身就是選擇器。**

（`sync` 的 doc 側 185,690 B 裡，base 就佔 60.0%——換句話說，**如果把 `共同約定.md` 移出執行迴圈，`sync` 的固定成本會掉到十萬出頭。**）

## ③ `消失的密室/風格.ai.md` 的形狀 —— 正文 0 B 的衍生檔

見 3.1 ②。它是「衍生檔該長什麼樣」的唯一完整範本：**只留機讀欄與不可機械導出的判斷，散文一律留在源檔由下游一起讀。**

`共同約定.md` 的「資格條款」其實已經把這個二選一寫成規則了——**衍生檔要嘛正文趨近 0，要嘛就得有真正的節級切片工具。現在缺的只是執行。**
