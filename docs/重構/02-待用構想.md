## 三、registry ＋ 抽取器（C3，功能 01＋02）

讓「人寫散文 → AI 抽 ID」可靠的機制：

1. 每種 ID 一份 registry（就是物件資料夾本身）
2. 抽取器**只能**命中既有 ID，或**提請註冊新 ID 交人確認**，不得自由造字
3. 抽取結果依 B2 **預填**給人核可，核可後 `stamp` 封章（A3 第 2 條路）
4. 只有散文變了才重抽

抽取失準的認賠依 E3：伏筆會自癒（有強制的「收」）；錨與約束不會，必須預檢或人核可。

## 六、增量重生（功能 04）

若把「不可重生」的內容改成「有散文源可重生」，重生成本會變成問題（從長 prose log 重生數百列表格，貴且不確定）。解法：

- prose 源是 append-only 的
- 每一列衍生結果記下它來自**哪一段 prose 的 hash**
- 只有新段落產生新列，既有列不重算 → 成本 O(新增) 而非 O(全部)

### ✗ 現在就蓋物化快照（`fact-project` 的第三階）

**駁回於** 2026-07-27（功能 01 重構輪，作者拍板）。**理由是量出來的，不是感覺**：

| 量 | 一世之尊實測 |
|---|---|
| 單次 `--for-beat` fold 幾筆 | **259 筆**（全書 100%，毫秒級） |
| 單次輸出多大 | **4,624 字元**（25 slot 行／16 個實體節） |
| 成長率 | 每 arc 首幕投影字數線性回歸 **≈ +356 字元／arc** |
| 500 章外推 | ≈ 21,000 字元／次查詢、fold ≈1,400 筆 |

**真正的成本不在 fold**（259 筆的 fold 是毫秒級），**在輸出塞進 context**。所以門檻該量輸出、不該量筆數：

> **觸發門檻＝單次 `fact-project --for-beat` 輸出 > 8,000 字元。** 依 +356 字元/arc 的斜率，約在 **arc22（≈190 章）**。到那時再蓋，之前不要。

**為什麼不「反正遲早要蓋，先蓋了省事」**：快照是衍生層，蓋了就要負責「什麼時候失效、誰重算、怎麼 stamp」。在還沒有任何一本書逼近門檻時蓋，等於**先付一筆維護成本去換一個還沒發生的問題**，而且會把還會變的 delta 格式提前釘死（D2 的解法階梯是「一階一階往上，不是一次蓋到頂」）。

> **附帶紀錄**：`設計原則.md` D2 是目前唯一能說出「**不要做**」的原則，這一條就是它的產出。一條只能說「要做」的原則沒有決定力。

### ✗ 把「有故事可寫的物件才開檔」量化成引用次數門檻

**駁回於** 2026-07-27。**理由**：在一世之尊上跑不出任何數字能分——29 個實體裡 `孟奇` 顯然要開檔、`金剛寺使者` 顯然不要，**中間那 27 個沒有任何可依循的判準**，任何 N 都是任意的。而且次數門檻會逼一個「只有狀態、沒有故事」的東西開一支寫不出內容的檔，那正是 G4 原本要避免的事。
