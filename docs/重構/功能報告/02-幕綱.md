## 零、先講四個實測結論

1. **幕綱的「為什麼」沒有家，於是它長進了故事欄裡。** schema、beat-sheet skill 三處（`幕綱.schema.md:42/55/65`、`beat-sheet/SKILL.md:60`）都命令「設計註落檔時搬進 `story/參照/裁決流.co.md`」——**那支檔不存在**（`一世之尊/story/參照/` 只有 `就緒儀表.md`／`狀態事件流.md`／`結構.md`）。搬移無處可搬，結果：`行動`欄均長從 arc01 的 **76 字/幕** 漲到 arc09 的 **513 字/幕（6.7×）**，B/幕 從 1366 漲到 **9113**，7 個 arc 超過 2500 的健康上限。成長哨兵忠實地報了 7 筆「幕綱肥大」，但它是 advisory、不影響 exit code，而且它指的補救動作是搬去一支不存在的檔。**守衛在響，但它指向的門是關死的。**

2. **幕綱是四支工具逐行解析的強格式，卻零檢查器。** `_BEAT_HEAD_RE`／spine regex／伏筆 regex 各被手抄進 4–5 個套件（見 §二 V7），而下面這些 schema 白紙黑字的格式承諾，**沒有任何一支工具在守**：幕號唯一性與存在性、`前因 [[幕NNN]]` 指向的幕是否存在、八欄是否填齊、spine 是否涵蓋所有 arc。實測 157 條前因引用**恰好 0 條懸空**——但那是人手維持的乾淨，不是工具保證的乾淨。`beat-test/SKILL.md:38` 甚至明文說懸空前因「是最高優先級的**機械事實，不需 LLM 判斷**」——可是沒有機械在判，只有 LLM 在手做。這正是 E1 說的「口頭承諾」。

3. **「本 arc 伏筆狀態」表宣稱是視圖，但它比來源多出 2 個名字，而且沒有任何工具重算它。** 全書 18 個埋收標記／15 個伏筆名；狀態表 **53 列／17 個名**。多出來的兩個是 `呆底下另有東西（真慧）` 與 `寺裡那個開門的人（真觀）`——把純文字別名括進去造出來的變體。`幕綱.schema.md:131` 稱這張表是標記的「視圖」「作者永遠只維護幕綱這一份」，但 53 列全是手維護、無工具重算，而且它承載的東西標記裡根本沒有（那些「純文字續行」的伏筆刻意不立 token）。**它不是視圖，是第二個家，而且已經和第一個家漂移了。**

4. **幕綱是功能 01 狀態物件的「計畫軌」（G5），但這條軌目前一半在 token、一半在散文表格裡，程式只看得見前一半。** 埋收標記（18 筆）程式讀得到；「純文字續行」（arc07 起大量採用，狀態表 53 列裡的多數）程式讀不到。G5 要的「計畫軌 vs 已成軌」一行 diff，前提是計畫軌整條可解析——現在不成立。

### Q3 · 量隨什麼成長？一次查詢讀幾筆

| 量 | 一世之尊上的數字 | 怎麼量的 |
|---|---|---|
| 一本書有幾份 | **11 支** `arcNN.md` ＋ **1 支** `_index.md` | `ls` |
| 每份多大 | arc 檔 12–87 KB；`_index.md` **28,996 B／17 行** | `os.path.getsize` |
| 每份幾幕 | 6–12 幕（arc08 只 6 幕、87 KB） | 逐檔 parse |
| **B/幕（肥大指標）** | arc01 **1366** → arc08 **9113** → arc09 **8673** → arc10 **7402**；健康上限 2500，**7 個 arc 超標** | `sentinel.beat_sheet_density` 實跑 |
| **行動欄均長** | arc01 **76 字** → arc09 **513 字（6.7×）**；全書基準 124 字 | `beat-metrics` 實跑 |
| **母題重複率** | arc01 **4.6‰** → arc10 **62.6‰**；基準 11.0‰ | 同上 |
| `_index` 最長單行 | **1949 字**（arc09 概覽行）；8 行 >600 字；概覽 11 行全是單行 652–1949 字 | 逐行量 |
| 設計註 | 只 arc11 有 `## 設計註` 節（4897 B）；其餘 10 支＝0（**不是搬走了，是滲進欄位了**） | 逐檔 parse |
| **一次「全書」查詢讀幾筆** | `foreshadow-project`／`beat-metrics` 每跑一次**讀全部 11 arc／108 幕**（O(全書)） | 讀 `load_book`／`scan` |
| **一次「單幕 context」查詢讀幾筆** | `settings-select --arc` 讀 **1 支 arc**；`fact-project --for-beat` 由 `find_beat` **順序掃 arc 檔直到命中目標幕**（O(目標之前的 arc)） | 讀 `select.py:215`／`beats.py:83` |

**兩個結論：**

- **成長的是「行」，不是「筆」**——與功能 01 完全同構。幕數每 arc 穩定 6–12、無成長；成長的是每一欄塞多少字（76→513）。而它**已經有守衛**：`beat-metrics` 用相對前段基準抓「行動欄膨脹」「母題複製」（arc07–10 命中 3–4×），`sentinel` 抓 B/幕。問題不在沒守衛，在守衛**只報不擋**、且補救動作指向不存在的檔（見 §零 1）。
- **查詢成本本身健康。** 全書報告 O(全書) 是應該的（要看全書伏筆帳就得讀全書）；單幕 context 是 O(1 arc)。`_index.md` 的 28 KB 膨脹**不傷查詢成本**（解析器只掃 `全書順序：` 那一行），但它**傷人與 AI**——`_index` 定位是「AI 檢索入口」，一個 1949 字的單行索引項等於沒有索引。這是 D1 的實例：一支索引檔在回答「全書關於這個 arc 的一切」。

E1 說「每一條格式承諾都要指名一個檢查器與一個觸發時機」。V1（設計註搬去不存在的 `裁決流.co.md`）暴露了一個 E1 沒覆蓋的縫：**schema 指名了一個搬移動作與觸發時機（`beat-sheet` 落檔時），但沒有人驗證「目的地存在」**。這不是「格式承諾無守衛」，是「**遷移承諾的終點無守衛**」——工作流的箭頭指向空氣，而箭頭本身格式完全合法。

建議 E1 補一句可執行推論：**凡 schema 指定「搬去某檔」的遷移動作，那支目的地檔的存在性本身要有守衛**（或至少 `derived-sync`/`beat-lint` 在觸發時檢查目的地在不在，不在就報而非靜默）。這一條同時會抓到功能 04 的 `.ai.md 待裁決回饋` 那類「有出口指標、出口卻不存在」的病。

### 6.2 判得動、記錄一下（避免下輪重測）

- **G5（兩條時間軌）在本功能上非常好用**：它直接告訴我 D/E 是計畫軌、`write-test` 讀的是已成軌，diff 是審稿標的。它也讓抉擇 2（續行算不算計畫軌）變成一個**可判**的問題。
