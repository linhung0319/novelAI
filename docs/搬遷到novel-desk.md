## 已定案

1. **放棄全自動。** 以人使用、AI 輔助為主。功能範圍是討論世界觀、輔助建構角色、建立大綱與幕綱、寫內文。
2. **方法論不預設載入。** AI 先自由回答，作者不滿意才主動觸發招數。
3. **不測招數是否勝過自由回答。** 會觸發就代表自由回答不夠，招數只是再試一種方式。
4. **不做平時同步。** 原本的主要用途是忘記前情時查角色變化，改由搜尋取代，前提是資料好搜。只同步搜到的部分屬於低優先 bonus。
5. **不做用程式硬算的統計與門檻。**
6. **上架與題材類需求目前不做：** 數值帳、起名、書名簡介、拆書、敏感詞、版本快照作為申訴證據。
7. **知識庫要精煉、結構化、去重，取用時走 progressive disclosure。**
8. **skill 遵守 Agent Skills 規格。** 名稱只用小寫英文、數字和連字號，並與資料夾同名；skill 自己的檔案只從 `SKILL.md` 往下一層。招卡是專案資料，放 skill 外的 `knowledge/`。
9. **每本書用獨立 git。** `novel-desk` 的 `.gitignore` 忽略 `books/`，每本書在自己的資料夾 `git init`，並要有自己的備份。不用 submodule。測試用的書也照這樣做。
10. **`novel-desk` 完成後是獨立 repo，不再回頭看本 repo。** 搬過去的內容不留任何參考路徑，要自足。
11. **先為 `novel-desk` 重新產生「新技巧知識庫」，再寫進 skill。** 舊 `技巧知識庫/` 有寫死的數字等無用內容，萃取角度也和新需求不同。寫新庫時依需要回 `Data/` 看原文。
12. **不做章表。** 沒有任何功能會用到字數和對白數；想知道章節內容或長度時，直接問或用 `/search`。作者實際寫到幾十章，發現想一眼看完全書時再考慮。作者定案（2026-11-03）。

## 功能

名稱除了 `change-angle`、`draft`（落筆，Claude 定）、`search`（問全書）、`check`（幫我看，作者定案，2026-11-02）和 `passage`（局部操作，作者定案，2026-11-02）都還沒定。

| 動作 | 內容 |
|---|---|
| 討論 | 世界觀、角色、劇情共用一個入口。預設自由回答，只讀提到的卡片。作者說「記下來」才寫檔，寫之前先給作者看 |
| `/change-angle` | 討論中叫出的動作，換一種方式再答 |
| `/check`（幫我看） | 討論中叫出的動作，用問句檢查作者覺得怪的內容。每處寫原句、依據、問句；預設不給改法，作者問「怎麼改」才給（作者定案，2026-11-02）。各領域共用一個 skill，只能手動觸發 |
| 落筆 | 組出 prompt 給作者過目，開乾淨對話送出；可出 3–5 稿並排，標出重複的梗，由作者挑句拼接 |
| `/passage`（局部操作） | 作者貼上段落或給章號加起訖句，後面接擴寫、補感官、改對白、提三個下一步或自訂指令，共用一個 skill。改文字預設給 3 版。用 `context: fork` 執行，看不到對話；結果回到主對話，作者選了才照抄寫入。只能手動觸發。作者定案（2026-11-02） |
| `/search`（問全書） | 例如「他第 3 章傷哪隻手」「截至第 20 章他知道了嗎」「哪些伏筆沒收」。先定範圍（章節、章節區間、截至第 N 章、來源）再找；回答附章號和原句，引文用腳本核對，分清「沒有」和「沒搜到」。可自動觸發。作者定案（2026-11-02）。業界對照：閱文作家助手有同名的問全書和掛章節 |

**建議順序：** 先做 `/change-angle`（幾乎不依賴骨架），再定骨架，然後做落筆和問全書。

### skill 結構

**原則：** skill 固定邊界，中間由 AI 自組，每個 skill 只放它需要的檔案。每次都要一樣或做錯代價高的部分才固定，可靠度要求最高的寫成腳本；需要判斷的交給 AI。

```
novel-desk/
├── .claude/skills/
│   ├── change-angle/SKILL.md   # 只寫怎麼用
│   └── ...                     # 有分支才加 references/，有固定組裝才加 templates/、scripts/
└── knowledge/
    ├── 索引.md                 # 每招一行，用症狀寫，依領域分組
    └── cards/                  # 一招一檔，不分子資料夾
        └── 核心謊言.md
```

| 層 | 內容 | 何時進 context |
|---|---|---|
| 1 | 名稱和描述 | 手動觸發的 skill 不常駐（`disable-model-invocation: true`） |
| 2 | `SKILL.md` | 觸發時 |
| 3 | 索引 | 觸發後 |
| 4 | 招卡，只讀 1–2 張 | 選定招之後 |

不用多層樹或向量搜尋：招卡數量讀索引就夠，每多一層就多一次走錯路的機會。作者叫得出招名或關鍵詞時，直接搜尋 `knowledge/`。AI 把卡片當材料，不必照步驟。對話要從 `novel-desk` 根目錄開。

招卡不標出處，「再深入」就找不到原文，所以不設原文層，`Data/` 不帶到新專案。招卡要寫得夠完整。精煉時仍要回頭看 `novelAI/Data/`。

**運作方式：** AI 判斷領域和狀況，選 1–2 招直接給 2–3 個具體候選，並說用了哪招。不評分、不填表、不落檔。作者可以說「換一招」或要它列出全部。沒有合適的招就直說，照自己的想法回答；信心低也算沒有合適的招（測試中 agent 傾向硬選）。不主動表態，作者問了才說。

**為什麼只有一份索引：** 原本分發想和檢查兩份，測試發現會把對的卡隔開，例如作者嫌台詞沒演出虛偽，要的卡在另一份。合併後選招明顯變好，也沒有造成硬套。動作只決定輸出形式：`/change-angle` 給候選，幫我看給問句和可疑處。作者定案（2026-11-02）。

不做自動路由：舊實驗的路由佔總成本 85%，門牌會寫錯，也會漏抓。

### 精煉規則

- **回頭看 `Data/` 原文。** 知識庫有提煉失真。例如原文是「猜中會不屑、猜不到會不服、猜對一半會驚喜」，入庫後只剩「別被輕易猜中」。部分招數只存在於 `Data/`。
- **保留具體例子**，卡片不寫「必須」，也不寫評分標準。
- **一招一卡。** 已知重複：連問法（H2／選題二）、主題三角（C1／主題題旨四）、謎三角（D2／伏筆三）、限制與代價（E1／世界觀八）、幕尾停止點（F2／戲劇張力二）。完整清單要逐招讀過才能確定。
- **用量建議改成文字描述**，例如「一章 2–3 處」，否則可能被當配額執行。

## 資料夾骨架

以 `novel-desk/README.md` 為準。比原提案多了 `CLAUDE.md` 和 `drafts/`：落筆的落選稿如果放進 `chapters/`，問全書會把沒採用的劇情當成事實。

作者定案：資料夾名固定用英文，避免路徑出錯；檔名可以用中文，書名、角色名和主題照作者的叫法。

```
novel-desk/
├── .gitignore             # books/
├── .claude/skills/        # 第一個 skill 建立時才出現
├── CLAUDE.md              # 引入 README，動作定案後再寫行為
├── README.md              # 一頁存放慣例，取代結構定義
└── books/<書名>/           # 獨立 git
    ├── raw/               # 隨手丟素材，沒有格式
    ├── 摘要.md            # 一頁：主線、題旨、結局、基調
    ├── cards/
    │   ├── characters/<名>.md
    │   ├── world/<主題>.md  # 道具、地點也放這裡
    │   └── hidden/<名>.md   # 水下
    ├── outline/           # 總綱.md、arc01.md…
    ├── beats/arc01.md     # 幕綱
    ├── samples/           # 範文：作者挑的人類片段
    ├── drafts/ch0001/     # 落筆的 prompt 和各稿
    ├── chapters/ch0001.md # 正文定稿
    └── 筆記.md            # 決定和被否決的想法，一句一條
```

固定格式只留兩處，其他自由書寫，沒有 lint：

```yaml
# 卡片開頭
---
別名: [塔主, 白袖先生]
---
# 章節開頭
---
摘要: 林澈發現墨斑洗不掉，被老抄寫員瞥見。
POV: 林澈
---
```

舊 `書本模板/` 的處理：

| 舊內容 | 處理 |
|---|---|
| `.ai.md`、`參照/`、`幕綱/_順序.md` | 刪 |
| `物件/` | 刪，道具併入世界觀，禁令不保留 |
| `風格/` | 刪，改成 `samples/` |
| raw、摘要、大綱、幕綱、正文、角色、世界觀 | 留 |

**搜尋需求：** 一章一檔、檔名帶章號、卡片有別名、每章一句摘要。搜不到關鍵字的問題先從摘要定位再讀章。

## 水下（待確認）

還沒揭露、AI 提前知道就可能寫壞的真相，放 `cards/hidden/`。業界有對應做法（Novelcrafter `never include`、oh-story「作者真相／讀者已知」、馬良框架），「水下」這個名字和獨立資料夾則是本專案自己的。

| 動作 | 能不能看 |
|---|---|
| 討論 | 能 |
| 問全書 | 作者明說才查，並標明來自水下（作者定案，2026-11-02） |
| 幫我看 | 作者明說才查，並標明來自水下；讀過就提醒寫稿要開新對話（作者定案，2026-11-02） |
| 落筆包 | 不能，除非作者親手寫進事件 |
| 局部操作 | 不能，在看不到對話的 fork 執行（作者定案，2026-11-02） |

- 埋伏筆時，事件只寫現象和外在行為，不寫原因。
- 揭曉那章由作者把真相寫進事件；之後併進公開卡片，刪除水下那支檔。
- 只有落筆包會跳過這個資料夾，作者自己寫進卡片或事件一樣會洩漏，所以送出前要過目。
- 真相已揭給讀者、只有主角不知道時，移回公開設定，並在事件註明。
- **同一個對話討論完再改段落的漏洞：** 作者定案（2026-11-02）用 `context: fork` 補。fork 看不到對話，所以「照剛才說的」不會生效，要把要點寫進指令。主對話讀過水下或談過真相時，作者要它動筆，它會請作者打 `/passage`，作者堅持才寫。不讀 `cards/hidden/` 靠的是指示，不是工具限制，測試見 `docs/實驗/局部操作測試/01-結果.md`。
