## 已定案

1. **放棄全自動。** 以人使用、AI 輔助為主。功能範圍是討論世界觀、輔助建構角色、建立大綱與幕綱、寫內文。
2. **方法論不預設載入。** AI 先自由回答，作者不滿意才主動觸發招數。
3. **不測招數是否勝過自由回答。** 會觸發就代表自由回答不夠，招數只是再試一種方式。
4. **不做平時同步。** 原本的主要用途是忘記前情時查角色變化，改由搜尋取代，前提是資料好搜。只同步搜到的部分屬於低優先 bonus。
5. **不做用程式硬算的統計與門檻。**
6. **上架與題材類需求目前不做：** 數值帳、起名、書名簡介、拆書、敏感詞、版本快照作為申訴證據。
7. **知識庫要精煉、結構化、去重，取用時走 progressive disclosure。**
8. **skill 遵守 Agent Skills 規格。** 名稱只用小寫英文、數字和連字號，並與資料夾同名；skill 自己的檔案只從 `SKILL.md` 往下一層。招卡是專案資料，放 skill 外的 `knowledge/`。
9. **每本書用獨立 git。** `novel-desk` 的 `.gitignore` 忽略 `books/`，每本書在自己的資料夾 `git init`，並要有自己的備份。不用 submodule。測試用的書也照這樣做。
10. **`novel-desk` 完成後是獨立 repo，不再回頭看本 repo。** 搬過去的內容不留任何參考路徑，要自足。
11. **先為 `novel-desk` 重新產生「新技巧知識庫」，再寫進 skill。** 舊 `技巧知識庫/` 有寫死的數字等無用內容，萃取角度也和新需求不同。寫新庫時依需要回 `Data/` 看原文。
12. **不做章表。** 沒有任何功能會用到字數和對白數；想知道章節內容或長度時，直接問或用 `/search`。作者實際寫到幾十章，發現想一眼看完全書時再考慮。作者定案（2026-11-03）。
13. **敘事層級的名稱**（作者定案，2026-11-09）：故事弧（story arc）由場景（scene）組成，場景由節拍（beat）組成；章（chapter）是正文的切分，由一到多個場景組成，要有一個主要高點。場景＝局勢改變一次（開頭和結尾的處境不同）；節拍＝角色碰壁後換一次做法，採 McKee 的定義，同一種來回重複幾次仍是同一個節拍。取代之前討論用的「幕」（一般用法指 act，AI 和搜尋會誤讀）和「步」。故事弧之間的起伏在場景層決定，快慢在節拍層決定。理由和資料見 `docs/實驗/第一章重寫/07-幕與步-跨媒介整理.md`；06、07 和這份文件較早的段落仍寫「幕／步」，是當時的用詞。
14. **拆解流程用混合做法**（作者定案，2026-11-09）：故事弧拆場景在對話裡討論，AI 被要求時才提候選拆法；場景拆節拍由 `/draft` 動筆前的「排章」自動產生，作者過目，作者特別在意的場景（例如高點）可以先在對話裡談。`/draft` 排章時決定哪幾個場景組成這一章、要不要讓場景跨章（例如在高點前切開做章尾鉤子）。
15. **定案用 `/settle`**（作者定案，2026-11-09）：討論結果要寫進正式區時打 `/settle`。它讀對應層級的注意事項清單、檢查、把問題列給作者，作者決定後才寫入。注意事項是「每次都該成立的條件」，和招卡（卡住時換一種想法）分開：放在 `knowledge/checks/`，每層最多五條，場景層由 `/settle` 讀，節拍層由 `/draft` 排章讀。招卡照舊給 `/check`、`/change-angle`。
16. **知識的入口**（2026-11-09）：知識都放在 `knowledge/`，由 skill 叫出來；`CLAUDE.md` 只放短規則，不放知識。

| 動作 | 內容 |
|---|---|

| `/search`（問全書） | 例如「他第 3 章傷哪隻手」「截至第 20 章他知道了嗎」「哪些伏筆沒收」。先定範圍（章節、章節區間、截至第 N 章、來源）再找；回答附章號和原句，引文用腳本核對，分清「沒有」和「沒搜到」。可自動觸發。作者定案（2026-11-02）。業界對照：閱文作家助手有同名的問全書和掛章節 |

### skill 結構

**原則：** skill 固定邊界，中間由 AI 自組，每個 skill 只放它需要的檔案。每次都要一樣或做錯代價高的部分才固定，可靠度要求最高的寫成腳本；需要判斷的交給 AI。

```
novel-desk/
├── .claude/skills/
│   ├── change-angle/SKILL.md   # 只寫怎麼用
│   └── ...                     # 有分支才加 references/，有固定組裝才加 templates/、scripts/
└── knowledge/
    ├── 索引.md                 # 每招一行，用症狀寫，依領域分組
    └── cards/                  # 一招一檔，不分子資料夾
        └── 核心謊言.md
```

| 層 | 內容 | 何時進 context |
|---|---|---|
| 1 | 名稱和描述 | 手動觸發的 skill 不常駐（`disable-model-invocation: true`） |
| 2 | `SKILL.md` | 觸發時 |
| 3 | 索引 | 觸發後 |
| 4 | 招卡，只讀 1–2 張 | 選定招之後 |

不用多層樹或向量搜尋：招卡數量讀索引就夠，每多一層就多一次走錯路的機會。作者叫得出招名或關鍵詞時，直接搜尋 `knowledge/`。AI 把卡片當材料，不必照步驟。對話要從 `novel-desk` 根目錄開。

招卡不標出處，「再深入」就找不到原文，所以不設原文層，`Data/` 不帶到新專案。招卡要寫得夠完整。精煉時仍要回頭看 `novelAI/Data/`。

**運作方式：** AI 判斷領域和狀況，選 1–2 招直接給 2–3 個具體候選，並說用了哪招。不評分、不填表、不落檔。作者可以說「換一招」或要它列出全部。沒有合適的招就直說，照自己的想法回答；信心低也算沒有合適的招（測試中 agent 傾向硬選）。不主動表態，作者問了才說。

**為什麼只有一份索引：** 原本分發想和檢查兩份，測試發現會把對的卡隔開，例如作者嫌台詞沒演出虛偽，要的卡在另一份。合併後選招明顯變好，也沒有造成硬套。動作只決定輸出形式：`/change-angle` 給候選，幫我看給問句和可疑處。作者定案（2026-11-02）。

不做自動路由：舊實驗的路由佔總成本 85%，門牌會寫錯，也會漏抓。

### 招卡格式

欄位是適用、吃、做、吐、例；`限界` 只在該卡有特殊限制時才寫。見 `docs/新技巧知識庫/cards/`。

測試顯示卡片的作用主要在 `吐`，`做` 只留 AI 自己想不到的內容，不列清單。

作者定案：招卡不標出處。

### 精煉規則

- **回頭看 `Data/` 原文。** 知識庫有提煉失真。例如原文是「猜中會不屑、猜不到會不服、猜對一半會驚喜」，入庫後只剩「別被輕易猜中」。部分招數只存在於 `Data/`。
- **保留具體例子**，卡片不寫「必須」，也不寫評分標準。
- **一招一卡。** 已知重複：連問法（H2／選題二）、主題三角（C1／主題題旨四）、謎三角（D2／伏筆三）、限制與代價（E1／世界觀八）、幕尾停止點（F2／戲劇張力二）。完整清單要逐招讀過才能確定。
- **用量建議改成文字描述**，例如「一章 2–3 處」，否則可能被當配額執行。

## 水下

**2026-11-11 改版（作者定案）：真相可以寫在任何地方，`cards/hidden/` 改成清單。** 之前的做法（場景表和卡片只寫現象、真相拆到 `cards/hidden/`、主 agent 只當濾網、`/passage` 不讀水下）已取代。

水下是讀者還不知道的事。摘要、大綱、場景表、角色卡、世界觀卡都照實寫真相。`cards/hidden/` 是「讀者還不知道的事」清單，一件事一條：

```
妹妹是陸辛分出去的精神體。
揭曉：arc03「入職檢測」。讀者看懂，陸辛自己還半信半疑。
伏筆：arc02「湖邊」儀器在妹妹旁邊沒反應；arc02「紅色潮水」牽手後有了她的身手。
```

- **揭曉和伏筆記到場景**（故事弧加場景小標題），不記章號，也不記場景編號。章號太容易變，場景排了比較不會動（作者）。章號只留在場景表，選填。
- **不用「已揭露」的是否標籤。** 算不算水下要看正在寫的地方在揭曉場景之前還是之後；回頭改前面的章時，已揭曉的事對那一段仍是水下。所以揭曉後條目留著，不刪，也不用把真相併回卡片。
- 還沒排揭曉就留空，代表寫到哪裡都不能說。只揭給讀者、角色還不知道時，寫在揭曉那一行。

| 動作 | 怎麼用 |
|---|---|
| `/settle` | 真相照作者說的寫，不拆、不另給拆過的版本。只顧清單對得上：有新的水下問要不要加一條；場景揭曉了清單上的事問要不要填揭曉；改了場景名就跟著改清單 |
| `/draft`（組 prompt 的主 agent） | 讀清單，每條拿揭曉場景和這一章比。之前揭曉：當已知設定。這一章揭曉：寫手要知道，把「揭曉前不能出現的事」寫成具體的事，並查稱呼和角色段有沒有先洩。之後揭曉或沒排：真相不進 prompt，也不寫「不要揭露某事」；場景表安排的伏筆只寫現象。伏筆埋在哪仍由場景表決定，主 agent 不自己加 |
| `/passage` | 每次讀清單和場景表，判斷段落在揭曉之前或之後；還沒揭曉的事不寫出來、不暗示，原有的伏筆不加重。回答多一項「碰到水下」 |
| `/search`、`/check` | 查計畫來源時一起讀清單，引到還沒揭曉的事標【水下】；「讀者知道了嗎」只算正文。不再提醒「讀過水下要開新對話」 |
| 主對話直接寫或改正文 | 先讀清單，照揭曉位置避開 |

**為什麼改：**

- `/draft` 的寫手本來就看不到場景表和卡片，只看得到主 agent 改寫過的 prompt，而主 agent 讀水下。限制場景表沒有保護到東西，卻讓作者要「寫手知道這層」時沒地方寫（settle 測試案例 B），伏筆也得拆兩處記。
- 舊規則真正保護的是 `/passage`（寫手自己讀卡片）。作者判斷：為一個小範圍的擴寫功能去限制世界觀、角色、大綱、場景，是沒必要的複雜；擴寫只動一小段，明說哪些是水下它就避得開，不像寫整章容易洩。
- 排章測試的破梗（S403）顯示「主 agent 只當濾網」太嚴：它看出哪裡會洩，卻沒有路寫進 prompt。
- settle 測試的「照寫照哪一版」「揭曉要按條刪」兩個問題跟著消失：只剩一版，也不用刪。
