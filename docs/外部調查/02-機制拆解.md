# 02 · 機制拆解

**這支檔回答**：那些工具的關鍵機制**具體怎麼實作**？摘要鏈裝了什麼、偵測式注入的組裝順序是什麼、狀態怎麼掛、伏筆存哪、同類的 skill 包長什麼樣？以及使用者踩到了什麼雷？

以下五個機制按「可移植性」排序，前三個有完整規格可直接抄。

---

## 機制一：摘要鏈（storySoFar）

**這是長篇 AI 寫作的記憶本體。** Novelcrafter 把它做成 prompt 函式：

- `storySoFar` — 回傳當前位置**之前**所有場景的 summary（不給參數就是全部）
- `storyToCome` — 回傳當前位置**之後**的 summary
- `textSoFar` / `textToCome` — 同樣範圍，但是全文而非摘要

### 關鍵規格

- **場景摘要在系統 prompt 裡被壓到 80 字（words）。**
- 可裁剪：`takeLast()` 只取最近 3 場、按 Act 過濾、**按 POV 過濾**（角色條目會去找該 POV 的所有場景，只用那些摘要）。
- 導航函式讓「上一個同 POV 的場景」變成一次查詢：`scene.previousSamePOV` / `scene.nextSamePOV`、`nextBeat` / `previousBeat`。
- 每一層都有 `.summary` 與 `.fullText`：`act.summary`／`chapter.summary`／`scene.summary`。

### 形狀上最重要的一點

**摘要是寫作單位自帶的一欄（`scene.summary`），不是另外一支要同步的檔。** 它跟正文住在同一個物件裡，所以不存在「摘要過期了沒人知道」這個問題類別。

### 旁證

業界對 AI 長篇的共識做法是：把前一段的 micro-summary 放進 prompt，是防止「敘事重置」（AI 忘記前面發生什麼、重新開場）的主要手段。

## 機制二：偵測式注入

**Novelcrafter 組裝 codex context 的完整順序**（官方文件逐條列出）：

1. beat／chat 訊息內 **＋ beat 之前的正文中**，所有被偵測到的 mentions
2. 手動掛在該場景上的 references
3. **POV 條目**（若前面沒被提及）
4. 所有 **global 條目**
5. 上述 1–4 的 **related child 條目**
6. **濾掉沒有描述／沒有內文的條目**

組裝完才排序：**global 優先 → 依型別 → 字母序**。所以**你在正文裡提及的順序不影響結果**。

### 四檔開關（每條條目各自設定）

| 設定 | 行為 |
|---|---|
| `always include` | 一律送，且排在最前面 |
| `include when detected` | **預設**：名字出現才送 |
| `don't include when detected` | 偵測到也不送，但可手動掛或經由 relations 帶進來 |
| `never include` | 永不送——**官方指定用途是劇透與私人筆記** |

### 偵測本身

靠 name ＋ aliases 比對，三個調節鈕：

- **auto-pluralization**（英文專用：`Goblins` 命中 `Goblin`）
- **case-sensitive matching**（區分角色名 `Red` 與顏色 `red`）
- **exclusion list**（避免 `will` 這種常用詞被當成人名）

### 條目長度的官方指南

| 長度 | 用在 |
|---|---|
| 1–3 句 | 次要角色、背景地點、簡單物品——**壓低 token** |
| 3–4 段 | 主要角色、關鍵地點、核心概念 |
| 更長／有結構 | 種族、宗教、複雜體系這類必須前後一致的 |

配套規則：

- **外觀細節移到 notes 區**——因為 **AI 會一直複讀**你給的外貌描述。
- 不要放劇透（會影響前期正文生成）。
- 不要重複別條目已有的資訊——**用 relations 代替**。
- 官方原話：「便宜／小 context 的模型會死抓（cling to）你給的資料。」
- 「從能滿足需求的最小條目開始。」

### 成本現實

BYOK 用戶回報月費 **$20–$100+**，主因就是每次請求把 codex 塞進 prompt。官方給的省法：只掛關鍵條目、**替長條目另建一個精簡版專供場景掛載**、只需要一個小細節時直接寫進 beat 而不是掛整條。

### 附帶發現：它有一整套查詢 DSL

`codex.get()`／`codex.all()`／`codex.characters`／`codex.isCharacter()`／`codex.hasTag()`／`codex.hasDetail()`／`codex.inCategory()`／`codex.isRelatedTo()`／`withRelations()`／`scene.references`／`scene.hasMention()`／`pov.isFirstPerson`／`takeFirst()`／`without()`／`ifs()`／`join()`／`asList()`／`asXml()`……近百個函式。

**這等同於本系統的「投影查詢語言」，差別在於：它查的是一個簡單資料模型，而不是一堆被 lint 守著的檔。**

## 機制三：progression（角色／物件狀態隨章變化）

這是 Novelcrafter 對「狀態隨章節變化」的完整答案，規格小到可以一段話說完：

1. 在 Write 介面的新行打 `/`，選 codex progression
2. 綁定一個 codex entry
3. （可選）再綁定該條目底下的某個 **detail**——官方 recipe 就是建一個叫 `character arc` 的 detail
4. 選模式：**`addition`**（角色打了個耳洞，其餘不變／預設）或 **`replacement`**（原描述作廢，但不重寫整條）
5. 寫一行自由文字

**效果只有一個：AI 只在該場景（含）之後看得到這行；回頭寫前面的場景時，它不在 context 裡。**

### 配套視圖：Matrix

Plan 介面的三種視圖之一（官方稱它是「supercharged spreadsheet」）：**codex entry × scene 的網格**。可以看角色／地點／副線出現在哪些場景、progression 落在哪、跟其他大事件的相對位置，還能一鍵改某場景的 POV。

### 官方 recipe 的一句話

> 「把角色旅程的 at-a-glance 摘要放在一個地方，你才看得出來自己是不是偏航了，或者某個關鍵轉折發生時**根本沒有你原本打算給的鋪墊或邏輯**。」

而且 recipe 明說：**不用 AI 也值得做這件事。**

### 沒有的東西

沒有維度、沒有集合運算語法、沒有 lint、沒有專用投影工具。就是「一行自由文字 ＋ 綁定 ＋ 生效點 ＋ add/replace」。

## 機制四：伏筆的五種存法

| 做法 | 資料模型 | 誰在用 |
|---|---|---|
| 三格試算表 | `線索 / 埋在哪章 / 對應的 payoff` | 作者社群通用慣例 |
| 一條 plotline | 卡片落在埋與收的位置，**中間空著一眼看得出來**；跨書伏筆進 Series View | Plottr |
| subplot 型 codex 條目＋progression | 在 Matrix view 看每個場景上該副線的推進格 | Novelcrafter |
| 正文內嵌標記 | 「一鍵標記伏筆、回收線」，配對就是全部的資料模型 | 筆落寫作 |
| **事後 AI 掃全文** | **不維護任何檔**，掃出伏筆分佈圖＋回收提示 | 閱文妙筆、sumeru 的 review 階段 |

**共同點：伏筆的資料模型只有「埋在哪／收在哪／收了沒」三格，而且它不需要跟設定檔同步。** 它是一個獨立的、可以事後重建的清單。

## 機制五：同儕系統（同樣是 markdown ＋ Claude Code skill 包）

### `worldwonderer/oh-story-claudecode`

```
{書名}/
├── 设定/
│   ├── 世界观/          # 依主題分檔
│   ├── 角色/            # 一角色一檔
│   ├── 势力/            # 一組織一檔
│   ├── 关系.md
│   └── 题材定位.md
├── 大纲/
│   ├── 大纲.md          # 卷級結構
│   ├── 卷纲_第一卷.md   # 節奏＋情緒弧＋角色弧＋伏筆＋反轉
│   └── 细纲_第001章.md  # 梗概＋多線事件＋人物出場序＋鉤子
├── 正文/ 第001章_章名.md
├── 对标/{對標書名}/ 原文/ 角色/ 剧情/ 设定/ 文风.md 拆文报告.md
├── 追踪/
│   ├── _tracking-state.json   # ★ 唯一結構化狀態
│   ├── 上下文.md               # 派生：固定 7 欄、≤12KB
│   ├── 逐章记录/               # 派生
│   ├── 角色状态/{角色}.md      # 派生：核心角色快照
│   ├── 伏笔.md                 # 派生：伏筆當前視圖
│   └── 时间线/{作者真相.md, 读者已知.md}   # 派生
└── 参考资料/
```

**架構要點：**

- **`_tracking-state.json` 是唯一的結構化真相**，`追踪/` 底下其餘全部是派生。
- 派生由**確定性腳本 `tracking_commit.py`** 在每章寫完後跑，序列化出上述檔案。
- **時間線刻意分兩份：`作者真相.md` vs `读者已知.md`**——與本系統 `水下.md` 是同一個需求。
- README 裡留著優化紀錄：**「日更每章必读从五个文件收缩到三项」**（上下文卡／角色狀態／時間線）。

13 支 skill：setup／router／long-write／long-analyze／long-scan／short-write／short-analyze／short-scan／**deslop（去 AI 味）**／import（把既有小說反解成專案結構）／review／cover／browser-cdp。

#### 續寫狀態卡 `上下文.md` 的固定 7 節（實檔逐節取樣）

檔頭一行：`> 状态修订：0。截至当前章的续写状态卡，只放下一章真正需要的连续性状态。`

| # | 節 | 實檔內容範例 |
|---|---|---|
| 1 | `## 当前位置` | `- 当前章：第20章` / `- 卷：第一卷·军宣整顿（候选）（始于第1章）` |
| 2 | `## 长期约束` | `- 军宣爽点必须通过作品效果、传播数据和围观反应链兑现，不能只靠系统播报。` |
| 3 | `## 核心角色状态` | `- 江晨｜火箭军文工团宣传兵；军宣顶流创作者｜《如愿》点击破亿并获官方认证，声望到达新高点` |
| 4 | `## 活跃伏笔` | `- F016｜钟嘉嘉并非普通军报实习生，她的军方家庭背景仍未完全公开｜埋第7章` |
| 5 | `## 近三章速记` | `- 第18章｜《如愿》破千万并获官方媒体转发，吴伟封号且收到公诉通知。` |
| 6 | `## 下一章承诺` | `- 先补第21章细纲，再承接老兵邀请、新歌伴奏和钢琴能力。` |
| 7 | `## 连贯性风险` | `- 第21章尚无细纲，不能直接写正文。` / `- 第一卷卷界仍是候选方案，未确认前不要擅自开新卷。` |

**這七節的組成邏輯**（值得單獨看）：
- 2 是**不變的約束**（跨章恆真）
- 1／3／4 是**當下狀態**（角色、伏筆、位置）
- 5 是**短期記憶**（只有三章，不是全書摘要鏈）
- 6／7 是**前瞻**——**「下一章承諾」與「連貫性風險」這兩節市面上其他工具都沒有**，等於把「這一章不許寫錯的地方」直接寫進狀態卡

官方對保留什麼的判準原話：**「沒有它這一章就會寫錯的資訊」**。篩選分三類：當前狀態（相關角色最新的能力／關係／公眾形象）、歷史因果（與本章事件直接相連的伏筆源頭與前事）、世界約束（適用的規則／力量體系／社會結構／地理）。

#### `伏笔.md` 的欄位（實檔表頭逐字）

```
| ID | 内容 | 埋设章 | 计划回收章 | 状态 | 重要度 | 最近变更章 |
```

- **每個 ID 只保留一行當前狀態**，歷史變化去 `逐章记录/`
- 實檔範例：`| F016 | 钟嘉嘉并非普通军报实习生…… | 第7章 | — | 已埋 | 高 | 第20章 |`
- 容量上限 **≤3072 bytes**

#### `角色状态/{角色}.md` 的欄位（實檔逐字）

檔頭六個單行欄：`状态修订`／`截至章节`／`身份`／`位置`／`当前目标`／`身心状态`
四個列表節：`## 能力与资源`／`## 关键关系`／`## 已知信息`／`## 未结事项`

- **完整快照覆蓋，不是增量**：工具整份覆寫，角色的變化史在 `逐章记录/`，不在快照裡
- 目標 **≤4096 bytes**、硬上限 **8192 bytes**
- **靜態人設仍讀 `设定/角色/`**——快照只放會變的部分
- `逐章记录/第NNN章.md` 目標 ≤1536 bytes、硬上限 3072

#### 交易協定（`tracking_commit.py` 三模式）

寫手提交的是**語意交易**，不是直接編輯多支檔。

| 模式 | 行為 |
|---|---|
| `init` | 從 `初始化事务.json` 建初始狀態；**絕不覆蓋既有專案**；舊追蹤檔移進 `追踪/_旧追踪存档/` |
| `commit` | 讀當前狀態進記憶體 → 驗證並合併本章 delta → 渲染全部派生視圖並**檢查容量上限** → 寫章記錄與視圖 → **原子替換 `_tracking-state.json` 作為 commit point** |
| `check` | 只驗證：schema、檔名規範、位元組上限、**派生視圖與狀態逐位元組一致**。成功輸出 JSON，失敗只走 stderr |

**幾個設計決定值得抄：**

- **手改偵測靠 byte-for-byte 比對**，不是 hash 過期警告。偵測到不一致 → 提交 `mode=revision`（帶當前的 `expected_state_revision`）由工具**整份重建**。
- **`expected_state_revision` 是樂觀鎖**：構造交易前先跑 `check` 抄下 `state_revision`；狀態變過就得重讀重構。序列提交，一本書不允許並發 agent。
- **提交前的參照完整性檢查**跨角色／伏筆／時間線三軸。
- **活躍角色上限 6 人**——直接用配額控 context，不是靠勸。
- 寫檔失敗時 `_tracking-state.json` 停在前一個 revision，修好環境後重跑同一份交易即可（**同輸入同輸出，不做狀態機追蹤**）。

### `xindoo/sumeru`（須彌寫作）

7 支 skill：worldbuilder（統籌）／topic（選題）／outline／write／review／polish／finalize。

產物落在工作目錄（`选题策划报告.md`、`小说大纲_*.md`、`chapters/`、`剧情审查报告.md`、`publish/`），**中間資料全進隱藏的 `.sumeru/`**：`outline/chapter-outlines.json`、`review/fix-plan.json`、`write/original/`（修改前自動備份）。

**它最值得注意的一點：一致性完全是「審查階段」的事，不是平時維護的不變量。**

1. **全局審查**：時間線、設定一致性、衝突點分布、**伏筆回收狀態**
2. **細節審查**：逐章驗證字數、人物 OOC、**物品狀態**、伏筆設置（子 agent 並行）
3. **統一修復**：輕量修復直接改 `chapters/`，需重寫的章節產 `fix-plan.json`

### 馬良長篇框架（實操指南）

- 每 session **60K token 上限**，畫面上有即時消耗進度條
- **六類資源（設定／角色／懸念／大綱／卷綱／章綱）各自可切「完整 / 只給名字」兩檔**——官方講法是「按需裝配而非全量塞入」
- 三條明確禁令：
  1. 不要一次生成所有章綱——**過早鎖死後面的劇情**
  2. 不要把有可見性限制的資訊餵進去（不管 context 裝配怎麼設）
  3. 不要每次重述文風——綁到一個常駐 Persona
- 失效閾值回報：**2–4 萬字開始出現角色狀態矛盾**

## 踩雷回報（跨來源彙整）

### 1. recency bias 打敗設定卡 ★

角色卡寫綠眼睛，但最近三章的正文寫成褐色 → **AI 跟最近的、比重更大的 context 走**，設定卡在拉鋸中輸給正文。

> 推論：維護一份「與正文平行、但不是從正文抽出來的」事實表，注定會輸給正文。要嘛它是從正文抽出來的（可重算），要嘛它就是會被正文覆蓋。

### 2. Codex 的根本張力

條目太少 → AI 缺 context、輸出變差；條目全填 → 等於**把稿件裡已經有的東西手抄一遍**。

別家選擇停在「手抄」，沒有再加一層保證機制。本系統是在「手抄」上又加了重生＋lint＋新鮮度三層。

### 3. 設定成本本身就是勸退點

Novelcrafter 的公開評價是「powerful for fiction writers, **frustrating to set up**」。

### 4. 有人往反方向走

Novarrium 主打的是 **自動事實抽取 → 相關性加權注入 → 生成後驗證**，而不是要作者維護 story bible；宣稱對照組（ChatGPT／Sudowrite／NovelAI）在第 15 章前就出現一致性錯誤。**這是廠商自述，非獨立驗證**，但方向值得記：把一致性從「作者的維護義務」移成「系統的抽取與驗證動作」。

### 5. AI 長篇崩壞的三個根因（中文社群共識）

context 窗裝不下全書 ／ 記憶沒有外部錨點 ／ 風格缺少統一約束。
