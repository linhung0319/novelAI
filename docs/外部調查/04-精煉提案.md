# 04 · 精煉提案：寫作真正需要保存哪些檔案

**這支檔回答**：把 01–03 的外部資料對回**本 repo 的實測數字**之後，一本書應該保存哪些檔、每支檔多大、檔案結構要具備哪些性質。

**這是提案，不是決策。** 每一項都標了依據（實測／外部）。刪除類的每一項另標「它原本在解什麼問題、拿掉之後那個問題由誰接手」——**沒有接手人的就不提議刪**。

**日期**：2026-08-10。實測對象：`消失的密室`（已寫 4 章、8 個 arc 已下沉大綱、arc01 已拆幕綱）。

### 三個發現

**發現一：27:1，而且是在第 4 章就 27:1。**
這個比例本身不必然壞——一本 30 萬字的書寫完之後，同樣 568 KB 的支援檔會變成 0.3:1。**問題是這套系統的成本幾乎全是固定成本，而它壓在最需要動能的前段。** 分母成長得比分子慢，是因為寫一章正文之前要先載入 663,919 B（`CLAUDE.md` 自己的實測，其中 73.6% 與這本書無關）。

**發現二：`裁決流.md` 是 238,316 B ＝ 正文的 11.4 倍，而它從不進 `write` 的 context。**
211 筆裁決，**平均每筆 1,116 bytes**。這支檔的 schema 檔頭自己寫明：「理由欄可以寫長，它不會擠進 `write` 的 context」。
也就是說——**它的成本 100% 在生成端，0% 在載入端**。每一輪拍板，AI 要把「為什麼」寫成一千字的段落，寫完之後沒有任何一次寫作會讀到它。這是全系統最貴的一支檔，而且貴在一個沒有讀者的地方。

**發現三：設定層 16 個實體裡，11 個的 `.ai.md` 比它的源檔還大。**

| 實體 | 源 | `.ai.md` | 比 |
|---|---:|---:|---:|
| 角色/榮恩 | 1,249 | 5,967 | **4.78×** |
| 角色/麥朵 | 1,251 | 3,276 | 2.62× |
| 角色/莫莉 | 1,637 | 3,480 | 2.13× |
| 世界觀/權力與程序 | 1,801 | 3,593 | 2.00× |
| …（另 7 支 1.1–1.8×） | | | |
| 角色/哈利 | 7,415 | 4,498 | 0.61× |
| 世界觀/密室與繼承人 | 6,057 | 4,661 | 0.77× |

全層 70,531 B ＝ 設定層總體積的 **44%**。而依現行設計，這一層**只能有新表述、不得有新資訊**。
**一層被定義為「不含新資訊」的檔，佔了它所屬軸的四成體積，而且對一半以上的實體來說比它的源還大。**

### 對照組

`oh-story` 的「每章必讀」是三項：狀態卡 ≤12 KB、角色快照 ≤8 KB、伏筆表 ≤3 KB ＝ **≈23 KB，而且與書長無關**。
本系統的每章必讀是 663,919 B，**且隨書成長**。

## 二、判準：一支檔要活下來，必須說出「哪一次 prompt 會載入它」

四個可能的消費者：

| | 消費者 | 意思 |
|---|---|---|
| **P1** | 寫這一章（`write`／`revise`） | 進 prompt |
| **P2** | 決定下一章寫什麼（`organize`／`beat-sheet`／`expand`） | 進 prompt |
| **P3** | 事後審查（`*-test`） | 進 prompt，但**只在審查那一次** |
| **P4** | 作者自己翻閱 | 不進 prompt |

**測試句（借 oh-story 原話）：「沒有它，這一章就會寫錯。」**

由此得三條可執行的推論：

1. **只有 P3／P4 的檔，不必即時維護、不必 lint、可以事後重建。** 一致性檢查是**審查階段的一次掃描**，不是平時要守的不變量（sumeru 三階段、閱文妙筆全文掃）。
2. **只有寫者、沒有讀者的檔，成本是純損。** `裁決流.md` 是這一類的極端案例。
3. **派生檔只有在它比源檔小的時候才值得存在。** 壓縮型（正文 → 80 字摘要）留下，**展開型（一句設定 → 四象限分析）刪掉**——後者花 token 產出「源的新表述」，而 prompt 裡塞源檔本身更便宜也更準。

## 三、精煉後的檔案清單

```
<書名>/
├── raw/                                自由素材，零 schema、零 lint          （不動）
├── chapters/
│   └── chNNNN.md                       正文源 ＋ front-matter（摘要一句·POV·對應幕·錨·狀態）
├── story/
│   ├── 00-摘要.md                      一頁定位：主線·題旨·結局·取向·基調      ≤ 4 KB
│   ├── 大綱/arcNN.md                   每 arc 一檔                             ≤ 8 KB
│   ├── 幕綱/arcNN.md                   場景卡：synopsis·POV·角色·行動衝突結果  ≤ 16 KB
│   ├── 設定/
│   │   ├── 角色/<名>.md                自由散文（承重角色可目錄化）           ≤ 4 KB
│   │   │        └── <名>/水下.md       揭底前 write 拿不到                     ≤ 4 KB
│   │   ├── 世界觀/<主題>.md                                                    ≤ 4 KB
│   │   ├── 道具/<名>.md                （由 物件/ 的「是什麼」節搬來）         ≤ 2 KB
│   │   └── 風格.md                                                             ≤ 6 KB
│   ├── 約束.md                         「不得寫成什麼」全書單表                ≤ 8 KB
│   └── 續寫/
│       ├── 狀態.md                     七節狀態卡，每章重算、完整覆蓋          ≤ 12 KB
│       └── 伏筆.md                     ID·內容·埋設章·計畫回收·狀態·重要度    ≤ 3 KB
├── 參照/
│   ├── 待裁決.md                       四欄，作者拍板後刪列                    ≤ 4 KB
│   └── 就緒.md                         成熟度矩陣＋勾選清單                    ≤ 2 KB
└── notes/
    └── 決策日誌.md                     append-only，不進任何 prompt、無 lint
```

### 每章必讀的常數上限

| 載入項 | 上限 |
|---|---:|
| `00-摘要.md` | 4 KB |
| `設定/風格.md` | 6 KB |
| `續寫/狀態.md` | 12 KB |
| `續寫/伏筆.md`（只印本章相關列） | 3 KB |
| `約束.md`（全書恆真那節無條件印） | 8 KB |
| 該幕的幕綱切片 | ~2 KB |
| 偵測命中的設定條目（**活躍上限 6 條**） | 24 KB |
| **合計** | **≈ 59 KB，與書長無關** |

對比現行的 663,919 B：**約 1/11**，而且封頂。

> **這裡的關鍵不是數字，是「封頂」二字。** 上限要在**寫入時檢查、超了就寫入失敗**（oh-story 的做法），不是印個警告。現行只限行長，而行長限不住總量——`裁決流.md` 每一列都合法，合起來 238 KB。

### 逐項說明

**A. 成品層**

| 檔 | 消費者 | 說明 |
|---|---|---|
| `chapters/chNNNN.md` | P1 P4 | 正文源，不動 |
| **摘要改成 front-matter 的一欄** | P1 P2 | **不獨立成檔。** 外部通例是「摘要是寫作單位自帶的一欄（`scene.summary`），不是另一支要同步的檔」（機制一）。摘要與正文同居，**「摘要過期了沒人知道」這個問題類別直接消失**——不需要 hash、不需要 stale 標記、不需要 `derived-sync`。Novelcrafter 把它壓到 80 words，並讓它身兼 `storySoFar` 的本體 |

`chNNNN.ai.md` 因此整支併入 front-matter，欄位收成：`摘要`（一句）／`對應幕`／`POV`／`錨〔名〕`（正文釘死的數字·專名·道具語彙）／`狀態`。

> **`錨` 要保，六維狀態 delta 不保。** 理由是踩雷回報 ①：**「與正文平行、但不是從正文抽出來的事實表，注定會輸給正文」**。`錨` 合格——它就是從正文抽出來的；六維 delta ＋集合運算語法（`＋已知〔X〕`／`〔X〕→已知`）不合格，因為要回答「他現在會什麼」得跑 `fact-project` 重播全部歷史。**換成 oh-story 的做法：狀態卡完整快照覆蓋，變化史另有去處。** 快照直接就是答案，而「他是怎麼變成現在這樣的」這種歷史查詢，頻率遠低於「他現在是什麼樣」。

**B. 計畫層**

三層（摘要／大綱／幕綱）保留，**層與層之間不做同步檢查**——外部的三層大綱（大綱／卷綱／章綱）零同步，這一條不是外部偷懶，是因為**下層永遠比上層新，上層被下層推翻是正常工作流不是錯誤**。

`幕綱/arcNN.md` 是**全系統最該保的一支**：一句 synopsis ＋ POV ＋ 出場角色 ＋ 行動/衝突/結果，正好是 Scrivener 索引卡、Plottr scene card、Novelcrafter scene 三者的交集，而本系統的版本比三家都完整。

> **但幕綱要瘦身一個地方**：現行 `arc01.md` 的「不得發生」清單佔了 23 KB 的大半，其中**跨 arc 恆真的那些應該搬進 `約束.md`**（「不吐槽輕重順序」「不寫群像」「哈利的內心不得寫成感受」），**只有 arc 局部的留在幕綱**（「妙麗在本 arc 不登場」「本 arc 沒有第五個不求救的格子」）。判準：這條規則在 arc09 還成不成立。

**C. 設定層（一實體一檔、自由散文）**

外部三方一致：一實體一檔、內容自由散文、**唯一必要的結構欄是別名**。所以 front-matter 收成三欄：

```yaml
別名: [榮恩, 榮恩·衛斯理, 衛斯理]
載入: 偵測          # 常駐 | 偵測 | 不給
揭示層級: 檯面       # 檯面 | 水下
```

`載入` 三檔是 Novelcrafter 四檔開關的簡化（`always include` / `include when detected` / `never include`），**`不給` 那一檔就是現行的 `水下.md`**——這是三方獨立佐證的真需求（oh-story 分「作者真相／讀者已知」、Novelcrafter 官方指定 `never include` 用於劇透、馬良框架列為明確禁令）。**這個原創要保。**

配套（可直接抄，外部已驗證）：
- **條目長度分級**：次要角色／背景地點 1–3 句；主要角色／關鍵地點 3–4 段；種族·宗教·力量體系可更長有結構。
- **外觀細節移到單獨一節並標「不常駐」**——因為 AI 會一直複讀你給的外貌描述。
- **不要重複別條目已有的資訊，用關聯代替。**
- **exclusion list**：中文比英文更需要（單字名、常用詞人名）。

**刪 `.ai.md` 衍生層**（設定層 16 支）。理由三條：市面零例；實測 11/16 比源檔大；定義上不含新資訊。

> **這一刀會掉的東西是真的**：`哈利.ai.md` 的需求四象限逼出了「他的想要與他的需要不只是不同方向，追求前者會直接惡化後者」這句——那是分析結論，源檔裡沒有。
> **但正解不是保留這一層，是把結論回寫源檔。** 現行 `CLAUDE.md` 第二問的③類判準自己就是這麼寫的（「共創問答問出來的具體事實是③，正解是把結論回寫源檔一句話」）。差別在：**推導是一次性的，不該每次重生。** 遷移動作＝把 16 支 `.ai.md` 裡真正的③類內容手工併回源檔，然後整層刪除。

**D. 約束層 —— 本系統真正的差異化資產**

`約束.md` 一支表，收掉現行分散在 22 支 `物件/<名>.md` 的「不得寫成什麼」＋ 幕綱裡跨 arc 恆真的禁令：

```
| 約束名 | 不得寫成 | 綁定 | 生效自 | 解除於 |
```

**為什麼這一層值得保、值得 lint、值得單一寫入口**：市面上零個工具有事前的「不得寫成什麼」——最接近的只有 oh-story 的 `deslop`（事後去 AI 味）。**本系統把去 AI 味前移成了寫作前的可執行配額**，而實測那份清單（「不替看門人說情」「答案先給說明不給」「不得吐槽輕重順序」）正是這套系統寫出好正文的主要原因之一。**這是唯一一項我建議加碼而不是減碼的軸。**

**收成一支表的理由是 03 的核心推論**：12 支閘門的根源是**寫入口有 12 個**。約束軸現在有 22 個寫入口（22 支物件檔），收成 1 個之後，`object-lint` 從「守 22 支檔的 front-matter ＋ 表格」變成「守 1 支表 ＋ 一個位元組上限」。

物件檔的另一半（「是什麼／為什麼存在」，例如日記的外觀與功能）搬進 `設定/道具/<名>.md`——**它本來就是設定卡，只是住在約束軸裡**。

**E. 連續性層（每章必讀、常數大小）**

`續寫/狀態.md`，固定七節（oh-story 實檔逐節，這是全部外部資料裡最值得整套抄的一份）：

| # | 節 | 性質 |
|---|---|---|
| 1 | `## 當前位置` | 當下 |
| 2 | `## 長期約束` | 跨章恆真 |
| 3 | `## 核心角色狀態` | 當下（**只放會變的部分，靜態人設仍讀設定層**） |
| 4 | `## 活躍伏筆` | 當下 |
| 5 | `## 近三章速記` | 短期記憶（**三章，不是全書摘要鏈**） |
| 6 | `## 下一章承諾` | **前瞻** |
| 7 | `## 連貫性風險` | **前瞻** |

6／7 兩節市面其他工具都沒有——**它把「這一章不許寫錯的地方」寫進每章必讀的卡片，等於把審稿的一部分職責前移到寫作之前。** 這與本系統既有的 `*-test` 方向一致，但成本低得多。

`續寫/伏筆.md` 三格＋ID，硬上限 3 KB，每個 ID **只保留一行當前狀態**。伏筆的資料模型在全部五種外部做法裡都只有「埋在哪／收在哪／收了沒」，**而且它不需要跟設定檔同步**——它是一份可以事後從正文重建的獨立清單。

**F. 治理層 —— 降級，不刪除**

| 現行 | 提案 | 理由 |
|---|---|---|
| `story/參照/裁決流.md`（238 KB、211 筆、平均 1,116 B/筆、7 欄、`decision-lint`、`decision-project` 投影） | **移出 `story/` 到 `notes/決策日誌.md`**：一筆一列、**理由壓到一句 ≤80 字**、無 lint、無投影、不進任何 prompt | 成本 100% 在生成端。**但它的核心功能要保**：「被駁回的提案不會出現在任何產物裡，否則每隔幾輪就有人重新提議同一件事」——這是 **agent 協作特有的失效模式**，外部工具沒有這一層是因為它們沒有 agent，不是因為這個問題不存在。**要保的是清單，不是論文**：211 筆 × 80 字 ≈ 17 KB，仍然查得到「這件事裁決過沒有」 |
| `story/參照/待裁決.md`（4.5 KB） | **保，不動** | 便宜、有讀者（作者 P4 ＋ `sync`）。**別為了對稱砍它** |
| `story/參照/就緒.md`（1.4 KB） | **保，不動** | 同上 |

**G. 閘門**

12 支 → **4 支**：`約束.md`／`伏筆.md`／`狀態.md`（三者都有位元組硬上限，要在寫入時檢查）＋ `幕綱`（唯一仍被逐欄取值的強格式源）。

其餘八支的消失是**被動的**——`derived-sync validate`／`summary-lint`／`style-lint`／`char-lint`／`world-lint` 守的是 `.ai.md`，那一層不在了；`decision-lint` 守的是裁決流的七欄，那支檔降級成自由日誌了；`fact-lint` 守的是六維事實流，換成快照了；`object-lint` 從 22 支收成 1 支。

**投影工具（`*-lint --emit`／`structure-project`／`readiness`／`fact-refs`）全部保留並加碼。** 這是資產不是負債：外部零工具把索引落成檔，Novelcrafter 甚至把投影做成近百個函式的 DSL。**`fact-refs --anchor 〔名〕`（找下游正文還寫著舊值的地方）在外部完全沒有對應物，是真正的原創。**

## 四、「檔案結構需要什麼」——七個性質

檔案清單會隨書變，性質不會。這七條才是本提案的本體。

**1. 每章必讀的集合必須是常數，且上限在寫入時強制。**
超了就寫入失敗，不是印警告。**只限行長壓不住總量**——`裁決流.md` 的每一列都合法。

**2. 摘要與被摘要的東西同居一檔。**
一旦摘要是正文的 front-matter 而不是隔壁的檔，「摘要過期」這個問題類別就不存在，hash 新鮮度那一整套機制隨之失去對象。**這是整份提案裡投資報酬率最高的一個改動。**

**3. 一實體一檔 ＋ 別名欄 ＋ 三檔載入開關。**
別名是偵測式注入的鑰匙；`不給` 那一檔（＝現行 `水下.md`）有三方獨立外部佐證。

**4. 狀態用完整快照覆蓋，歷史另有去處。**
快照回答「現在」，日誌回答「怎麼變成現在的」。**不要用 delta ＋重播去回答「現在」**——那讓最高頻的查詢付最貴的代價。

**5. 每一軸只有一個寫入口。**
03 的核心推論：閘門的成本來自寫入口的數量，不是檔案的數量。約束軸 22→1 是本提案唯一真正動到這個結構的地方；**其餘軸是靠砍掉整層來減少寫入口，不是靠收窄**。

**6. 索引一律是投影，不落檔。**（現行已對，外部佐證，繼續）

**7. 一致性是審查階段的一次掃描，不是平時要守的不變量。**
`*-test` 系列該加碼；平時的 12 支閘門該減。**這一條是本提案能砍掉這麼多東西的總前提**——如果不接受「平時允許不一致、審查時一次抓」，前面每一刀都收不回來。

## 五、誠實的風險欄

**1. 27:1 這個數字會被過度解讀。**
它在第 4 章很難看，寫到第 100 章會變成 0.3:1。真正該引用的數字不是比例，是**「每章必讀 663,919 B 且無上限」**——那一項不會因為書變長而改善。

**2. 幕綱的「不得發生」清單砍不得。**
它佔 arc01 幕綱的大半體積，而它很可能是本系統正文品質高於外部工具的主因。本提案不砍它，只搬家（跨 arc 恆真的→`約束.md`）。**如果搬家過程中順手「精簡」它，這份提案的收益會被它造成的品質損失全部吃掉。**

**3. 刪 `.ai.md` 有一次性遷移成本，而那個成本必須先付。**
16 支檔裡確實有源檔沒有的分析結論。**先回寫源檔、再刪**；順序倒過來就是永久損失。

**4. 「降級裁決流」不等於「不再記錄為什麼」。**
差別只在**理由寫一句還是寫一千字**。若實測發現一句話版本導致同一件事被反覆重議，這一刀要退回去——但退回去的形式應該是「理由欄放寬到 300 字」，不是恢復 7 欄 ＋ lint ＋ 投影。

**5. 本提案沒有解決 03 指出的根本問題。**
`oh-story` 把守衛收成 1 支，靠的是**單一 JSON 真相 ＋ 語意交易單一寫入口 ＋ 提交時原子替換**。本提案只做到「砍層 ＋ 約束軸收單一寫入口」，仍然是多支 `.md` 各自可被直接寫。**如果將來要再減一個數量級，那一步是交易協定，不是繼續砍檔。**
