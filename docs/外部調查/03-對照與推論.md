# 03 · 對照與推論

**這支檔回答**：把外部做法對回現行系統，哪些該保留、哪些該要求它說出存在理由、哪些可以降級？

**這一支不是決策，是備選清單。** 每一項後面標了外部依據，方便日後逐項辯論。

---

## 一、最關鍵的一個架構對照

| | `oh-story-claudecode` | 本系統 |
|---|---|---|
| 真相 | 單一 `_tracking-state.json` | 多支 `.md` 源檔 |
| 派生者 | **確定性腳本** `tracking_commit.py` | **LLM 重生** `.ai.md` |
| 派生物尺寸 | **每支檔各有硬上限**（狀態卡 12KB／角色快照 4–8KB／伏筆表 3KB／章記錄 1.5–3KB），commit 時檢查、超了就失敗 | 不限（僅行長受限） |
| 手改偵測 | `check` 做**派生視圖 vs 狀態逐位元組比對** | hash 新鮮度 → stale 警告 |
| 保證手段 | **不需要 lint**——腳本輸出恆定 | **12 支 lint ＋ hash 新鮮度** |

### 推論

**12 支閘門的成本，根源不是「檔太多」，而是「派生者是 LLM」。**

LLM 派生會產生兩個確定性腳本不會有的問題，而現行系統的三層機制正好各對應一個：

| LLM 派生的問題 | 現行機制 | 若派生者換成程式 |
|---|---|---|
| 輸出格式不穩 | 12 支 lint | 不需要 |
| 派生物會偷偷長出新資訊（③類內容） | `derived-sync` 成長哨兵、`fact-lint` 純化三條 | 不需要 |
| 重生會吃掉手改 | `.ai.md` 副檔名約定 ＋ 「別改」訊號 | 仍需要（但只剩這一條） |

現行系統已經有的 `*-lint --emit`／`fact-project`／`structure-project`／`readiness` **正是確定性投影**，方向與 Novelcrafter 的 prompt DSL 一致，是資產不是負債。**該質疑的是 `.ai.md` 這一層 LLM 派生物，不是投影工具。**

### 但要補一個關鍵修正：他們沒有把 LLM 趕出去，只是把它關進一個窄口

看完交易協定後，上表「派生者＝確定性腳本」這句話要修正。實際的職責切法是：

| 誰做 | 做什麼 |
|---|---|
| **LLM** | 讀完本章正文後，構造一份**語意交易**（本章 delta：角色哪幾維變了、伏筆新增／推進哪幾條、時間線加什麼） |
| **程式** | 驗證 schema、檔名、**跨角色／伏筆／時間線的參照完整性**、容量上限 → 渲染全部派生視圖 → 原子替換狀態檔 |

也就是說：**狀態的內容仍然是 LLM 產的，但它只能從一個窄口進去，而那個窄口有一支驗證器。**

這比「派生者是程式 vs LLM」更接近問題核心。真正的差別是**閘門的數量與位置**：

| | oh-story | 本系統 |
|---|---|---|
| 閘門數 | **1 支**（`tracking_commit.py check`） | **12 支** |
| 位置 | 卡在**唯一的寫入口**（交易提交點） | 分散在 **12 種檔型**上 |
| 失敗時機 | commit 當下，交易被拒、狀態不動 | 事後掃描，壞內容已經落檔 |
| 併發 | 樂觀鎖 `expected_state_revision`，一本書序列提交 | 無此概念 |

**推論修正版**：本系統 12 支閘門的成本，根源是**寫入口有 12 個**（12 種檔型各自可被 LLM 或人直接寫），所以守衛只能分散部署、且只能事後掃描。oh-story 用「單一寫入口 ＋ 提交時驗證 ＋ 原子替換」把 12 支收成 1 支。

這一條比「砍掉 `.ai.md`」更根本，也更難做——但它解釋了為什麼砍檔本身不會讓成本線性下降。

## 二、保留（外部也有，且是核心）

| 元件 | 外部依據 |
|---|---|
| `chapters/chNNNN.md` ＋ **每章一句摘要** | 唯一被普遍結構化的劇情層欄位；Novelcrafter 把它壓到 80 字並當成 `storySoFar` 的本體 |
| **一實體一檔的自由散文卡**，唯一必要結構欄是**別名** | Obsidian／Novelcrafter／Campfire 全部如此；別名是偵測式注入的鑰匙 |
| 幕綱 ＝ 場景卡：一句 synopsis ＋ POV ＋ 出場角色 | Scrivener 索引卡、Plottr scene card、Novelcrafter scene 三者的交集 |
| 一份 open threads（伏筆）三格清單，或正文內嵌錨點 | 五種外部做法的共同資料模型 |
| **投影式查詢**（等同 Collections／Matrix／熱度圖） | 沒有工具把索引落檔；Novelcrafter 甚至做成完整 DSL。**應強化而非削減** |
| **`角色/<名>/水下.md`（`write` 拿不到）** | oh-story 分「作者真相／讀者已知」、Novelcrafter 有 `never include`、馬良框架把「不要餵有可見性限制的資訊」列為明確禁令。**三方獨立佐證，這是真需求** |

## 三、質疑（市面零例，要求逐項說出存在理由）

| 元件 | 質疑點 |
|---|---|
| `.ai.md` **LLM 衍生分析層**（摘要類除外） | 市面零個工具有。Sudowrite 生成完 Story Bible 那份就是源、人直接改。這一層是 token 成本的主要來源，而它的產出是「源的新表述」，不是新資訊 |
| hash 新鮮度 ＋ stale 標記 | 市面零例。作者慣例是 **draft first, document afterward**——先寫，寫完再記故事真的用到的事實 |
| **12 支 lint 閘門** | 前提是「LLM 逐欄取值」。若改成「整條卡片偵測式注入」（外部通例），前提消失，閘門一起消失 |
| `裁決流／待裁決／就緒` 治理三件套 | 市面零例。最接近的只是「working bible vs canon bible」兩份文件的手工慣例 |

**注意這裡的不對稱**：質疑不等於刪除。這四項都是為了解決真實存在的失效模式而長出來的（見上表「LLM 派生的問題」）。要判斷的是——**如果先砍掉 `.ai.md` 這一層，後面三項還剩多少存在理由？**

## 四、降級候選（外部也有，但做法輕得多）

| 現行 | 外部的輕量版 |
|---|---|
| `story/物件/<名>.md` 的「不得寫成什麼」規則表 | Novelcrafter 直接寫在條目描述／notes 裡，沒有獨立軸 |
| 逐章六維事實流 delta（`狀態`／`錨〔名〕`／集合語法） | progression 行：自由文字 ＋ 綁實體（可綁到某個 detail）＋ 生效場景 ＋ add/replace。**沒有維度、沒有集合語法** |
| 大綱 ↔ 幕綱 ↔ 正文之間的同步檢查 | 外部三層大綱（大綱／卷綱／章綱）**層與層之間零同步** |
| 12 支 lint 分散在 12 支 schema | sumeru 把一致性收成**審查階段的一次掃描**（全局→細節→統一修復），平時不維護 |

## 五、可直接移植的具體招數

這五項不需要改架構就能用，成本低、外部已驗證。

1. **條目長度分級**：1–3 句（次要）／3–4 段（主要）／更長（複雜體系）。配「**外觀細節移到 notes**，因為 AI 會複讀」。
2. **exclusion list**：常用詞當專名時的誤判防護（外部例子是英文的 `will`；中文更需要——單字名、常用詞人名）。
3. **「完整 / 只給名字」兩檔載入**（馬良框架）：六類資源各自可切。**這比 SKILL.md 裡寫「請只讀相關部分」這種規勸可執行得多**——現行 CLAUDE.md 已經指出規勸不會被執行、工具才會。
4. **每支派生檔各給一個位元組硬上限，並在寫入時檢查**（oh-story：狀態卡 12KB／角色快照目標 4KB 硬上限 8KB／伏筆表 3KB／章記錄目標 1.5KB 硬上限 3KB）。比只限行長更直接地控 token，而且**超了就寫入失敗**，不是印個警告。
5. **一致性 ＝ 審查階段的一次掃描**（sumeru 三階段、妙筆全文掃）而非平時維護的不變量——這對應現行系統已有的 `*-test` 系列 skill，可考慮把部分閘門的職責移過去。
6. **配額直接控 context**：oh-story 硬性限制**活躍角色最多 6 人**，超過就得先讓角色退場。比「請只載入相關角色」這種規勸可執行。
7. **狀態卡的「前瞻兩節」**：`## 下一章承诺` 與 `## 连贯性风险`。市面其他工具都沒有——它把「這一章不許寫錯的地方」直接寫進每章必讀的卡片，等於把審稿的部分職責前移到寫作前。
8. **完整快照覆蓋，而非增量 delta**：角色狀態卡整份覆寫、只放會變的部分，**靜態人設仍讀設定層**；變化史另有去處（`逐章记录/`）。與現行事實流的集合運算語法（`＋已知〔X〕`／`〔X〕→已知`）方向相反，值得對照——他們用「快照 ＋ 另一份歷史檔」換掉了「delta ＋ 重播」。
