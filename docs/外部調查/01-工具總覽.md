# 01 · 工具總覽

**這支檔回答**：9 個小說寫作工具各自把什麼東西結構化了、一致性靠什麼保證？哪些元件跨工具共有（＝大概必要），哪些元件市面上零個工具有（＝本系統的自造成本）？

---

## 一、資料模型對照

| 工具 | 結構化的東西 | 一致性怎麼保證 |
|---|---|---|
| **Scrivener** | binder 樹（part／chapter／scene）；每個 document 的 index card **synopsis**；**Label**（單選，通常＝Act 或 POV，binder 顯示為色標）；**Status**（草稿階段）；**Keywords**（多選：角色／地點／POV）；Collections（存起來的查詢視圖） | **完全不保證。** 零驗證、零同步。要查靠 Collections 與全文搜尋 |
| **Plottr** | scene card（含 POV／角色目標／衝突）排在 timeline(X) × plotline(Y) 的格子上；plotline 可以是主線／副線／角色弧線／伏筆線；顏色標記；Series View 存跨書伏筆 | 不保證。靠**視覺**——哪條 plotline 中間斷掉一眼看得出來 |
| **Campfire Writing** | 17 個模組：Characters／Manuscript／Locations／Maps／Research／Timeline／Arcs／Relationships／Encyclopedia／Magic／Species／Cultures／Items／Systems／Languages／Religions／Philosophies。角色卡有自訂欄位，角色頁**自動反查**「出現在哪些場景／去過哪些地點／與誰有關係／落在時間線何處」 | 不校驗，靠關聯自動反查。**模組是分開付費的**——多數人只開 2–3 個 |
| **Obsidian（各家小說 vault 範本）** | 資料夾：Manuscript／Characters／Worldbuilding（Locations、Magic、Factions、History）／Plot（Outline、Timeline）／Research／Templates。**一實體一檔**，靠 `[[連結]]` 反查。另一種分法是按「完成度」分：seeds／indices／longform／metatext | 不保證，靠 backlink |
| **Novelcrafter** | Codex 六型：character／location／object／lore／**subplot**／other。每條有 aliases、relations、categories、custom details、**progressions**。每個場景有 summary。Plan 介面有 grid／matrix 兩種視圖 | 不校驗，改用**偵測**：名稱與別名在正文中自動 underline、統計出場熱度圖、Matrix 網格看斷點 |
| **Sudowrite** | Story Bible 欄位鏈：Braindump → Synopsis → Genre/Style → Characters → Worldbuilding → Outline → Scenes | **不保證，也不回頭同步。** 單向瀑布，上層改了下層不會被標記過期 |
| **閱文作家助手·妙筆** | 章／卷、設定集、人物卡 | **AI 事後掃全文**：掃伏筆與線索 → 生成伏筆分佈圖＋回收提示；自動分析角色關係網 → 生成人物小傳、性格標籤、出場統計。官方口號是「查設定、找伏筆、算數值、理線索、挖角色」 |
| **筆落寫作** | 大綱／卷綱／章綱三層；**正文內一鍵標記伏筆與回收線**；卡片式角色與設定（頭像、圖集、名稱顏色、圖示） | 靠內嵌標記配對（埋 ↔ 收） |
| **橙瓜碼字** | 人物卡片（建卡後正文中該人名**高亮**）；大綱助手（劇情框架＋人物檔案＋世界觀設定）；隨機生成人名／地名／功法／秘籍；敏感詞檢測 | 不保證。高亮是提示不是校驗 |
| **蛙趣拼文** | 結構化設定（人物檔案、關係圖譜、地圖、物品屬性、伏筆）＋**「長篇穩定層」：角色狀態／情緒／實力／當前目標** | **程式自動維護**：故事狀態追蹤、因果鏈斷鏈檢測、生成前檢查（上一章是否存在、角色與世界觀是否完整）、寫作時 AI 自動檢索相關設定 |

## 二、跨工具的最小共同核心

出現在幾乎每一家 → 大概真的必要。

1. **稿件樹**：卷／章／場景的層級，順序可拖。
2. **每個場景／章一句 synopsis**——這是全部工具裡**唯一被普遍結構化的劇情層欄位**（Scrivener 索引卡、Plottr scene card、Novelcrafter scene summary、中國網文的章綱）。在 AI 工具裡它還身兼第二職：**它就是長篇的記憶**（見 `02-機制拆解.md` 機制一）。
3. **一實體一檔的卡片**（角色／地點／物品／設定），內容自由散文，唯一的結構欄位是**別名**。
   > Obsidian 社群把這條講得最清楚：角色資料夾要一角色一檔、不要一支合併檔，這樣 vault 裡任何一處提到該角色都能連回去。
4. **單字級 metadata，而不是檔案**：POV、狀態（草稿／已修／定稿）、標籤。這些在別家是「一格值」，不是一支檔、更不是一支帶 schema 的檔。
5. **索引是視圖，不是檔案**：Scrivener Collections、Plottr timeline、Campfire 的角色頁反查、Novelcrafter Matrix，全部是**查詢結果**，沒有人把它落成一支要維護的檔。
   > 這一點與現行系統「沒有索引檔，是刻意的」方向一致，可視為外部佐證。

## 三、大家都**沒有**的東西

零個工具有 → 每一項都是本系統的自造成本，值得逐項要求說出存在理由。

### 1. 源檔 → LLM 衍生分析檔的重生機制

Sudowrite 生成完 Story Bible 的欄位之後，**那份就是源**，人直接改，不存在「下次重生會覆蓋你的手改」。Novelcrafter 的 Codex 條目也是人寫、人改。**「把角色源檔展開成需求四象限＋馬斯洛的 `.ai.md`」這種層，市面零例。**

### 2. hash 新鮮度／過期偵測

上游改了，下游不會被標記 stale。作者社群的規範反而是反向的：**draft first, document afterward**——先寫，寫完再把「故事實際用到的事實」記下來，而不是預先發明一堆設定再想辦法同步。

> 業界原話：最快的建 bible 方式通常是先寫再記，這樣你記的是故事真的用到的事實，而不是你事先發明的。

### 3. 格式閘門（lint）

本系統有 12 支；別家是 0 支。差別在於：**別家不把設定切片餵 LLM，而是整條卡片丟進去**，所以沒有「逐欄取值者」，也就沒有欄位錯位的失效模式。

### 4. 裁決流／待裁決治理層

零例。最接近的只是一個手工慣例：維護兩份文件——**working bible**（草稿期隨意更新，可含推測與暫定）與 **canon bible**（書定稿後才更新，是讀者能拿來追究你的權威版本）。

### 5. 寫作前強制填滿設定

- Campfire 的 17 模組是**選購**的。
- Novelcrafter 官方明教「條目寫短一點」，因為條目會進 prompt、會花錢。
- 作者社群的規範是 **minimum viable documentation**：只記你真的會回頭查的東西；series bible 應該替你省時間，不是吃掉時間。

那份「真的會回頭查」的清單長這樣：世界規則與限制、cast state、關係狀態、時間線、**open threads（未回收的線）**、secrets。時間要記成相對時間（「圍城第 3 天」「流放後六週」）。
