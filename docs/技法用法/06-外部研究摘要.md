# 外部研究摘要：LLM 怎麼「按需使用方法論」

> 搜尋日期：2026-08-09。承 `05-按需載入驗證結果.md`。
> **全程唯讀 repo**，只新增本檔。這一支是**外部證據台帳**，不是提案。

## 0 · 為什麼有這一輪，以及它回答的是哪一個問題

作者的原問題：**「難道無法用管理 context 的方式達到目標嗎？是否只有訓練模型本身才可能解決？」**

`05` 回答不了這個問題，因為它測的那一格（路由）是三格裡最容易的。外部文獻把「按需使用方法論」拆成三個**獨立**的失敗點，而三者的判定不一樣：

| | 問的是什麼 | `05` 測了嗎 | 文獻判定 |
|---|---|---|---|
| **A 觸發** | 會不會想到要查 | ❌ `05 §8`「零證據」 | **預設就是壞的**，但有確定性解 |
| **B 路由** | 想到之後挑不挑得對 | ✅ 04＋05 主體 | **可解，而且 05 的形狀是對的** |
| **C 應用** | 載進來之後**產出**有沒有變 | ❌（`05` 的評分者 C 判的是「**作者**讀完能不能用」） | **真正的難處** |

一句話：**不是「只有訓練模型才行」，但 05 通過的那一格，本來就不是難的那一格。**

## 1 · 九條證據

每條四欄。**最後一欄是本檔存在的理由**——沒有它，這支檔只是書單。

### 1.1 階層式 progressive disclosure 從不幫忙，有時有害

| | |
|---|---|
| **主張** | 比較 raw 直接翻／**flat 單層索引**／**hierarchical 每塊自成 skill**，跨 Codex／Pi／Claude-Code 三個 harness、三個模型家族、三個 ∞Bench 子集 |
| **讀數** | 階層式在單一文件規模「never helps, sometimes hurts」——Pi 的 En.MC **0.9126 → 0.6398**。20 本書的語料庫規模才是分水嶺：raw 崩到 0.26、flat 穩在 0.46，開放式問答約 **1.8×** 準確率、約**一半** token 成本。作者結論：**"Progressive disclosure buys context, not intelligence."** |
| **出處** | [arXiv 2607.17598](https://arxiv.org/html/2607.17598v1)（**本輪唯一抓了全文的一篇**） |
| **打在哪** | `05` 的正式形態**不得**做成「先選檔、再選節」的兩層路由。而 `技巧知識庫/` 是 **311,134 B／225 節／27 支檔**——正好落在論文說 flat 有決定性優勢的那一側，這解釋了 `05` 四條判準為什麼會過。**單層扁平是結論，不是省事。** |

### 1.2 語意檢索先篩，大幅改善「從很多東西裡挑對的」

| | |
|---|---|
| **主張** | 把工具發現外包給語意檢索（RAG），只把命中的少數幾個送進 prompt |
| **讀數** | prompt token **砍掉 50%＋**；工具選擇準確率 **13.62% → 43.13%（約 3 倍）** |
| **出處** | [RAG-MCP, arXiv 2505.03275](https://arxiv.org/abs/2505.03275)；旁證 [MCP-Bench](https://arxiv.org/pdf/2508.20453)（每題掛 10 個干擾 server／100+ 額外工具） |
| **打在哪** | `05-原型/kb_route.py` 的粗篩是 **OR 字面關鍵詞比對**（`--symptom` 走 `k in r["sym"]`）。字面比對正是最吃「措辭同源」的那種匹配——也就是 `05 §9③`「兩個 Claude 撞詞」那個最致命攻擊點的**機制**。換成 embedding 是那一擊的直接對策，而且可測。 |

### 1.3 指令密度越高，遵守率越低；失敗模式是「遺漏」且偏向前面

| | |
|---|---|
| **主張** | IFScale：500 條關鍵詞納入指令的商業報告寫作，量遵守率隨密度的衰減曲線 |
| **讀數** | 最強前沿模型在 500 條密度僅 **68%**。三種衰減型態：threshold decay（o3、gemini-2.5-pro）／**linear decay（gpt-4.1、claude-sonnet-4）**／exponential decay。**主要失敗模式是 omission（遺漏）**，且**偏向較早出現的指令**。指令排序技巧在 N≈150 後失效。 |
| **出處** | [arXiv 2507.11538](https://arxiv.org/pdf/2507.11538) |
| **打在哪** | 直接解釋 `診斷01` 那個讀數：「**角色行為不得低於全書三分之二**」這把尺**已經在庫裡**，而生成側**連續 11 章遠低於它、零告警**。也解釋 `發想引擎/03 §1.1`「12 個步驟是同時壓在注意力上的 12 段約束」為什麼會失效。**推論：把方法論塞進輸入端，塞越多漏越多，而且不會有任何告警。** |

### 1.4 禁令型指令特別無效

| | |
|---|---|
| **主張** | 審計 16 個模型 × 14 個情境下對「不要做 X」的服從度 |
| **讀數** | 開源模型在**簡單否定**（"Don't do this"）下照做被禁事項 **77%**，**複雜否定**下 **100%**。一般解釋：負向約束要求模型壓抑一條**已被激活**的生成路徑，正向約束只要求走一條路；且「LLM 一旦被暴露於某知識就無法抑制使用它」。 |
| **出處** | [When Prohibitions Become Permissions, arXiv 2601.21433](https://arxiv.org/html/2601.21433)；綜述 [The Pink Elephant Problem](https://eval.16x.engineer/blog/the-pink-elephant-negative-instructions-llms-effectiveness-analysis) |
| **打在哪** | 這是 `_index.md` 那句實測觀察的文獻版本——「**只罰不給替代品，實測會換一種寫法繼續犯**」；也是 `診斷01`「**在一個只有負向約束的系統裡，最安全的產出就是最空的產出**」的機制解釋。**推論：`01-用法模式.md` 把「替代」（22 節）與「量尺」（19 節）排在前面是對的，而且理由比當時寫的更硬——那不只是「缺席的用法」，是唯二在密度衰減下還撐得住的形態。** |

### 1.5 無標準答案領域，目前最強的訊號形態是 rubric／checklist

| | |
|---|---|
| **主張** | 把「好不好」拆成一組**逐條可判**的問句，取代 scalar 分數或 pairwise 偏好 |
| **讀數** | **RaR**（Rubrics as Rewards）：用 instance-specific rubric 把 RLVR 擴到不可驗證領域，細粒度 rubric 作為結構化獎勵訊號優於 scalar。**RLCF**：從任務描述抽 per-instruction checklist（AI 判＋程式可驗兩種混合），是**唯一在所有評測基準上都一致改善**的方法。**RocketEval**：把評分重寫成「回答一組 checklist 問句」，讓小模型也能與人類偏好高相關。 |
| **出處** | [RaR, arXiv 2507.17746](https://arxiv.org/html/2507.17746v2)；[綜述：From Holistic Evaluation to Structured Criteria](https://arxiv.org/html/2606.08625v1)。⚠️ **RLCF 與 RocketEval 的具體讀數轉引自搜尋摘要與上述綜述，本輪未取得原始論文 URL、未核對。** |
| **打在哪** | **本輪最重要的一條。** 同一份方法論，放輸入端會被 §1.3 的 omission 吃掉；放**輸出端**逐條問答則不受密度衰減影響——因為每一條都被單獨問到。`01-用法模式.md` 盤的「量尺」（19 節）現在有了落點：**它該住在產出之後，不是產出之前。** |

### 1.6 skill 自主啟動率低，而 forced-eval hook 可大幅拉高

| | |
|---|---|
| **主張** | skill 的啟動依賴模型自發呼叫工具，實測不穩；改用 `UserPromptSubmit` hook 每次注入「逐支 skill 判 YES/NO → 才准 activate → 才准 implement」三步序列 |
| **讀數** | 基準情境自主啟動率 **約 20%**；forced-eval hook 拉到 **84%**。另：**祈使句 description**（"ALWAYS invoke when…"／"DO NOT write X without invoking this first"）在 Anthropic 自己的測試裡**改善了 6 支公開 skill 中的 5 支**。 |
| **出處** | [Measuring Claude Code Skill Activation With Sandboxed Evals](https://scottspence.com/posts/measuring-claude-code-skill-activation-with-sandboxed-evals)；[How to Make Claude Code Skills Activate Reliably](https://scottspence.com/posts/how-to-make-claude-code-skills-activate-reliably)；[Mandatory Skill Activation Hook (gist)](https://gist.github.com/umputun/570c77f8d5f3ab621498e1449d2b98b6)；[Agent Skills — Claude Platform Docs](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview) |
| **打在哪** | `05 §8` 選的觸發器是「**一支極輕的 skill**」——依 `CLAUDE.md` **E1**，那是**口頭承諾**。而 `發想引擎/04 §四` 已經獨立得出同一個結論（「hook 是最大的缺口……它是唯一能在模型的注意力預算之外執行的機制」），本條只是替它補上外部讀數。**`04 §0.2` 那個實例（封存紀律寫在規格裡、讀過、第一個工具呼叫就破了）＝ 那個 20% 的一個樣本。** |

### 1.7 skill 檔可以當「可訓練參數」，用 held-out 驗證閘門守每一次編輯

| | |
|---|---|
| **主張** | SkillOpt：模型權重凍結，把 skill 檔本身當參數優化。forward（跑任務）→ backward（優化器模型分析軌跡）→ update（**有界編輯** add/delete/replace，**必須通過 held-out 測試集的驗證閘門**才准落地） |
| **讀數** | 6 benchmarks × 7 models × 3 modes ＝ **52 格全部最佳或並列最佳**；GPT-5.5 平均 **+23.5 分**（SpreadsheetBench 41.8→80.7）；最終 skill **中位數約 920 tokens、只有 1–4 個被接受的編輯**；skill **可跨模型規模／harness／相關任務遷移**。設計理由原話："Bounded edits, validation gating, and best-version selection keep skill optimization controllable and auditable, **so the skill converges instead of drifting**." |
| **出處** | [SkillOpt — Microsoft Research](https://www.microsoft.com/en-us/research/blog/skillopt-agent-skills-as-trainable-parameters/) |
| **打在哪** | `05 §6.1` 那個明說「**這一格我沒有好答案**」的問題——門牌會說謊，而 `kb-lint` 守得了格式、守不了誠實度。SkillOpt 的答案是**別靠人審 227 行**：把「門牌對不對」定義成一組可重跑的 held-out 情境（該被挑中嗎／挑中後有用嗎），每次改門牌都要通過。`05 §5` 的三段盲流程**已經是這個 harness 的雛形**，差在它是一次性驗證而不是回歸測試。 |

### 1.8 反覆重寫會侵蝕細節：brevity bias 與 context collapse

| | |
|---|---|
| **主張** | ACE 把 context 當**演化中的 playbook**，用 generation → reflection → curation 的**增量**更新（grow-and-refine），而不是整份重寫 |
| **讀數** | 具名兩個失敗模式：**brevity bias**（越改越短，細節被摘要掉）與 **context collapse**（迭代重寫侵蝕領域知識）。offline（system prompt）與 online（agent memory）兩種設定皆一致優於強基線。 |
| **出處** | [ACE, arXiv 2510.04618](https://arxiv.org/html/2510.04618v1) |
| **打在哪** | 若門牌走 §1.7 的迭代優化，**不得整份重寫**——那正好會把 `05 §3.3` 撈回來的那些細節（突兀感清單的「先寫正常版，再把角色踢出舒適圈」兩步、象徵四類）摘要掉。這條與本 repo 已有的直覺同構：`CLAUDE.md` 對五支 rollup 的判定「任何找不到家的內容都會落在它身上，而沒有任何東西會反對」——ACE 講的是同一件事的另一半。 |

### 1.9 Claude Code 本身就是 hybrid：預載 ＋ JIT

| | |
|---|---|
| **主張** | 與其預先處理所有資料，agent 該持有**輕量識別符**（file paths、stored queries、web links），執行期才用工具動態載入 |
| **讀數** | 原文點名 Claude Code 是這個 hybrid model 的實例：**CLAUDE.md 被 naively 丟進 context，而 glob／grep 讓它 just-in-time 取檔**。其餘建議：system prompt 高度（避免 brittle if-else，也避免空泛）／工具集 minimal viable 且不重疊／少量 canonical 範例勝過 edge case 清單／compaction／structured note-taking／sub-agent 回傳 1,000–2,000 tokens 的濃縮摘要。 |
| **出處** | [Effective context engineering for AI agents — Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)；[Agent Skills: Progressive Disclosure as a System Design Pattern](https://www.newsletter.swirlai.com/p/agent-skills-progressive-disclosure) |
| **打在哪** | 佐證「**指針而非酬載**」這條路線本身是對的，也解釋 `CLAUDE.md` 為什麼是全系統最貴的一支檔（`write` 落一章載入 663,919 B、其中 73.6% 與書無關）——它剛好站在那個 hybrid 的「naively 丟進去」那一邊。**推論：`_index.md` 該是指針層，技法檔內文該是 JIT 層，而這正是 `05` 節級門牌的形狀。** |

## 2 · 三條結論

**① 三格的判定不一樣，不能一起講。**

| | context 能不能解 | 憑什麼 |
|---|---|---|
| **A 觸發** | ✅ 完全能，但要用 hook 不能用規勸 | §1.6：20% → 84% |
| **B 路由** | ✅ 能，單層扁平 ＋ 語意粗篩 | §1.1 flat 1.8×／§1.2 RAG-MCP 3× |
| **C 應用** | ⚠️ **部分**——輸入端受 §1.3／§1.4 硬限；**輸出端 checklist 繞得開** | §1.5 |

**② 唯一 context 硬解不了的殘餘，是模型預設的散文分佈。** 餵它「用具體意象取代抽象形容」，它讀懂了、也同意了，寫出來還是它習慣的那個腔。這一格確實是權重的事。

**③ 但那不構成「只能訓練模型」的理由，因為兩條路的前提是同一份資產。** RaR／RLCF 的前提是一套 rubric，SkillOpt 的前提是一組 held-out 任務——**「量尺 ＋ 情境測試集」同時是 context 方案的閘門與訓練方案唯一的訊號源**。而 §1.7 的讀數指出：在那份資產上「訓練門牌」比訓練權重便宜數個量級，效果還可能更好（skill 能跨模型、跨 harness 遷移，權重不能）。
