## 1 · 一頁框架

「按需使用方法論」不是一件事，是**四件事串起來**，而它們的難度與解法完全不同。

```
作者打一句話
   │
   ├─① 觸發   會不會想到要查？        ← hook（不佔注意力預算）
   │
   ├─② 路由   該開哪扇門？            ← 程式粗篩 + 單層扁平門牌
   │
   ├─③ 載入   把節內文餵進去          ← 節級 · 正向措辭優先
   │
   │      〔模型寫東西〕
   │
   └─④ 驗收   寫出來的東西合不合尺？   ← rubric checklist（輸出端閘門）
              ↑
        跨層：門牌自己怎麼維護         ← held-out 情境當回歸測試
```

| 層 | 機制 | 為什麼是這個機制 | 文獻 | 現行系統 | 本輪測不測 |
|---|---|---|---|---|---|
| **① 觸發** | `UserPromptSubmit` hook，注入「逐支評估 → 才准動作」序列 | **它不在模型的注意力預算裡**；且跨 skill 自動涵蓋、不會被忘記呼叫 | `06 §1.6`：自主 ~20% → forced-eval 84%；祈使句 description 6 改善 5 | 只有 skill description（模型觸發）。`.claude/` 底下**沒有 hooks** | ✅ 測**注入文字**的效力（模擬），**不測遞送** |
| **② 路由** | `kb-route --symptom` 程式粗篩 → 不足才 fallback 全表。**單層扁平，禁階層** | 確定性的工作進程式；扁平是文獻結論不是省事 | `06 §1.1` flat 1.8×／階層 0.91→0.64；`06 §1.2` RAG-MCP 3× | 無。作者靠 `_index.md`「何時查它」欄手動找 | `05` 已驗四條判準全過；本輪只補**真人措辭**穩健度 |
| **③ 載入** | 節級（平均 1,424 B）；**正向措辭優先**：替代 22 節／量尺 19 節 ＞ 診斷 45 節 | 輸入端的容量是**注意力**不是 token | `06 §1.3` IFScale 68%＠500 條、失敗＝遺漏；`06 §1.4` 否定失效 77–100% | 27 支檔整檔讀或不讀 | ✅ **Arm1** |
| **④ 驗收** | rubric checklist 當**輸出端**閘門（形態＝`PostToolUse` hook） | 逐條問答不受密度衰減影響 | `06 §1.5` RaR／RLCF／RocketEval | 12 支閘門**全部是「你寫錯了」，沒有一支問「你有沒有寫」** | ✅ **Arm2** |
| **跨層** | 門牌維護：held-out 情境當回歸測試、bounded edits ＋ validation gate、增量不重寫 | 門牌是「沒有機械判準的保證」 | `06 §1.7` SkillOpt 52/52、+23.5；`06 §1.8` ACE 防 collapse | 無 | ❌ 本輪不做，只寫進設計 |

## 2 · 逐層

### 2.1 ① 觸發 —— 唯一一格「預設是壞的、但解法是確定性的」

`05 §8` 自己寫下：

> 「**觸發沒測。** 設計選的是『一支極輕的 skill』，本輪沒有實作，因此『Claude 會不會在對的時刻想到要查』這件事**零證據**。」

外部讀數說那一格的預設值是 **約 20%**。而 `CLAUDE.md` **E1** 對這種東西的判定早就寫好了：**沒有檢查器的保證只是口頭承諾。** 一支「極輕的 skill」仍然是請求，不是強制。

`發想引擎/04 §四` 已經獨立得出同一結論，理由更精準：

> 「hook **完全不佔那個預算**——它住在檔案系統的事件裡，模型正在寫字的時候它照跑。而且它**跨 skill 自動涵蓋**……**這是 `references/` 和 subagent 都做不到的一格**——那兩個都要『被記得呼叫』。」

**本輪要測的不是 hook，是 hook 注入的那段文字。**

> **為什麼可以不測 hook 本身**：hook 的**遞送**是確定性的——`UserPromptSubmit` 觸發、script 跑、stdout 進 prompt，這條路徑不需要實驗證明。有不確定性的只有一件事：**那段被注入的文字，能不能讓模型真的去查。** 而那可以用 prompt 前綴模擬，不必動 `.claude/settings.local.json`。
>
> 這也讓本輪維持「唯讀＋純新增」的紀律。

**設計形態**（若實作）：

```
UserPromptSubmit
  → script 判斷這一句是不是寫作難題（否 → exit 0 靜默）
  → 是 → 跑 kb-route --symptom "<抽出的病症短語>"
  → stdout 注入：命中的節位址（≤5 行）＋「先判要不要開，再動作」
```

⚠️ 注意這個形態把 ① 與 ② **合成了一步**——注入的不是「請記得查知識庫」這種規勸，而是**已經查完的結果**。這正是 `發想引擎/04 §5.1` 那句話的形狀：「**模型醒來時看到的是結果，不是說明書。**」

### 2.2 ② 路由 —— 已驗，剩下一個致命的未知

`05` 的四條判準全過（六案例 4.5/6、假陽性 27.6% 且用不上 0/29、平均載入 4,151 B、空門牌 3.6%）。文獻只加碼了兩件事：

**① 別加深。** 階層式在論文裡「never helps, sometimes hurts」。`05 §10` 說的正式形態（門牌內嵌節標題下、索引走投影）就是 flat pack——**維持它**。任何「先選檔、再選節」的兩層設計都是論文量到會掉分的那一格。

**② 粗篩該換 embedding。** 現行 `kb_route.py` 是 OR 字面比對：

```python
hits = [r for r in hits if any(k in r["sym"] or k in r["title"] for k in kws)]
```

而 `05 §9③` 判為**最致命的攻擊點**正是：

> 「症狀欄與測試情境可能只是『兩個 Claude 的中文碰在一起』……**真正的作者會怎麼抱怨，這輪一個樣本都沒有。**」

**字面比對就是那個弱點的機制。** 換 embedding 是直接對策（`06 §1.2`），而它可測——本輪附帶測項②就是拿真人措辭去比字面粗篩的召回落差。

### 2.3 ③ 載入 —— 輸入端的容量是「注意力」，不是 token

這是本框架最反直覺的一層。`05` 量到「平均載入 4,151 B」並判定「✅ 省到了」——**但省 token 從來不是問題所在**。

`06 §1.3`：500 條指令密度下最強模型只剩 **68%**，主要失敗模式是 **omission**，且**偏向較早出現的指令**。翻成本系統的語言：即使門牌把對的 3 節挑進來了，那 3 節裡的十幾條準則會**被靜默地漏掉一部分，而且不會有任何告警**。

這在本 repo 有現成的病例：`診斷01` 量到「角色的行為/對話/意識不得低於全書三分之二」這把尺**已經在庫裡**，而生成側**連續 11 章遠低於它、零告警**。

`06 §1.4` 再補一刀：禁令型指令的服從度在簡單否定下只有 23%（＝77% 照犯）。而 `05 §3.3` 的普查說庫裡**診斷型 45 節**、替代 22 節、量尺 19 節——**最大的一類正好是最弱的那一型。**

**所以這一層的設計不是「載多少」，是「載哪一種」**：

| 型別 | 節數 | 在輸入端的預期效力 | 依據 |
|---|---|---|---|
| **量尺**（「一章 2–3 處、不連續兩段」） | 19 | **最高**——它是正向、有數字、可自我核對 | `06 §1.4`＋`06 §1.5` |
| **替代**（「禁令旁邊放該換成什麼」） | 22 | **高**——正向路徑，不需要壓抑 | `06 §1.4` |
| **診斷**（「你少寫了什麼」） | 45 | **最低**——禁令型，且需要壓抑已激活的路徑 | `06 §1.4` |

**這是可測的預測，本輪 rubric 刻意把禁令型與正向型各半並成對，就是為了量它。**

### 2.4 ④ 驗收 —— 為什麼它不是第三層的加強版

**最容易被誤解的一格：以為「輸出端 checklist」只是「輸入端方法論」的又一次提醒，力度大一點而已。不是。它是另一個機制。**

| | ③ 輸入端載入 | ④ 輸出端 checklist |
|---|---|---|
| 準則怎麼進到模型面前 | **一次全部**，混在其他 context 裡 | **逐條被問到**，一條一個回合 |
| 失效原因 | omission——沒有任何機制保證每一條被讀到 | 沒有 omission 的空間，因為每條都要回答 |
| 受密度衰減影響 | **是**（`06 §1.3`） | **否** |
| 受否定失效影響 | **是**（`06 §1.4`） | **較小**——「有沒有連續三段純講述」是可數的事實，不是要壓抑的路徑 |
| 它能不能告訴你「這次沒做到」 | 不能 | **能**，而且是可落檔的讀數 |

而這一格在本 repo 有一個現成的、獨立得出的同構結論——`發想引擎/03 附②`：

> 「補上正向地板。現行 12 支閘門**全部是『你寫錯了』，沒有一支問『你有沒有寫』**……**這是唯一會攔下 93 章崩塌曲線的東西，而它只需要數幾個數字。**」

**`發想引擎/04 §4.2` 的「正向地板 PostToolUse hook」與本層是同一格**——差別只在：`04` 講的是**機械可數**的那幾項（對白數／動作詞頻／在場有台詞角色數），本層講的是**同一個位置的語意版**（rubric 問句由 LLM 逐條回答）。

**兩者是同一條防線的兩段，不是二選一**：

| | 判官 | 守什麼 | 落點 |
|---|---|---|---|
| **正向地板** | 程式（`prose_metrics`） | 可數的（對白數、動作詞頻、篇幅） | `PostToolUse` hook，`發想引擎/04 §4.2` |
| **rubric checklist** | LLM 逐條回答 | 可指認但不可數的（「設定有沒有由角色行動帶出」） | 同一個 hook 的第二段，或 `*-test` skill |

`發想引擎/04 §9.4` 那句「**用一個計數器就攔得住。用 LLM 判官不一定**」仍然成立且重要——**所以 rubric 問句必須寫成「有沒有／幾處／最長幾行」，不得寫成「寫得好不好」**。那是把 LLM 判官逼回計數器的做法，也是 `06 §1.5` RocketEval 的核心設計。

### 2.5 跨層 —— 門牌自己怎麼維護

`05 §6.1` 標題就是「**門牌會說謊，而且沒有任何東西守得住**」，結尾寫「**這一格我沒有好答案。**」`05 §9` 更狠：「另外 226 行沒有任何人檢查過。真實錯誤率未知，而我唯一能說的是它**不是 0**。」

`06 §1.7` 的 SkillOpt 給了一個 `05` 沒考慮的形狀：**別靠人審 227 行。把「門牌對不對」定義成一組可重跑的測試。**

```
held-out 情境集（N 題，作者原話）
   ↓
門牌改動（bounded edit：add / delete / replace 一行）
   ↓
重跑：該被挑中嗎？挑中後評分為有用嗎？
   ↓
通過才落地；不通過就回退到 best version
```

`05 §5` 的三段盲流程（出題 A ／ 路由 B ／ 評分 C，互不知道對方存在）**已經是這個 harness 的雛形**——差在它是一次性驗證，不是回歸測試。

兩條約束：

- **增量，不整份重寫**（`06 §1.8` ACE）。整份重寫會把 `05 §3.3` 撈回來的細節（突兀感清單的「先寫正常版，再把角色踢出舒適圈」兩步、象徵四類）摘要掉。
- **`05 §6.1` 自己提的緩解仍然要做**：症狀欄必須指得出節內文的**字面依據**，指不出來的標成「衍生自末行註腳／衍生自策展判斷」——**把 over-promise 從隱形變成 lint 守得住的東西**。這與 held-out 測試互補：字面依據守「有沒有標」，held-out 守「標得對不對」。

> **本輪的 rubric 是這條紀律的第一次實作**：`08-原型/rubric-T*.md` 每一條都必須指得出節內文的字面依據，指不出來的不准進 rubric。

## 3 · 這個框架不解決什麼

**① 模型預設的散文分佈。**
餵它「用具體意象取代抽象形容」，它讀懂了、也同意了，寫出來還是它習慣的那個腔。四層裡沒有任何一層碰得到這一格——③ 是提醒、④ 是抓，但**抓到之後要它改，它改出來的仍然在同一個分佈裡**。這確實是權重的事。

**② 庫裡沒有的東西。**
`05 §4` 第 4 列（可信度型刪減）0 命中，判定為真陰性——「這個世界裡有一個更正確、也更無聊的做法，讓角色採用它」這一格**內容確實不在 27 支檔裡**。路由誠實回報 0，這正是它該做的。四層改善的是知識的**用法**，不是知識的**存量**。

**③ 接龍（型別鍵）。**
`05 §8` 記為零測試，本框架也沒有把它排進來。`06 §1.1` 的「hierarchical never helps, sometimes hurts」讓我對它的期望值調低了——**它不等於接龍會失敗**（型別接合 ≠ 階層路由），但排序上它在四層之後。

## 4 · 「是否只有訓練模型才可能解決」

**不是，而且方向反了。**

| | context 能不能解 | 憑什麼 |
|---|---|---|
| ① 觸發 | ✅ 完全能，但要用 hook 不能用規勸 | 20% → 84% |
| ② 路由 | ✅ 能 | flat 1.8× ／ RAG-MCP 3× |
| ③ 載入 | ⚠️ 受 §2.3 的硬限，但可以靠**選型別**（正向 ＞ 禁令）改善 | IFScale 68% ／ 否定 77–100% |
| ④ 驗收 | ✅ 這一層**繞開**了 ③ 的硬限 | RaR／RLCF |
| 散文分佈 | ❌ | — |

**而即使哪天真要走訓練那條路，路徑仍然要先經過現在這件事。**

RaR／RLCF 的前提是一套 rubric；SkillOpt 的前提是一組 held-out 任務。**「量尺 ＋ 情境測試集」同時是 context 方案的閘門與訓練方案唯一的訓練訊號。** 不是二選一，是同一份資產的兩種用法。

而 `06 §1.7` 的讀數說明：在那份資產上「**訓練門牌**」比訓練權重便宜數個量級（中位數 skill 約 920 tokens、1–4 個編輯），效果還可能更好——skill 能跨模型、跨 harness、跨相關任務遷移，權重不能。

## 5 · 落地順序（若作者要走）

**與 `發想引擎/04 §十` 的六項改造順序合併看**，本框架只增加兩項，且都排在它後面：

| # | 做什麼 | 出處 | 為什麼這個順序 |
|---|---|---|---|
| 1–3 | `共同約定.md` 移出迴圈 → `write` 拆 `references/` → 前置改 slash command | `發想引擎/04 §十` | 零風險、不動流程，且**它們騰出的注意力預算正是 ③ 要用的** |
| 4 | 正向地板做成 `PostToolUse` hook | `發想引擎/04 §4.2` | **＝本框架第 ④ 層的機械那一半**；先做可數的 |
| **4.5** | **rubric checklist 接到同一個 hook** | **本檔 §2.4** | 語意那一半。**先有 4 的 harness，這一項只是加一段** |
| 5 | 落檔外包給 subagent ＋ 閘門 hook | `發想引擎/04 §十` | 與本框架無關，但風險低、可並行 |
| **5.5** | **門牌內嵌技法檔 ＋ `kb-lint` ＋ `tools/kb_route`** | **本檔 §2.2**／`05 §10` | 要改 27 支技法檔，**應該等 `08` 那一輪的讀數出來再決定值不值得** |
| 6 | 每章一個 subagent | `發想引擎/04 §十` | 仍排最後 |

**① 觸發那一層刻意沒進表**：它依賴 5.5 的 `kb-route` 存在（注入的是查完的結果，不是規勸），所以它是 5.5 的延伸而不是獨立一項。

## 6 · 本框架的哪幾格有讀數、哪幾格是推論

| 格 | 狀態 |
|---|---|
| ② 路由可行 | **有讀數**（`05` 四條判準，n=1 書、14 題、單一路由者、**且症狀鍵未經真人措辭測試**） |
| ① 觸發預設是壞的 | **外部讀數**（社群實測，非同行評審）＋ `發想引擎/04 §0.2` 的一個本地樣本 |

| 門牌誠實度 | **未知，且不是 0**（`05 §9`）← 本輪不測 |
| 接龍 | **零讀數** ← 本輪不測 |

## 7 · 重跑方式
