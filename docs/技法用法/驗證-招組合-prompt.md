## 你在驗證什麼

有一個假說：**寫作技巧的可用單位不是「技法檔」，而是「招」**——一招 ＝ 一個具名的、有型別的變換（吃某幾個具名故事物件，吐另一個）。若成立，就可以做到：

- 小需求只載入一招，成本不隨系統大小成長；
- 複雜需求靠**招與招接龍**達成，而不是靠一支更大的 skill；
- 「什麼時候用什麼」由**前提比對**（程式可判）收窄，再由 LLM 在存活集合裡挑。

這個假說有三個可以分別證偽的部分。**你的任務是分別證偽它們，不是證實它。**

| Part | 主張 | 如果錯了，錯在哪 |
|---|---|---|
| **0** | 型別詞彙足以描述真實作者的決策 | 詞彙有系統性缺口 → 整個方案的地基 |
| **1** | 前提比對有鑑別力 | 路由不可行，只能全載 |
| **2** | 招真的接得起來 | 「組合」是修辭，不是機制 |

> ⚠️ **反向動機聲明**：這份規格的作者（前一個 session）**相信**這個假說。你的價值來自於**找到它不成立的地方**。若三段全過、且你找不到任何反例，請在報告裡明說你嘗試過哪些破壞方式而失敗——「我沒找到問題」與「我沒找」必須可區分。

## 前置：建立招目錄

### 步驟 A — 讀來源

1. `docs/發想引擎/01-引擎目錄.md` — **32 招已經寫好了**，每招附「什麼時候用／輸入／步驟／輸出／依據／載入／不做」。這是你的招來源，不要重新發明。
2. `docs/技法用法/01-用法模式.md` — 14 種用法模式。用它替每招標「這一招是哪一種用法」。
3. `docs/技法用法/02-覆蓋矩陣.md`、`03-Data逐篇台帳.md` — 只在需要查某招出處時翻，不必通讀。

### 步驟 B — 定型別詞彙

**故事物件型別**是招的輸入輸出單位。下面是**種子詞彙，不是標準答案**：

```
碎片        raw 素材，未成形
概念        有衝突內核、但還不是故事
題旨        「因為 X，導致 Y」
主線        主要劇情走向
目標        某角色要什麼（可掛主角／反派／配角）
阻礙        對抗某目標的力量
世界規則    一條核心設定
代價        規則的成本
角色骨架    恐懼｜傷痕｜謊言｜想要｜需要｜弧線型
角色位置    尚未具名的功能位（對手／盟友／受害者／得利者）
關係        兩個角色之間的線
幕          五要素：角色｜時空｜行動｜衝突｜結果
事件足      前因／中間／後果 之一
伏筆位      埋點 ＋ 預定回收點
揭露序      什麼時候放出哪一個
張力型別    資訊差三型（同步／優越／替他捏汗）
結局型      六型之一
情緒曲線    分段的升降
刪除候選    可以砍的東西
```

**你必須做的三件事**（這是 Part 0 的實質內容）：

- 每次你**不得不新增**一個型別 → 記下來，並寫清楚為什麼既有的不夠用。
- 每次你發現某個型別**太粗**（兩招都吃「幕」，但吃的其實不是同一種東西）→ 記下來。
- 每次某個型別**從頭到尾沒被任何招用到** → 記下來（表示是我多加的）。

### 步驟 C — 產出招目錄

把 32 招各壓成**一行**，欄位固定：

```
招名 | 用法模式 | 前提（這本書必須已經有什麼） | 吃（型別） | 吐（型別） | 何時用（一句，用作者會講的話）
```

**硬性要求**：

- **「前提」必須是可機械判定的**——寫「已存在 ≥1 個 `世界規則` 且該規則沒有 `代價`」，**不要**寫「當作者覺得設定不夠深時」。凡是你只能寫成後者的招，**單獨列出來**，它們就是「前提不可機械化」的那一類，本身是重要發現。
- 一行控制在 200 B 內。記錄整份目錄的總位元組數。

## Part 0 · 逆向拆解（測型別詞彙是否夠用）

**讀** 引子 ＋ ch1–20。**拆解** ch16–20 這五章。

對這五章，逐條列出**作者實際做過的決策**——不是劇情摘要，是決策。例如：

- 「讓主角在此處得知 X，而不是讓他更早知道」＝ 一個揭露序決策
- 「這一章的對手是 A 而不是 B」＝ 一個角色位置決策
- 「這件事的後果延到下一章才交代」＝ 一個事件足決策

每條標註：

| 決策 | 對應到哪一招 | 吃／吐的型別對不對得上 | 若無對應：缺的是招還是型別 |
|---|---|---|---|

**判準（先寫下來，再去看結果，不要事後調整）：**

| 讀數 | 意義 |
|---|---|
| 對應不到任何招的決策 **> 30%** | ❌ 招目錄有系統性缺口 |
| **> 40%** 的決策都擠在同一招 | ❌ 招太粗，等於沒有分辨力 |
| 新增型別 **> 5 個** | ❌ 型別詞彙沒收斂，地基不穩 |
| 有型別**零使用** | ⚠️ 該型別是虛設，記下來 |

## Part 1 · 前提過濾（測路由是否有鑑別力）

**凍結點：ch20 結束。**

### B1 · 先寫「書況」

只根據 ch1–20，列出這本書**現在已經有哪些具名故事物件**，按型別分。例如 `世界規則: {紅月亮事件, 污染源分級, 精神異變}`、`目標(主角): {…}`、`伏筆位: {…}`。

> 這一份等同於現行系統 `*-lint --emit` 投影會吐的東西。**寫的時候留意：這份書況有多少是程式真的算得出來的，有多少其實需要閱讀理解？** 這個比例決定路由能不能自動化，請在報告裡明確回答。

### B2 · 跑過濾

拿書況比對 32 招的前提，逐招判 **合法／不合法**，不合法的寫出缺哪一格。

**判準：**

| 存活招數 | 意義 |
|---|---|
| **> 20** | ❌ 前提沒有鑑別力，等於沒過濾 |
| **< 3** | ❌ 前提太嚴，正常書況會餓死 |
| **5–15** | ✅ 甜蜜區 |

### B3 · 關鍵檢查（比招數更重要）

**假裝你是這本書的作者，站在 ch20 結束的位置**，寫下你接下來真正想做的 3 件事（用作者會講的話，例如「我想讓某個一直很可靠的人變得不可信」）。

然後回答：**這 3 件事，在存活集合裡各自找得到對應的招嗎？**

- 找得到 → 路由至少對這幾件事有效
- 找不到，但招在 32 招裡、只是被前提擋掉 → **前提寫錯了**（這是最有價值的發現）
- 32 招裡根本沒有 → 招目錄的洞

## Part 2 · 接龍與可挑性（測組合是否為真）

從凍結狀態實跑一條 **3–5 招**的鏈。

### 規則

1. **貪婪，不預先規劃**：跑完一招 → 出候選 → 選一個 → **重算存活集合** → 再選下一招。不准一次規劃五步。
2. 每招輸出 **2–3 個候選，各附代價**。不准只給一個答案。
3. **只提案，不寫任何書內檔。**
4. 每一步記錄：**這一招吃的型別，是不是上一招真的吐出來的東西？**

### 每步必填

| 欄 | 內容 |
|---|---|
| 招名 | |
| 吃到的東西 | 具體指名，並標出它來自哪一步 |
| 型別接合 | `直接吻合` / `需要轉換（寫出轉換了什麼）` / `硬套` |
| 2–3 個候選 | 各附代價 |
| 可挑性 | 你會不會當場挑得下去？挑不下去就寫為什麼 |
| 載入量 | 這一步實際讀了哪些檔、多少 B |

### 判準

| 讀數 | 意義 |
|---|---|
| **型別接合** 出現 `硬套` ≥ 1 次 | ❌ 「組合」是修辭不是機制 |
| 出現 `需要轉換` | ⚠️ 記下轉換內容——它可能是一個**缺掉的招** |
| 某一步後**沒有合法後繼招** | ❌ 鏈會斷，招目錄不連通 |
| 三個候選**實質是同一件事的換句話說** | ❌ 招沒有生成力，只是換句話說 |
| 全鏈總載入量 | 對照 `docs/發想引擎/03-現行系統診斷.md` 的 `write` doc 側 566,304 B |
